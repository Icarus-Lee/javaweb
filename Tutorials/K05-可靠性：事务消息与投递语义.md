## 1. 生活类比与动机：外卖骑手的三次按铃

骑手送完餐要上报"完成"。但手机网络可能吞掉这条上报。三种姿势对应三种投递语义：

- **多按几次**（at-least-once）：网络吞了就重按。商家端要**扛得住"完成"通知来两遍**（看到了一次还是一次）。**这是"肯定不失败，但要防重"。**
- **按一次不重按**（at-most-once）：拍一下就走。丢了就是丢了——商家永远不知道你已经送达。**这是"绝不重复，但可能丢"。**
- **精准一次**（exactly-once）：与商家 Affairs 签一份"应答对账协议"，上报与"完成单"入账**同进同出**（Kafka 事务 API 之类的重量级姿势）。**最贵也最稳。**

**现实里，绝大多数业务选第一种 + 业务侧防重（幂等）**：网络抖动难免、重放难免，但只要"处理两遍=处理一遍"，重放就无害。**这就是本项目的姿态**——K04 的 DispatchConsumer 已经长在这里了，本章把它挖出来钉实。

## 2. 投递语义三方表

| 语义 | 承诺 | 配置面貌 | 代价 / 自损 | 适用 |
|---|---|---|---|---|
| **at-least-once** | 不丢、可能重（producer acks 确认后才算发出；consumer 消费失败不提交） | 默认姿势 | **消费端必须幂等**；网络抖动会重放 | 绝大多数业务（**本项目姿态**） |
| **at-most-once** | 或零或一：先提交位移再处理 | 消费端"先 commit 后干活"或例程快吞 | **可能丢**（处理崩了消息已报已消费） | 监控指标、日志类 |
| **exactly-once** | 不多不少 | Kafka 事务 API（producer 事务性尽早投递） | 配置重、吞吐跌 | 金融级账务 |
| **乱配** | at-least-once 的投递 + 不幂等的业务 | 忽略幂等 | **重复派单/重复扣款** | ——事故的常见配方 |

**本项目口径一句话**：**at-least-once 的投递 + 业务状态机幂等 = 效果上的 exactly-once**。

## 3. 幂等消费的真-code（DispatchConsumer 三条门）

**K04 已贴全码，本节挖"防重"的三条门**：

```java
@KafkaListener(topics = OrderEventProducer.TOPIC, groupId = "dispatch")
@Transactional
public void onOrder(String payload) {
    String orderNo = extract(payload, "orderNo");
    String phase   = extract(payload, "phase");

    Order o = orders.findByOrderNo(orderNo).orElse(null);
    if (o == null || !"PAID".equalsIgnoreCase(phase) || !"PAID".equals(o.status)) return;
    if (o.status.equals("PAID")) {
        o.status = "DISPATCHED";
        o.riderId = 9000L;
        o.dispatchedAt = Instant.now();
        orders.save(o);
        System.out.println("[dispatch] order=" + orderNo + " -> 派给骑手 9000");
    }
}
```

### 三条门逐门读

1. **门一：假单拦**（`o == null`）：`findByOrderNo` 查不到就不动 —— broker 重投或**假事件**（实训案例有 `fake-0000`）直接路过，不产生任何 H2 写。
2. **门二：phase 校验**（`!"PAID".equalsIgnoreCase(phase)`）：消息语义必须"已支付"——CREATED 或别的 phase 直接 return；**这保证"白派单"事件进不了门**。
3. **门三：状态机挡疑**（`!"PAID".equals(o.status)`）：订单已在 DISPATCHED/CANCELLED 状态就不再派——**重复消费 PAID 事件也到此打住**。

**三门的威力**：任何一条同 phase PAID 事件**第二次进客厅**，都会在门三撞回——`System.out.println` 不打第二次、H2 不再写、 **派单只发生一次**。**这就是幂等的字面承诺：处理两遍=处理一遍。**

### 为什么去重键不用 Redis 的 SADD？

R02 练习里练过 `SADD used:fingerprint` 这种"用 Set 记已处理"的姿势。**本项目的 DispatchConsumer 却选了"DB 状态机"当去重键**（orderNo + status）。理由三条：

- 状态机本来就是业务的一部分（订单总要有 status），不额外付"指纹生命周期"的设计费；
- 指纹在 Redis 里会过期，而过期前后的行为边界是另一课的坑；状态机活在 H2 里，与订单同寿；
- 真要按"事件 ID 去重"防重，K05 的口径是"同一业务键 + 状态机"足矣——**越少的机制，越少的错误面**。

## 4. @Transactional 的窗口（何时需要、何时摆设）

**一条总律**：**@Transactional 只对"同一个数据库里的多个写"负责**。consumer 方法体里若只有一个写，事务注解近乎摆设（但不等于有害——为了防未来添写时漏保护，很多团队选择"宁可挂着"）。

### DispatchConsumer 为什么挂着 @Transactional？

- **当前一个写**（`orders.save`）：事务此刻其实是 1 个写的"单笔事务"，语义无害。
- **面向未来保护**：将来这里若追加 rider 表写、dispatch 流水写——注解已在，多写一包即有效。
- **与 at-least-once 的配合**：DB 写失败抛运行时 → 事务回滚 → **offset 不前进** → 同条消息下轮重试。**"事务 + 不提交位移"正是 at-least-once 的另一半。**

### 窗口定位表

| 场景 | 要 @Transactional 吗 | 口径 |
|---|---|---|
| consumer 内多个 DB 写 | 要（必须） | 保持原子与回滚 |
| consumer 内单写 | 可挂可不挂（教学挂，防未来漂移） | 本项目的选择 |
| 跨 Redis + DB + Kafka | **事务包不住** | **每步留退路：补偿为王**（S11/R04 祖源） |
| 纯 Kafka 事务消息 | 另属 exactly-once 话题 | 教学不实、仅讨论 |

**一句总**：事务管 DB 内的多写；跨系统的因果性一靠**事件顺序**（K06）、二靠**等级补偿**（R04 的 INCR 还票库存）、三靠**业务幂等**（本章三门）。**没有一招包打天下。**

## 5. 三笔勘证（每个门一笔真账）

| 业务流 | 三门上的走位 | DB 侧后果 | 业务后果 |
|---|---|---|---|
| `fake-0000` 假事件（真信 topic 有实录） | 门一：findByOrderNo → null → return | 无 H2 写 | 假单无害通过 |
| 真 PAID 事件来一次 | 三门全过 → save → DISPATCHED | H2 落 1 行 | 一次派单、骑手 9000 |
| 同一真单 PAID 重放 | 门三：o.status 已 DISPATCHED → return | 无 H2 写 | 不重复派单 |

**实测（真一单）**：

```
$ curl -s -X POST "http://127.0.0.1:8085/api/orders/2477c7fa-.../pay"
{"status":"PAID"}
# DispatchConsumer 消费一次：
[dispatch] order=2477c7fa-... -> 派给骑手 9000
# 再来同 phase 事件（重放/其他消费者会碰同样场景）——不再打印第二行 [dispatch]
```

**三门全在"业务键 + 消息语义 + 状态机"三个落点**——假单拦、误投拦、重放拦。这就是"业务幂等"的真实落地：**不加新设备，全靠状态机自己挡。**

## 9. 参考答案

**练习 1**（表格样）：
at-least-once = 不丢可能重（acks 确认 + 不提交位移）；at-most-once = 先 commit 后处理（可能丢）；exactly-once = 事务 API（贵）；乱配 = at-least-once 投递 + 不幂等业务（重复派单事故配方）。

**练习 2**（实录要点）：重投同 phase PAID、该单 status 已 DISPATCHED → 门三拦回 → `[dispatch]` **不出现第二行**。**这正是去重键+状态机在真 topic 上的实证。**

**练习 3**（要点）：consumer 抛异常 → 当前消息 offset 不提交（at-least-once 的重试姿势）→ 同条消息反复。**若异常永不消失，就退化为"无限重试"**——这就是 K06 的前奏（重试上限 / 死信 topic）。

**练习 4**（要点）：三步流水各自的退路——DB 写失败 → 抛异常回滚；Redis 写失败 → 业务键 INCR 补偿；Kafka 发失败 → offset 不前进、下轮重试，或 producer 侧 get() 等 ack。**每步有退路的流水**,与 R04 的"锁 + 扣 + 补偿"一脉相承。

## 10. 本节小结

- **语义表**：at-least-once（不丢可能重） / at-most-once（不重可能丢） / exactly-once（事务 API，贵）；**本项目 = at-least-once + 业务幂等 = 效果上的 exactly-once**。
- **幂等三条门**：假单拦（orderNo 必须真实存在）、phase 校验（语义 Gate）、状态机挡疑（DISPATCHED 后不再派）。**重复消费无害的本金。**
- **@Transactional 的窗口**：只为 DB 内多写服务；跨系统靠补偿不靠事务——"每步留退路"贯穿 R04/K 全线。
- **三笔真账**：fake 拦 / 真单一派 / 重放拦——三条门各就各位。

## 附录 A：语义三方的"多尔一角"（配置代码样貌）

| 视角 | at-least-once | at-most-once | exactly-once |
|---|---|---|---|
| producer 侧 | 默认（acks=1 起，ack 确认后算发） | 无所谓（丢了丢了） | enable.idempotence + 事务前缀 |
| consumer 侧 | 处理完才提交位移 | 先提交位移再处理 | 与事务 API 协作 |
| 业务端 | **必须幂等** | 别指望零丢失 | 可少写防重（但仍然建议） |
| 本项目落点 | DispatchConsumer 三重门 | ——（没有这种消费者） | ——（教学不实） |

**什么姿势判别你现在的语义**：看 consumer"异常时 offset 动不动"——不动即 at-least-once（会重试）；异常也照提交即 at-most-once（丢而不重）。

## 附录 B：幂等的三种实现路线对照（本项目的选择与备胎）

| 路线 | 实现载体 | 代价 | 备注 |
|---|---|---|---|
| **状态机幂等（本项目）** | DB 的 status + 三重门 | 零新设备 | 与业务同寿，最省 |
| Redis 指纹幂等 | `SETNX dedup:{orderNo}` + TTL | 新设备 + 过期语义设计 | 适合"无状态机的轻事件" |
| DB 唯一约束 | dispatch 表 orderNo 唯一索引 | 迁移代价小 | 兜底防重（逃不掉重复写时报错） |

**三条路的共性**：**都是"给同一业务事实挂唯一标签"**——区别只是标签挂在哪里、谁扛过期与迁移。

## 附录 C：@Transactional 挂与不挂的两难（一张表决策）

| 你 consumer 里在做的事 | 挂不挂 | 一句理由 |
|---|---|---|
| 多个 DB 写（save A + save B） | **挂** | 打包成败，防半成品 |
| 单个 DB 写 | 可挂（防未来漂移） | 1 写事务无害 |
| DB 写 + Redis 写 | 挂了也管不到 Redis | **Redis 走补偿**（R04 祖源） |
| DB 写 + Kafka 发 | 同上 | **事件丢了靠重试/对账**，不靠 DB 事务 |

## 附录 D：本节三重门的"重放矩阵"

| 重放场景 | 门一（假单） | 门二（phase） | 门三（状态机） | 结果 |
|---|---|---|---|---|
| fake-0000 假事件 | 拦 | —— | —— | 无害通过 |
| CREATED 事件重放 | 过 | **拦**（phase≠PAID） | —— | 白派单防住 |
| 真 PAID 重放 | 过 | 过 | **拦**（已 DISPATCHED） | 重复派单防住 |

**三重矩阵一图收**：三门各防一种事故——缺失/语义/状态。少装一门，就多一种事故常态。

## 1. 冷启动顺序：为什么是这个顺序

`infra/start-all.sh` 的四段：

```
① Redis（6379）  →  ② Kafka（9092，KRaft 单节点）  →  ③ 后端 ×5（8081-8085）  →  ④ Nginx（9090）
```

依赖决定顺序：

- **Redis 必须最先**：demo-counter、train、takeaway 启动时就要读写 Redis（种子数据灌 key）；
- **Kafka 第二**：train/takeaway 的 producer/consumer 启动即连接；起不连上会重试但日志刷屏；
- **后端互不依赖**：五个 jar 并行起都行（脚本里串行只是日志可读）；每个起完用 `/dev/tcp` 探测端口就绪（start-all.sh:44）；
- **Nginx 最后**：它反代的所有上游都已就绪，一次 reload 直接可用。

### 脚本里的就绪判定手法（值得抄走）

```bash
for i in $(seq 1 40); do (echo > /dev/tcp/127.0.0.1/$port) 2>/dev/null && break; sleep 0.5; done
```

`/dev/tcp/HOST/PORT` 是 bash 内建的 TCP 探测（不用装任何工具）——端口通即认为就绪。**端口通 ≠ 应用就绪**（Tomcat 先于 Spring 上下文完全加载），但教学场景够用；生产建议换成真正的健康检查（如 actuator/health，S09）。

### 幂等设计：重复跑不炸

每段都先探测"已在线就跳过"（Redis PING、9092 TCP、jar 端口检查）——**start-all.sh 可以反复执行，第二次只会补齐缺的组件**。这是运维脚本的第一美德。

## 2. 进程托管两种姿势

### 2.1 nohup（当前脚本的方式）

```bash
nohup "$JAVA_HOME/bin/java" -jar "$jar" > "$ROOT/logs/$name.log" 2>&1 &
echo $! > "$ROOT/logs/$name.pid"
```

- `nohup ... &`：后台运行，终端关闭不死（SIGHUP 被忽略）；
- `> log 2>&1`：stdout 和 stderr 都进日志——**这是你排查问题的第一现场**；
- `echo $! > pid`：记下 PID，stop-all.sh 靠它精准杀进程。

nohup 的短板：**崩了没人拉起来**、机器重启后全没了、没有统一的状态查询。所以有了——

### 2.2 systemd（新增模板：infra/javaweb.service）

```ini
[Unit]
Description=javaweb takeaway (Spring Boot 8085)
After=network.target redis.service kafka.service

[Service]
Type=simple
User=icaruslee
WorkingDirectory=/home/icaruslee/Projects/javaweb
Environment=JAVA_HOME=/usr/lib/jvm/java-21-openjdk
ExecStart=/usr/lib/jvm/java-21-openjdk/bin/java -jar backend/takeaway/target/takeaway-1.0.0.jar
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
StandardOutput=append:/home/icaruslee/Projects/javaweb/logs/takeaway-systemd.log

[Install]
WantedBy=multi-user.target
```

逐行讲关键项：

| 指令 | 含义 | 为什么是它 |
|---|---|---|
| `After=` | 本单元在这些之后启动 | 依赖顺序（对应 start-all 的 ①②） |
| `WorkingDirectory=` | 进程的工作目录 | **H2 相对路径 `./data/takeaway` 在这定位**——不设会建到 / 下 |
| `Type=simple` | ExecStart 前台进程即主进程 | java -jar 不自守护，simple 最贴切 |
| `SuccessExitStatus=143` | 退出码 143（SIGTERM）算正常退出 | stop 时 JVM 被 kill -15，不算失败 |
| `Restart=on-failure` + `RestartSec=5` | 崩溃 5 秒后自动拉起 | nohup 做不到的事 |
| `StandardOutput=append:` | 日志追加到文件 | 等价 nohup 的重定向 |

部署三连（需要 sudo）：

```bash
sudo cp infra/javaweb.service /etc/systemd/system/javaweb-takeaway.service
sudo systemctl daemon-reload
sudo systemctl enable --now javaweb-takeaway   # 开机自启 + 立即启动
systemctl status javaweb-takeaway              # 看状态
```

**选型口诀**：开发机/演示用 nohup（轻、无权限要求）；常驻服务用 systemd（自愈、自启、统一管理）。

## 3. Nginx 静态部署与反代（nginx-reload.sh）

`infra/nginx-reload.sh` 干三件事：

1. **生成配置**（heredoc 写 nginx.conf）：静态站与反代一目了然——

```nginx
location /takeout-ui/  { alias /…/frontend/takeout-ui/dist/; try_files $uri /takeout-ui/index.html; }
location /apitakeout/  { proxy_pass http://127.0.0.1:8085/api/; }
listen 9090;
```

   `try_files $uri /index.html`：Vue SPA 的 history 路由兜底——刷新任何路径都回 index.html 由前端路由接管。
2. **`nginx -t` 先验配置**：配置写错不会打死正在跑的服务（reload 前必验）。
3. **区分冷启与热重载**：有 pid 文件且进程活着 → `nginx -s reload`（不断连接平滑换配置）；否则冷启。

前端产物从哪来？`build.sh` 的第二段：`npm run build` 产出 `dist/`；脚本还贴心地在 dist 缺失时现编一次（nginx-reload.sh:12-18）。

## 5. 常见故障排查手册

### 5.1 端口冲突（Address already in use）

**症状**：`start_jar` 打印 `✗ xxx 启动失败`；日志里 `Web server failed to start. Port 8085 was already in use`。

**排查**：

```bash
$ ss -ltnp | grep 8085          # 谁占着 8085
LISTEN 0  ... users:(("java",pid=12345,...))
```

**处置**：是旧实例 → `kill 12345`；是别的程序 → 改 `application.yml` 的 `server.port` 或换回约定端口。

### 5.2 缺 jar

**症状**：start-all 打印 `✗ 缺 jar：…/takeaway-1.0.0.jar（先跑 infra/build.sh）`。

**排查与处置**：

```bash
$ ls backend/takeaway/target/*.jar     # 没有 → 编译
$ bash infra/build.sh                  # mvn -T 4 package + 前端 build，一次齐活
```

深因常是：只 `mvn compile` 没 `package`；或多模块 reactor 里单模块单独构建没带依赖。**信脚本，别手拼 mvn 参数**。

### 5.3 Kafka 未格式化（KRaft 存储缺失）

**症状**：kafka.log 里 `InconsistentClusterIdException` 或启动后 9092 一直不通。

**排查**：

```bash
$ ls data/kafka/kraft/cluster.meta.properties    # 不存在 → 没格式化过
```

**处置**（start-all.sh:22-29 已经自动做，理解它）：

```bash
UUID=$(python3 -c 'import uuid;print(uuid.uuid4())')
tools/kafka/bin/kafka-storage.sh format --standalone \
  --cluster-id "$UUID" --config tools/kafka/config/server.properties
```

原理：KRaft 模式下 broker 第一次启动前必须用 cluster-id **格式化存储目录**（相当于"初始化账本"）。注意：`rm -rf data/kafka/kraft` = 全部 topic/offset 清零重来（消费组 offset 也没了——dispatch 组会触发 auto-offset-reset，W03 的知识当场回收）。

### 5.4 快诊表

| 症状 | 第一现场 | 快诊命令 |
|---|---|---|
| 500 全线 | 后端日志 | `tail -50 logs/takeaway.log` |
| 页面 404 | nginx | `tail logs/../nginx/run/logs/error.log`；`nginx -t -c infra/nginx/nginx.conf` |
| 派单不生效 | Kafka | `kafka-consumer-groups.sh --describe --group dispatch`（看 LAG） |
| 登录 401 | JWT | token 过期（ttl-minutes=120）重登 |
| H2 打不开 | 锁文件 | `data/*.lock.db` 残留（异常退出），停进程后删 |

### 参考答案要点

- 思考 1：端口通只说明 Tomcat 起了，Spring 上下文（含 Kafka 消费者注册、种子数据）可能还没好——`curl -s 127.0.0.1:8085/api/health` 返回 `{"ok":true}` 才算真就绪。
- 思考 2：JVM 收到 SIGTERM(15) 正常关闭时退出码 = 128+15=143；systemd 默认视非零为失败，声明 143 才不会误判"崩溃"而触发 Restart。
- 思考 3：新实例起不来（端口被占）→ systemd 判定失败 → 5 秒后再拉 → 再失败……反复重启刷爆日志；正确做法是启动前探测/`Before=` 排序，或用 `ss` 预检脚本作为 ExecStartPre。
- 思考 4：消费组 offset 随存储一起没了 → dispatch 组变"无 offset 组" → `auto-offset-reset=latest` 生效 → 从最新开始消费，历史事件不重放（且幂等 guard 也挡得住，双保险）。

## 本节小结
- 冷启动顺序 = 依赖顺序：Redis → Kafka → 后端 ×5 → Nginx；每步有就绪探测，整脚本幂等可重跑。

- nginx 三步曲：生成配置 → `-t` 验证 → 冷启/reload 二选一。
- smoke 22/22 是上线的最后一道闸；本次翻车（Redis 脏状态→已售罄→修复→全绿）证明它值得信任。

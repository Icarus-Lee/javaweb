## 1. 冷启动顺序：为什么是这个顺序

```text
① Redis（6379） → ② Kafka（9092 + controller 9093，KRaft 单节点） → ③ 后端×5（8081-8085） → ④ Nginx（9090）
```

- **Redis 最先**：demo-counter/train/takeaway 启动即读写 Redis 灌种子；
- **Kafka 第二**：producer/consumer 启动即连接（连不上会重试但日志刷屏）；
- **后端互不依赖**：五个 jar 并行都行；起完用 `/dev/tcp` 探测端口就绪；
- **Nginx 最后**：它反代的上游全就绪，一次 reload 直接可用。

就绪判定手法（start-all.sh:45）：`(echo > /dev/tcp/127.0.0.1/$port) 2>/dev/null && break` ——bash 内建 TCP 探测。**端口通 ≠ 应用就绪**（Tomcat 先于 Spring 上下文完全加载），生产建议换 actuator/health（S09）。每段先探测"已在线就跳过"——**start-all 可反复执行**，运维脚本第一美德。

## 2. 进程托管两种姿势

### 2.1 nohup（脚本现状）

```bash
nohup "$JAVA_HOME/bin/java" -jar "$jar" > "$ROOT/logs/$name.log" 2>&1 &
echo $! > "$ROOT/logs/$name.pid"
```

`nohup ... &` 脱离终端；`> log 2>&1` 是排查第一现场；pid 文件供 stop-all 精准杀。短板：**崩了没人拉起**。W02 实录里 `kill $(cat logs/takeaway.pid)` 杀掉的其实只是 nohup 的壳——精准姿势见 W03 §4.2 的 `ss -ltnp` 端口反查。

### 2.2 systemd（infra/javaweb.service）

```ini
[Unit]
Description=javaweb takeaway (Spring Boot 8085)
After=network.target redis.service kafka.service

[Service]
Type=simple
User=icaruslee
WorkingDirectory=/home/icaruslee/Projects/javaweb
Environment=JAVA_HOME=/usr/lib/jvm/java-21-openjdk
ExecStart=/usr/lib/jvm/java-21-openjdk/bin/java -jar backend/takeaway/target/takeaway-1.0.0.jar
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
StandardOutput=append:/home/icaruslee/Projects/javaweb/logs/takeaway-systemd.log

[Install]
WantedBy=multi-user.target
```

| 指令 | 含义 | 为什么是它 |
|---|---|---|
| `After=` | 后于这些单元启动 | 依赖顺序（对应冷启 ①②） |
| `WorkingDirectory=` | 进程工作目录 | **H2 相对路径 `./data/takeaway` 靠它定位**——不设会建到 / 下 |
| `Type=simple` | ExecStart 前台进程即主进程 | java -jar 不自守护 |
| `SuccessExitStatus=143` | 退出码 143 算正常 | 128+SIGTERM(15)，stop 不算失败 |
| `Restart=on-failure` + `RestartSec=5` | 崩溃 5 秒自动拉起 | nohup 做不到 |
| `StandardOutput=append:` | 日志追加到文件 | 等价 nohup 重定向 |

部署三连（系统级需要 sudo；**无 sudo 时可用用户级单元** `systemctl --user`，本站实录 A 即演示环境）：

```bash
sudo cp infra/javaweb.service /etc/systemd/system/javaweb-takeaway.service
sudo systemctl daemon-reload && sudo systemctl enable --now javaweb-takeaway
systemctl status javaweb-takeaway
```

**选型口诀**：开发/演示用 nohup（轻）；常驻用 systemd（自愈、自启、统一日志）。

## 3. Nginx 三步曲

`infra/nginx-reload.sh`：① heredoc 生成 nginx.conf：静态站与反代一目了然——

```nginx
location /takeout-ui/  { alias /.../frontend/takeout-ui/dist/; try_files $uri /takeout-ui/index.html; }
location /apitakeout/  { proxy_pass http://127.0.0.1:8085/api/; }
listen 9090;                                # 且必须 include /etc/nginx/mime.types（ES 模块白屏故名）
```

`try_files $uri /index.html`：Vue SPA 的 history 路由兜底——刷新任何路径都回 index.html 由前端路由接管。② `nginx -t` 先验配置（配置写错不打死在跑服务）；③ 有活 pid → `nginx -s reload` 平滑换配置，否则冷启。前端产物来自 `build.sh` 第二段的 `npm run build`（dist 缺失时脚本会现编一次）。**N02 有一段真实修复实录：忘了 include mime.types 时 JS 按 text/plain 下发、ES 模块拒执行 → 全白屏**——页面全白的排查第一站是 `curl -I <js 路径>` 看 Content-Type。

### 3.1 build.sh 的两段流水（为什么压缩在一条命令里）

```bash
(cd backend && mvn -q -T 4 -DskipTests package)   # 后端：多模块 reactor 一次出 5 个 jar
for ui in train-ui takeout-ui; do ... npm run build; done    # 前端：两个 dist
```

要点：**多模块构建必须在 backend/ 根目录跑**（单模块单独构建会缺兄弟依赖）；`-T 4` 四线程并行；`set -eu` 让前端失败即停——"后端绿前端红"的半成品不能叫 build 完成。缺 jar 的症状与处置见 §5 排查手册（先 `ls backend/*/target/*.jar`，缺就 `bash infra/build.sh`，**信脚本别手拼 mvn 参数**）。

## 4. 工程实录：真机部署事故两连（2026-09-15）

### 4.1 实录 A：JAVA_HOME 路径填错——journal 原文诊断

复制 javaweb.service 为用户级实验单元（~/.config/systemd/user/javaweb-lab.service），**故意把路径填成不存在的 java-17**（本机只有 java-21/java-26）：

```ini
Environment=JAVA_HOME=/usr/lib/jvm/java-17-openjdk
ExecStart=/usr/lib/jvm/java-17-openjdk/bin/java -jar backend/takeaway/target/takeaway-1.0.0.jar
```

启动后 status 与 journal 原文（真实输出）：

```text
$ systemctl --user start javaweb-lab
$ systemctl --user status javaweb-lab --no-pager
● javaweb-lab.service - javaweb takeaway lab (8085)
   Active: failed (Result: exit-code) since Tue 2026-09-15 13:11:48 CST; 13s ago
   Duration: 18ms
   Process: 156513 ExecStart=/usr/lib/jvm/java-17-openjdk/bin/java ... (code=exited, status=203/EXEC)
$ journalctl --user -u javaweb-lab -n 5
... (java)[156513]: javaweb-lab.service: Unable to locate executable
     '/usr/lib/jvm/java-17-openjdk/bin/java': No such file or directory
... (java)[156513]: javaweb-lab.service: Failed at step EXEC spawning ...: No such file or directory
... systemd[926]: javaweb-lab.service: Main process exited, code=exited, status=203/EXEC
... systemd[926]: javaweb-lab.service: Failed with result 'exit-code'.
```

**读法**：`Duration: 18ms` + `status=203/EXEC` 的组合是"**可执行文件本身找不到**"的指纹——进程根本没跑进 JVM，日志（StandardOutput 指向的文件）自然一分不剩，唯一的文字在 journal。修复 diff（单元文件两行路径）：

```diff
-Environment=JAVA_HOME=/usr/lib/jvm/java-17-openjdk
-ExecStart=/usr/lib/jvm/java-17-openjdk/bin/java -jar backend/takeaway/target/takeaway-1.0.0.jar
+Environment=JAVA_HOME=/usr/lib/jvm/java-21-openjdk
+ExecStart=/usr/lib/jvm/java-21-openjdk/bin/java -jar backend/takeaway/target/takeaway-1.0.0.jar
```

`systemctl --user daemon-reload && systemctl --user start javaweb-lab` 后约 3 秒拿到健康回包：

```text
$ systemctl --user status javaweb-lab --no-pager | head -4
Active: active (running) since Tue 2026-09-15 13:12:29 CST
Main PID: 156585 (java)
$ curl -s 127.0.0.1:8085/api/health → {"ok":true,"app":"takeaway"}
```

教训一行版：**systemd 的故障眉批先看 Duration 与 status 数字（203=可执行文件错，1=应用异常退出，124=超时）**，别一上来就翻应用日志。

### 4.2 实录 B：残留实例占领 Kafka 的 controller 端口

Kafka 停机重启时 reported `kafka: DOWN`，日志尾三行堆栈：

```text
org.apache.kafka.common.KafkaException: Socket server failed to bind to 0.0.0.0:9093:
    Address already in use.
Caused by: java.net.BindException: Address already in use
```

9093 是 KRaft 的 **controller 端口**（server.properties:37 `listeners=PLAINTEXT://:9092,CONTROLLER://:9093`），被谁占了？三行定位：

```text
$ ss -ltnp | grep 9093
LISTEN 0 511 0.0.0.0:9093 users:(("nginx",pid=147182,...))
$ cat /proc/147182/cmdline | tr '\0' ' '
nginx: master process nginx -c /tmp/opencode/lab/nginx.conf     ← 一个残留实验实例
$ kill 147182 && bash infra/start-all.sh → kafka: up
```

教训：**占端口的可能是"上一次的实验残留"**——按进程名找是不够的，`ss -ltnp` + `/proc/<pid>/cmdline` 两级定位才敢 kill；这正是零起点-03 "端口-进程- pid 文件"知识链的部署章回放。

### 4.3 大实验：stop → start → smoke（实录）

```text
$ bash infra/stop-all.sh
== 后端 ==   demo-chat 已停 / takeaway 已停    （缺 pid 的静默跳过——幂等）
$ bash infra/start-all.sh
== 1) Redis ==  redis: PONG
== 2) Kafka (KRaft 单节点) ==  kafka: up
== 3) 后端 ×5 ==   demo-todo 已在线（8081）... takeaway: up (8085)
== 4) Nginx ==  nginx: up (9090)
```

"已在线"与"up"之别：前者是跳过（进程还活着，幂等检查生效）；后者是真起的。然后 smoke：

```text
$ bash infra/smoke.sh
== train (8084) ==
  ✓ 车次列表   ✓ 注册   ✓ 登录+JWT
  ✗ 下单(UNPAID) (code=500, want=200) ...
smoke: 14 通过 / 3 失败         ← 首跑翻车（真实，上一轮实验留下的状态）
```

翻车排查：`grep IllegalStateException logs/train.log` → `已售罄`；`redis-cli GET train:trip:1:stock` → 0——**上轮实验把 G1024 的票卖光了**。补满货架（SET train:trip:1:stock 3 等）重跑 → `smoke: 23 通过 / 0 失败` ✅。

**这次翻车是冒烟测试价值的最短证明：冒烟不只是验收工具，更是状态泄漏检测器**——你的实验把 Redis 玩脏，测试当场红给你。

## 5. 常见故障排查手册（含本站新案）

| 症状 | 第一现场 | 快诊命令 |
|---|---|---|
| unit 反复 failed、日志空 | journal | `systemctl status`：duration 与 status 码（203=EXEC 错） |
| 500 全线 | 后端日志 | `tail -50 logs/takeaway.log` |
| 页面 404 | nginx | `nginx -t`；`tail .../nginx/run/logs/error.log` |
| Kafka `kafka: DOWN` | 9092 或 9093 | `ss -ltnp | grep 9093`（占口者） + `tail logs/kafka.log` |
| 派单不生效 | Kafka | `kafka-consumer-groups.sh --describe --group dispatch`（LAG） |
| 登录 401 | JWT | token 过期重登 |
| H2 打不开 | 锁文件 | 停进程后删 `data/*.lock.db` |

### 5.3 Kafka 未格式化（KRaft 存储缺失）

```bash
$ ls data/kafka/kraft/*.properties    # 4.x 是 meta.properties（无 → 没格式化过）
$ UUID=$(python3 -c 'import uuid;print(uuid.uuid4())')
$ tools/kafka/bin/kafka-storage.sh format --standalone --cluster-id "$UUID" \
    --config tools/kafka/config/server.properties
```

**警示实录**（W02 拆过）：4.x 的标记文件已从 `cluster.meta.properties` 更名为 `meta.properties`，旧判断恒真 → 每次重启清洗存储。这件事的修复 diff 已真机落地（W02 §4）。`rm -rf data/kafka/kraft` = topic/offset 全清零重来。

## 6. 思考题

1. `/dev/tcp` 探测为何对 takeaway 可能"假就绪"？写一个更严的探测。
2. `SuccessExitStatus=143` 的 143 哪来的？
3. 两个实例抢 8085 时 systemd 的 `Restart=on-failure` 会发生什么连环反应？用 ExecStartPre 怎么挡？
4. 为何 systemd 失败的 Duration 值是诊断指纹？（对照本站实录 A：18ms）

### 参考答案要点

1：`curl -s 127.0.0.1:8085/api/health` 返回 ok 才算真就绪。2：128+15。3：反复重启刷爆日志；ExecStartPre 里 `ss` 预检或在 start_all 里互斥探测。4：极短 duration + 203 = 环境错（路径/权限）；较长的 duration + 1 = 应用错误（配置/依赖）；不同的指纹指向不同的排查路径。

## 8. 本节小结

- 冷启动顺序 = 依赖顺序：Redis → Kafka → 后端×5 → Nginx；每步有探测，脚本幂等。
- nohup 管"今天的演示"，systemd 管"明年的生产"；203/EXEC + Duration 18ms 是"可执行文件错"的指纹。
- 残留实例占口是部署课的头号日常——`ss -ltnp` + `/proc` 两级定位再杀。
- smoke 23/23 是最后一道闸；翻车（库存被实验卖光→补货→全绿）证明它值得被信任。

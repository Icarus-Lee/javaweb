## 1. 生活类比与动机：千手同伸，票柜只有一个抽屉

想象售票员的**票柜**只有一个抽屉：十只手同时伸进来抽票，"我先看还剩几张 → 再拿走一张"两只动作不能接上——S11 用纯 JDBC 已经实测出"三个人 10 张票卖出了 2 张的错账"。

**火车站的天然疑问**：那我把抽屉做成"**伸手即抽（DECR）**"、并且**同一瞬间只放一个人天花板**（锁），成本谁最低？

train 给出的答案是**两件并用**：

- **DECR 原子扣票**：保证"哪怕 N 个人同时伸手，数字也一张不少地被扣除"。
- **setIfAbsent 锁**：保证"扣票 → 发号 → 落库 → 发事件"这一整段业务**没有并发交错**——锁是业务段的门，DECR 是票柜的原子算术。

**谁是必要谁是冗余？** 若只有扣库存这一件事，**DECR 就够**（demo-counter 的秒杀就是纯 DECR 雏形）。但 train 的下单还有"座位号 + 数据库 + Kafka"三兄弟要贯穿——**把一整段要"多人同罩"的工作装进锁里**，代码就免得满屏"还要不要同步"地思考。**锁是让业务段"可读、可推演"的设计手段，DECR 是让单一数字"分毫不差"的算法保证**。

### key 体系命名走查

```java
String stockKey = "train:trip:" + tripId + ":stock";
String lockKey  = "train:trip:" + tripId + ":lock";
String seqKey   = "train:trip:" + tripId + ":seq";
```

`域:对象:ID:字段` 命名法（R01 立的规矩）在这里的一次完整兑现。注意 `lockKey` 的**兜子有幸是"做一层就锁一层"**：锁 key 里的 tripId 保证"两个车次并行不互堵"——锁的粒度一步到位，别用全局一个"train:lock"把整个系统串行化（吞吐死）。

## 2. BookingService.book() 六步流水线逐行走查（真码全贴）

**文件：`backend/train/src/main/java/com/javaweb/train/service/BookingService.java`（核心段）**

```java
public Booking book(Long userId, Long tripId) {
    String stockKey = "train:trip:" + tripId + ":stock";
    String lockKey  = "train:trip:" + tripId + ":lock";
    String seqKey   = "train:trip:" + tripId + ":seq";

    // 1) 谁先 set 成功谁锁门（10 秒自动解锁，防"人走门忘关"）
    Boolean locked = redis.opsForValue()
            .setIfAbsent(lockKey, "1", Duration.ofSeconds(10));
    if (locked == null || !locked) {
        throw new IllegalStateException("手速太快，请重试（车次处理中）");
    }
    try {
        // 2) 原子扣票：DECR，结果为负即"卖重复了"，必须还回去
        Long stock = redis.opsForValue().decrement(stockKey);
        if (stock == null) {
            throw new IllegalStateException("车次未初始化（stock key 缺失）");
        }
        if (stock < 0) {
            redis.opsForValue().increment(stockKey);
            throw new IllegalStateException("已售罄");
        }
        // 3) 座位号：INCR 序列分配（教学版从 1 号开始）
        Long seat = redis.opsForValue().increment(seqKey);

        TrainTrip trip = trips.findById(tripId)
                .orElseThrow(() -> new IllegalArgumentException("车次不存在"));

        Booking b = new Booking();
        b.orderNo = java.util.UUID.randomUUID().toString();
        b.userId = userId;
        b.tripId = tripId;
        b.seatNo = seat.intValue();
        b.status = "UNPAID";
        b.createdAt = Instant.now();
        b = bookings.save(b);          // 4) 落库（H2）
        // 5) 广播给下游：本课的 Kafka 事件先给"审计台"盖个戳
        producer.orderCreated(b.orderNo, tripId, b.seatNo, trip.priceYuan, "CREATED");
        return b;
    } finally {
        redis.delete(lockKey);         // 6) 归还锁（finally 保证"无论成败都还"）
    }
}
```

### 六步的顺序（每一步为何在那儿）

| 步 | 动作 | 为什么必须此位 |
|---|---|---|
| 1 | **setIfAbsent 抢锁（TTL 10s）** | 锁要保安有**锁外的散兵**拒在门外 —— `locked=false` 时**直接抛**，**不重试**（教学：用户重按一次） |
| 2 | **DECR stock** | 锁内第一个动作就是"扣账"；负数当场发现 |
| 3 | **DECR < 0 → INCR 还票 + 抛** | "**先扣再补**"的完整形态：即使票不足，账也分毫不差 |
| 4 | **INCR seq 发座号** | 锁内保证"座号不重号"——两个请求若不限制，同时 INCR 会各拿不同号，但**1 号只有一人**，这正是**锁的真实目的** |
| 5 | **H2 save → Kafka send** | 落库、广播——这两步在锁内属于"业务段"；**派单不需要锁但动账段内省披巾** |
| 6 | **finally delete lock** | **无论成败**必还锁（H2 抛异常、Kafka 慢都会进 finally） |

### 三个"若不这样"的反事实

1. **若没有 finally delete**：H2 落库抛异常 → 锁 key 永留 Redis → **该车次从此 10 秒报"手速太快"直到 TTL 过期**（幸好有 TTL 兜底，但 10 秒窗口内所有请求全是失败——**两道防线缺一不可**）。
2. **若忽略 `stock < 0` 检查**：`DECR` 走到 -1 也照样返回，出票后库存成负数——**超卖**。`INCR` 还票 = "补偿"，是"先扣后补"的**完整形态**。
3. **若没用 setIfAbsent 而用 SET**：SET 无条件覆盖——大家都"写成功"，锁就名存实亡。`setIfAbsent` = Redis 命令层翻译的 **SET NX EX**（NX = 仅当不存在），**一把没有原子命令就没有锁**的硬道理。

### "人走门关"三防线

| 防线 | 防什么 | 代码源 |
|---|---|---|
| **finally delete** | 业务正常的异常路径（抛异常、超时） | `finally { redis.delete(lockKey); }` |
| **TTL 10s** | 进程被 SIGKILL（finally 来不及跑） | `setIfAbsent(..., Duration.ofSeconds(10))` |
| **锁 key 带 tripId** | 粒度错乱（一堵全堵） | `train:trip:{id}:lock` |

**TTL 与 finally 是拍档**（S11 那句话在此兑现）：单方面都被毙。**finally 是常态路，TTL 是灾备路**——两条都要。

## 3. "两把锁两种后果"：分布锁 vs 原子命令对比表

| 维度 | **DECR 原子命令**（票柜抽屉） | **分布式锁 setIfAbsent**（厕所占坑牌） |
|---|---|---|
| 保护对象 | **一个数字**（余票、计数） | **一段代码路径**（扣票→落库→发事件） |
| 防住什么 | 数字被并发算错（lost update） | 多人同时"看账-改账-落账"交错 |
| 防不住什么 | 业务路径上的交错与重号逻辑 | **本身不护数字**——锁忘了撂 DECR，照样超卖 |
| 失败表现 | 库存变负 / 前写被覆盖 | 段内重号、同人并发重复下单 |
| 复杂度/代价 | 一行命令、零维护 | 写锁、还锁、TTL、重试策略 |
| 本项目选择 | **两并用**：锁住业务段。数字部分名成正果由 DECR 实现；锁是让"段落可读"的**设计手段**。 | |

**一句话总 godz：能靠原子的管原子（数字）、需要"一段只有我一个人"的才上锁（业务段）。不是"锁是银弹"也不是"原子包打天下"。**

### 第 2 步：两个并发 curl 同刻抢票

```bash
curl -s -X POST http://127.0.0.1:8084/api/bookings \

curl -s -X POST http://127.0.0.1:8084/api/bookings \

```

### 实测输出（现场拷贝）

```
--- 并发 curl #1:
{"timestamp":"2026-09-14T10:24:59.174+00:00","status":500,"error":"Internal Server Error","path":"/api/bookings"}
--- 并发 curl #2:
{"id":21,"orderNo":"174faa8e-fbf3-4216-94e9-51a23dec5474","userId":33,"tripId":5,"seatNo":1,"status":"UNPAID","createdAt":"2026-09-14T10:24:59.174861870Z","paidAt":null}
$ redis-cli GET train:trip:5:stock
"0"
$ redis-cli GET train:trip:5:seq
"1"
```

### 读解

1. **一成一败**：#2 拿到 `seatNo:1` 的 `UNPAID` 订单；#1 收到 HTTP 500。**余票 0、序列号 1** —— 只剩下一张票里的一张犯错都分毫不差。
2. **500 的真实原因**（别看默认 JSON 体没说人话，**看 train.log**）:

```
java.lang.IllegalStateException: 手速太快，请重试（车次处理中）
```

第二个并发请求在**step 1**就被锁拒——`setIfAbsent` 返回 false 时抛的正是"手速太快"。**它连 DECR 都没走到**，更不会超卖。

3. **HTTP 500 与友好错的教务呼应**：本项目 S07 的 GlobalExceptionHandler 把运行时异常包装成 JSON 500。教学版把锁冲突与售罄**都走 500**（前者 message 与日志有，响应体没细化到"业务语义码"）——生产该配"业务码 + HTTP 200 骨架"或 409。**留这个差距的是教学聚焦**，不是本设计有多优秀。

4. **若你在另一个时刻同时抢**：胜负的可能换人（谁抢到锁值的毫秒）、**但从不会两张都成**——这正是我们想看到的**证言**：不必依赖"谁快 3ms"，**结构保证了后果**。

### 补充实战：把票卖光的后续（cancel 的 INCR 还仓）

顺手迈一步做**cancel 对照**（真实输出）：

```
$ curl -s -X POST http://127.0.0.1:8084/api/bookings/cancel \
    -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
    -d '{"orderNo":"174faa8e-fbf3-4216-94e9-51a23dec5474"}'
{"id":21,...,"status":"CANCELLED",...}
```

## 7. 参考答案

**练习 1**（现象确认）：并发触发下 train.log 里 `lock acquired` **只出现一次**——第二个请求连锁都没抢到（500 在 step 1 抛出），说明锁互斥生效。若没有锁、只在两处 put log，两行都会打——这就是**锁给也是一种观测证据**的作用。

**练习 2**（实测记录）：

```
注释 `stock < 0` 检查 后并发 3 curl：
$ redis-cli GET train:trip:5:stock
"-2"                       ← 超卖 2 张（票已 1 张、3 人抢）
...
（恢复代码后）
$ redis-cli SET train:trip:5:stock 4
```

负库存 = **超卖**的字面答案。DECR + 补偿 INCR 是**一行就防住**的——这正是 `stock < 0` 检查存在的意义。

**练习 3**（选型口径）：

- 全站锁更安全**不错**——但"两个车次毫无因果的订单"被强制串行，**吞吐几近被掐**（若 trip5 的处理要 200ms，其余车次的吞吐瞬时被腰斩到 5 QPS）。
- **粒度处以"业务因果" 为尺**：动的是哪份数据，就锁哪个维度（车次 → 车次级；全站唯一的资源 → 全站级）。

## 8. 本节小结

- train 下单 = **锁（业务门） + DECR（票柜原子） + finally/TTL（关人两道防线）**。
- **两把锁两种后果**：DECR 防数字错，锁防业务段乱——二者职责不同，互不替代。
- 六步顺序不可换：**锁→扣→补→号→库→事件→还锁**，一行也不是"装饰"，而是**每一步都防一种事故**。
- **实测证词**：两张并发 curl，一成 `seatNo:1`、一败 step-1 锁冲突；`stock` 分毫不差归 0、`seq` 才能 1。**数字不超扣**——今天"预防超卖"铁证如山。

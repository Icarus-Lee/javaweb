> **产出**：能白板画出三张表与外键关系；能说清"复用一个实体"的收益与代价；能默写外卖状态机的全部合法流转（含异常分支）。

## 1. 生活类比与动机：先有菜单，再有订单

### 需求清单（本模块只做这些）

1. **注册/登录**：顾客和骑手都用账号登录（JWT，见 S13）。
2. **看菜单**：按店（shopId）列菜品；菜单要快（Redis 缓存，W05 细讲）。
3. **点单→支付→派单→送达**：订单四步主流程，每步状态可查。
4. **取消/退款**：异常分支——付钱之前能反悔（CANCELED），付了钱之后出错要退（REFUNDED）。
5. **库存**：今日限售，卖完即止（Redis 扣减，W02/W04 出场）。

**不做**的（教学裁剪，说清楚比做出来更重要）：多菜品购物车（一单一菜）、真实支付网关、骑手实时定位、店铺注册（店铺是种子数据写死的 shopId 1/2/3）。

### 为什么表结构要先于代码

表结构是系统的**骨架**：Controller、Service 全是围绕它长出来的肉。三张表定了，W02 的链路、W04 的状态机都只是"在这骨架上跑流程"。

## 2. 三张表逐格走查（真实文件）

### 2.1 users —— 谁在点？（`backend/takeaway/src/main/java/com/javaweb/takeaway/model/User.java`）

```java
@Entity(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long id;

    @Column(unique = true, nullable = false, length = 64)
    public String username;

    @Column(nullable = false, length = 128)
    public String passwordHash;     // 注意：存的是哈希，不是明文（X02 细讲）

    /** USER=顾客 / RIDER=骑手（双角色一个模型，教学简化） */
    public String role;
}
```

三个字段，一眼看完。两个设计点：

- **`passwordHash`**：永远不存明文。本项目用 `sha256("takeaway-" + 密码)` 加了固定前缀（AuthController.java:38），X02 会对比 BCrypt 的工业做法。
- **`role` 只有 USER/RIDER 两个值**：没有 ADMIN——本模块用不上，不预留。

### 2.2 dishes —— 卖什么？（`model/Dish.java`）

```java
@Entity(name = "dishes")
public class Dish {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long id;

    public Long shopId;         // 哪家店
    @Column(length = 64, nullable = false)
    public String name;
    public int priceYuan;       // 整数元（A10 讲过：浮点数不能存钱）
    public int stock;           // 今日限售（教学：外卖菜也可能卖完）
}
```

注意 `shopId` 是个**裸 Long**——没有 `Shop` 实体。这是刻意裁剪：店铺在本项目只是个分组号（1=汉堡店、2=奶茶店、3=特产店），建表反而增加认知负担。**priceYuan 用 int**，复习 A10 的结论：金额要么整数分、要么 BigDecimal，绝不 double。

### 2.3 orders —— 单到哪一步了？（`model/Order.java`）

```java
@Entity(name = "orders")
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long id;

    @Column(nullable = false, length = 36)
    public String orderNo;      // 对外暴露的订单号（UUID），id 不外露

    public Long userId;         // 顾客
    public Long shopId;
    public Long dishId;
    public int quantity;
    public int totalYuan;

    /** CREATED(已下单) -> PAID(已支付) -> DISPATCHED(已派单) -> DELIVERED(已送达)；
        CANCELED/REFUNDED 为异常分支 */
    public String status;
    public Long riderId;

    public Instant createdAt;
    public Instant paidAt;
    public Instant dispatchedAt;
    public Instant deliveredAt;
}
```

逐个说：

- **`orderNo` 与 `id` 双主键设计**：`id` 是数据库自增的内部号；`orderNo` 是 UUID，对外接口（URL、消息队列里）只出现 `orderNo`。为什么不直接用 id？① 自增 id 会泄露"你是第几单"（业务量情报）；② UUID 天然可以由应用生成，跨服务引用不冲突。
- **四个时间戳**：`createdAt/paidAt/dispatchedAt/deliveredAt` 与四个主状态一一对应。进入哪个状态，就盖哪个时间的章——事后能精确还原"这一单慢在哪一步"。
- **`status` 是 String 不是枚举**：JPA 存枚举要么 `@Enumerated(EnumType.STRING)` 要么存序号（危险）。本项目直接用 String + 白名单校验（W04），简单且数据库里可读。

### 2.4 关系图（逻辑外键）

```
users (id) ──< orders.userId
dishes(id) ──< orders.dishId
dishes.shopId ──> （没有 shops 表，裸数字分组）
orders.riderId ──> users(id) 中 role=RIDER 的那批人（派单后回填）
```

注意全是**逻辑外键**：Java 字段关联，数据库层不建 FK 约束。教学取舍：H2 文件库 + `ddl-auto: update` 下，物理外键会让演示数据清理变麻烦；生产系统则应该建。

## 3. 设计取舍①：顾客和骑手为什么共用一张 users 表？

### 现状

`AuthController.register`（AuthController.java:35）：

```java
String role = "RIDER".equalsIgnoreCase(req.role()) ? "RIDER" : "USER";
```

注册时传 `role: "RIDER"` 就造出骑手账号。种子数据（SeedRunner.java:26-31）预置了 `alice`（USER）与 `rider9`（RIDER），密码都是 123456。

### 为什么这样设计（收益）

1. **登录逻辑只有一份**：`/auth/login` 不用区分"顾客登录"和"骑手登录"两个端点——验完密码，把 role 塞进 JWT claim（JwtUtil.java:29 `claim("role", role)`）就完事。
2. **拦截器只验一次**：`AuthInterceptor` 把 uid 和 role 挂到请求属性上（AuthInterceptor.java:22-23），Controller 里需要角色的地方自己再判（OrderController.java:64 `if (!"RIDER".equals(...))`）。
3. **现实中也有原型**：很多平台"骑手可以切换成顾客点单"（同一个手机号），账号本就是一个人。

### 代价（什么时候该拆表）

| 信号 | 应对 |
|---|---|
| 骑手需要特有字段：身份证、电动车牌照、接单区域 | 拆出 `rider_profile` 表，userId 关联 |
| 两类用户的登录方式不同（骑手用工牌号） | 拆表或拆登录端点 |
| 角色数量膨胀（商家、平台管理员、客服…） | 上 roles + user_roles 中间表（RBAC） |

**判断口诀**：字段重合度高、登录方式相同 → 一张表 + role；字段分化、权限模型复杂 → 拆。本项目是前者的教科书场景。

## 4. 设计取舍②：状态机的异常分支

### 主流程（快乐路径）

```
CREATED ──支付──> PAID ──Kafka 派单──> DISPATCHED ──骑手送达──> DELIVERED
```

### 异常分支为什么必须一开始就画进图里

新手画状态机只画快乐路径，结果"取消"功能上线时发现：**从哪些状态能取消？取消后库存退不退？Kafka 事件发不发？**——全没想过。正确的做法是把异常分支当一等公民：

```
CREATED ──用户取消──> CANCELED            （没花钱，直接撕单）
PAID    ──用户取消──> CANCELED            （已扣 Redis 库存：真退款场景的雏形）
CREATED ──超时未付──> CANCELED            （W06 的定时关单）
PAID    ──退款──> REFUNDED                （W06 引导你自己实现）
```

本项目已实现的合法流转白名单（OrderService.java:20-21）：

```java
private static final Set<String> LEGAL_NEXT = Set.of(
        "CREATED-PAID", "PAID-DISPATCHED", "DISPATCHED-DELIVERED",
        "CREATED-CANCELED", "PAID-CANCELED");
```

`REFUNDED` **故意没放进白名单**——它是 W06 的动手作业。你现在只需要知道：退款路径 = `PAID → CANCELED`（回库存）之后，如果钱实际已退给用户，订单终态应标 `REFUNDED` 而不是 `CANCELED`。

### 状态与库存的联动（提前埋个伏笔）

- 进入 `PAID`：Redis `DECR` 扣库存（OrderService.java:74），扣到负数要回滚（`INCR` 加回去再抛异常，74-78 行）。
- 进入 `CANCELED`：本项目**没有**自动回库存——这是教学简化还是 bug？留给 W06 思考题（提示：对比 train 的 `cancel()` 会 `INCR` 回余票，BookingService.java:100）。

## 7. 练习（H/F/M 三层）

- **H（热身）**：用注册接口造一个骑手账号 `rider_me`，登录拿 token，解码 payload 确认 `role=RIDER`。
  验收：token 三段里能看到 `"role":"RIDER"`。
- **F（进阶）**：给 `Order` 加一个 `cancelReason` 字段（String），取消接口多收一个可选参数。
  提示：`ddl-auto: update` 会自动加列；改 `OrderController.cancel` 的签名。
  验收：取消一单后 `GET /orders/{orderNo}` 能看到 `cancelReason`。
- **M（硬核）**：把 `users.role` 改造成枚举 `Role { USER, RIDER }` + `@Enumerated(EnumType.STRING)`，全模块编译通过且 smoke 不红。
  提示：改动点在 User 实体、AuthController、OrderController 的三处字符串比较；SeedRunner 也要改。
  验收：`bash infra/smoke.sh` 仍 23/23。

### 参考答案要点

- 思考 1：恶意用户传 `{"shopId":999,"dishId":1}` 会造成订单的店号和菜号对不上（对账错乱）。服务端从 `dish.shopId` 回填是"数据只有一个出处"原则。
- 思考 2：加 `order_items` 表（orderId, dishId, quantity, priceSnapshot）；`Order.totalYuan` 保留为汇总；`dishId/quantity` 从 Order 删掉。`priceSnapshot` 很关键——菜改价不能影响历史订单。
- 思考 3：好处是数据库直接可读、加新角色不改代码结构；坏处是失去编译期检查，拼写错误（"RIDER "带空格）只会在运行时炸。
- 思考 4：train 回票是"库存 = 余票"的强对账语义；takeaway 的 dish:1 库存被扣到 1 后取消并不回补——顾客白丢了一次购买机会。更公平的做法是 CANCELED 时 INCR 回去（这正是 W06 练习的一部分）。

## 本节小结
- 三张表：users（谁）、dishes（卖什么）、orders（到哪步）；金额全用 int，对外只露 orderNo。
- role 复用一个 JPA：登录/拦截器逻辑单份；字段分化时再拆表。
- 状态机异常分支（CANCELED/REFUNDED）与主流程同设计；REFUNDED 是 W06 的作业。
- 库存真相在 Redis（`takeaway:dish:{id}:stock`），H2 只是初始快照。

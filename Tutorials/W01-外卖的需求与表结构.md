## 2. 三张表逐格走查（真实文件）

### 2.1 users —— 谁在点？（`model/User.java`）

```java
@Entity(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long id;
    @Column(unique = true, nullable = false, length = 64)
    public String username;
    @Column(nullable = false, length = 128)
    public String passwordHash;     // 存的是哈希，不是明文（X02 细讲）
    /** USER=顾客 / RIDER=骑手（双角色一个模型，教学简化） */
    public String role;
}
```

两个字段值得停：`passwordHash` 永不存明文（本模块用 `sha256("takeaway-" + 密码)`，X02 会对比 BCrypt）；`role` 只有 USER/RIDER 两个值，没有 ADMIN——本模块用不上就不预留。

### 2.2 dishes —— 卖什么？（`model/Dish.java`）

```java
@Entity(name = "dishes")
public class Dish {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long id;
    public Long shopId;         // 哪家店（裸 Long，没有 Shop 实体）
    @Column(length = 64, nullable = false)
    public String name;
    public int priceYuan;       // 整数元（A10：浮点数不能存钱）
    public int stock;           // 今日限售
}
```

`shopId` 是刻意裁剪：店铺只是分组号（1=汉堡店、2=奶茶店、3=特产店），建表徒增认知负担。

### 2.3 orders —— 单到哪一步了？（`model/Order.java`）

```java
@Entity(name = "orders")
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    public Long id;
    @Column(nullable = false, length = 36)
    public String orderNo;      // 对外暴露的订单号（UUID），id 不外露
    public Long userId;         // 顾客
    public Long shopId;
    public Long dishId;
    public int quantity;
    public int totalYuan;
    /** CREATED -> PAID -> DISPATCHED -> DELIVERED；CANCELED/REFUNDED 为异常分支 */
    public String status;
    public Long riderId;
    public Instant createdAt;
    public Instant paidAt;
    public Instant dispatchedAt;
    public Instant deliveredAt;
}
```

- **`orderNo` 与 `id` 双主键**：id 是数据库自增内部号；orderNo 是 UUID，对外接口与消息队列只出现 orderNo。理由：① 自增 id 会泄露"你是第几单"（业务量被竞对爬取是真实情报事故）；② UUID 天然可由应用生成，跨服务引用不冲突。前端显示用 `orderNo.slice(0,8)` 短码，id 从不外露。
- **四个时间戳与四个主状态一一对应**：进入哪个状态就盖哪个时间的章——`createdAt/paidAt/dispatchedAt/deliveredAt` 事后能精确还原"这一单慢在哪一步"。可观测性在表结构阶段就决定了，不是事后补字段能换来的。
- **status 用 String 不用枚举**：JPA 存枚举要么 `@Enumerated(EnumType.STRING)`，要么默认存序号（危险：调换枚举常量顺序即错账）。String + 白名单校验（W04）朴素、数据库直接可读；代价是编译期拼写检查缺失（"CANCLED"），运行时由白名单拒绝兜底——W04 ~W06 会看到这个兜底工作的实景。

### 2.4 关系图（逻辑外键）

```
users (id) ──< orders.userId
dishes(id) ──< orders.dishId
orders.riderId ──> users(id) 中 role=RIDER 的那批人（派单后回填）
```

全是**逻辑外键**：Java 字段关联，数据库层不建 FK。取舍：教学项目 H2 + `ddl-auto: update` 下，物理外键让演示数据清理变麻烦（先删谁？顺序陷阱）；生产系统应该建——数据库帮你拦住"订单指向不存在的菜"这种脏数据，是应用层漏判时的最后防线。物理外键缺失时，脏数据防线全压在 Service 校验上——W01 实录 C 的键名 typo 正是"没有任何防线拦 typo"的家族事故。

### 2.5 为什么 IDENTITY 策略下 Java 侧永远别 set id

种子数据（SeedRunner.java:25）守卫是 `if (users...isPresent() && dishes.count() > 0) return;`。这里埋过本项目真实发生过的第一个 JPA 坑：**IDENTITY 策略下，如果 new 的时候手动 `dish.id = 1` 再 save，Hibernate 会走 merge 序列（先 SELECT 再 UPDATE）**，行为从"插入"漂移成"覆盖"，种子用户的 id 与预期错位后，拦截器解出的 uid 就与订单归属对不上（S11 的越权校验会误伤）。结论一句：**主键策略选定后，Java 侧永远别碰 id**——数据库发号，应用闭嘴。SeedRunner.java:41 的注释"（id 让数据库自增生成，IDENTITY 策略下更稳）"就是这次踩坑后的安全带。

## 3. 设计取舍：为何共用 users 表 / 异常分支要画进图里

### 3.1 role 复用一个 JPA

`AuthController.java:35` 一行决策：

```java
String role = "RIDER".equalsIgnoreCase(req.role()) ? "RIDER" : "USER";
```

收益：**登录逻辑只有一份**（验完密码把 role 塞进 JWT claim，JwtUtil.java:29）、**拦截器只验一次**（AuthInterceptor.java:22-23 把 uid/role 挂到请求属性，需要的地方自己再判，OrderController.java:64）。

| 信号 | 应对 |
|---|---|
| 骑手需要特有字段（身份证、牌照、接单区域） | 拆 `rider_profile` 表 |
| 登录方式不同（骑手用工牌号） | 拆表或拆登录端点 |
| 角色膨胀（商家/管理员/客服） | roles + user_roles 中间表（RBAC） |

**口诀**：字段重合度高、登录方式相同 → 一张表 + role；字段分化、权限模型复杂 → 拆。

### 3.2 异常分支为什么必须一开始就画进图里

```
CREATED ──用户取消──> CANCELED            （没花钱，直接撕单）
PAID    ──用户取消──> CANCELED            （已扣 Redis 库存）
CREATED ──超时未付──> CANCELED            （W06 的定时关单）
PAID    ──退款──> REFUNDED                （W06 引导你自己实现）
```

本项目已实现的合法流转白名单（OrderService.java:20-21）：

```java
private static final Set<String> LEGAL_NEXT = Set.of(
        "CREATED-PAID", "PAID-DISPATCHED", "DISPATCHED-DELIVERED",
        "CREATED-CANCELED", "PAID-CANCELED");
```

**REFUNDED 故意缺席**——它是 W06 的动手作业。状态与库存的联动伏笔：进入 PAID 扣库存（OrderService.java:74），扣到负数回滚（INCR 加回去再抛异常）；进入 CANCELED 则**没有**自动回库存——这是 bug 还是简化？留给 W06（对照 train 的 `cancel()` 会 INCR 回余票，BookingService.java:98）。

## 4. 工程实录：真实问题与解决（2026-09-15 真机实测）

三个在生产 里都会真实发生的问题，按"复现 → 排查 → 修复 → 复验"走一遍。

### 实录 A：非法 JSON body——400 与 500 的分界线

```text
$ curl -s -i -X POST 127.0.0.1:8085/api/orders -H "Authorization: Bearer $TOK" \
    -H 'Content-Type: application/json' -d '{"dishId":1, quanity:1'
HTTP/1.1 400
{"timestamp":"2026-09-15T05:10:35.702+00:00","status":400,"error":"Bad Request",
 "path":"/api/orders"}

$ curl -s -X POST 127.0.0.1:8085/api/orders -H "Authorization: Bearer $TOK" \
    -H 'Content-Type: application/json' -d '{"dishId":1,"quantity":0}'
{"status":500,"error":"Internal Server Error","path":"/api/orders"}
$ grep "至少点" logs/takeaway.log | tail -1
java.lang.IllegalArgumentException: 至少点 1 份
```

**排查路径**：同样是"客户端的错"，缺右括号落下 400（Spring 把 `HttpMessageNotReadableException` 映射好了），`quantity=0` 却炸成 500——因为 `OrderService.java:49` 抛的是没被映射的 `IllegalArgumentException`，S07 的讲法即时回收。**副作：类型错挡在门口（400），值不合意爆在业务层（现状 500，语义上应是 400/422——W04 练习 M 改造点）**。

### 实录 B：状态机流转错序实测——"错序"会被当场拒绝

对已取消订单调支付（操作顺序错了）：

```text
$ curl -s -i -X POST "127.0.0.1:8085/api/orders/$ON/pay" -H "Authorization: Bearer $TOK" | sed -n '1p;$p'
HTTP/1.1 500
{"status":500,"error":"Internal Server Error","path":"/api/orders/xxx/pay"}
$ grep "非法状态流转" logs/takeaway.log | tail -1
java.lang.IllegalStateException: 非法状态流转: CANCELED -> PAID
```

白名单（OrderService.java:40-41）在 `transition()` 里把这条边当场掐死，报错文本即接口文档。整套越轨组合的实测矩阵在 W04 §4（用教学实验端点把 6 个目标状态实测了一遍，`CANCELED -> REFUNDED` 一律拒绝）。

### 实录 C：库存键名 typo——第 2 号菜"永远库存不足"（本章招牌事故）

**事故**：某次改动把扣减 key 写成了 `:stokc`（少一个 c 的方向敲错了）。用户报告："招牌奶茶能下单不能支付"。菜单上看着有库存，支付永远"库存不足"。

**第一步：复现**（把 `OrderService.java:74` 的 `":stock"` 改成 `":stokc"`，`mvn -q -T 4 -DskipTests package` 重新打包，重启 8085）：

```text
$ redis-cli -p 6379 MGET takeaway:dish:2:stock takeaway:dish:2:stokc
4
(nil)                                        ← 真键活着，typo 键不存在

$ O=$(curl ... -d '{"dishId":2,...}') && curl -X POST ".../pay"
{"status":500,"error":"Internal Server Error"}          ← 支付失败！

$ redis-cli -p 6379 MGET takeaway:dish:2:stock takeaway:dish:2:stokc
4
0                                            ← 真键没扣，typo 键被造了出来
```

**第二步：推理**。DECR 一个不存在的 key：Redis 把 nil 当 0 减成 -1；`left < 0` 触发回滚 INCR 到 0 并抛"库存不足"（OrderService.java:75-77）。于是 typo 键永远 ≈ 0，**真键永远不被扣**——数据在两个平行宇宙里。菜单接口读 H2（stock=8）更添乱：三个"库存"三个数。

**第三步：修复 diff（一行）**：

```diff
-        Long left = redis.opsForValue().decrement("takeaway:dish:" + o.dishId + ":stokc");
+        Long left = redis.opsForValue().decrement("takeaway:dish:" + o.dishId + ":stock");
```

**第四步：复验**（重新打包重启后）：

```text
$ redis-cli -p 6379 GET takeaway:dish:2:stock → 4
$ 支付一单击中第 2 号菜 → status=PAID
$ redis-cli -p 6379 GET takeaway:dish:2:stock → 3（4→3，扣对了）
$ redis-cli -p 6379 DEL takeaway:dish:2:stokc   # 清掉事故残留键
```

**复盘三问**：①谁想要的？没人——这是事故不是"知识内 500"；②定位靠什么？`redis-cli KEYS 'takeaway:*'`（键清单即真相）+ `MGET` 双键对照；③教训：**Redis 键名没有任何编译期/类型检查，键名 typo 是静默事故**。防御姿态：键名常量集中定义 + 冒烟测试断言"支付后库存 -1"（smoke 已有，这次事故它就能红）。

## 8. 练习（H/F/M 三层）

- **H（热身）**：用注册接口造一个骑手账号 `rider_me`，登录拿 token，解码 payload 确认 `role=RIDER`。
  验收：token 三段里能看到 `"role":"RIDER"`。
- **F（进阶）**：给 `Order` 加 `cancelReason`（String）字段，取消接口多收一个可选参数。
  提示：`ddl-auto: update` 自动加列；改 `OrderController.cancel` 签名。
  验收：取消一单后 `GET /orders/{orderNo}` 能看到 `cancelReason`。
- **M（硬核）**：把 `users.role` 改造成枚举 `Role { USER, RIDER }` + `@Enumerated(EnumType.STRING)`，全模块编译通过且 smoke 不红。
  提示：改动点在 User 实体、AuthController、OrderController 三处字符串比较；SeedRunner 也要改。
  验收：`bash infra/smoke.sh` 仍 23/23。

### 参考答案要点

- 思考 1：恶意用户传 `{"shopId":999,"dishId":1}` 会造成订单店号与菜号对不上（对账错乱）。服务端从 `dish.shopId` 回填是"数据只有一个出处"原则。
- 思考 2：加 `order_items` 表（orderId, dishId, quantity, priceSnapshot）；`totalYuan` 保留为汇总；dishId/quantity 从 Order 删掉。价格快照很关键——菜改价不能影响历史订单。
- 思考 3：好处是数据库直接可读、加新角色不改结构；坏处是失去编译期检查，拼写错误（"RIDER "带空格）只能运行时炸。
- 思考 4：train 回票是"库存=余票"的强对账语义；takeaway 取消不回补，顾客白丢一次购买机会。公平做法是 CANCELED 时 INCR——这正是 W06 练习的一部分。

## 9. 本节小结

- 三张表：users（谁）、dishes（卖什么）、orders（到哪步）；金额全用 int，对外只露 orderNo。
- role 复用一个 JPA：登录/拦截器单份；字段分化时再拆表。
- 状态机异常分支（CANCELED/REFUNDED）与主流程同设计；REFUNDED 是 W06 作业。
- 实录 A/B：400 与 500 的分界、状态机默认拒绝；实录 C：键名 typo 是静默事故，修复前后靠 diff 与 MGET 双键对照。
- 库存真相在 Redis 真键（`takeaway:dish:{id}:stock`），H2 只是初始快照。

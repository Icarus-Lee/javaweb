> **产出**：能用点外卖比喻讲清生产者/消费者/队列；能对 topic、partition、offset 三件套各说一句人话；能现场用 `kafka-console-consumer` 收到一条真事件。

## 1. 生活类比与动机：服务员不该在厨房门口罚站

回忆一次真实点外卖：你在 App 按下"下单"，**平台立刻返回"订单已收，单号给你的了"**——此时厨师还没开火、骑手还没上岗。**平台没有等你吃完才返回**，它把"有新单了"这个**事实**交给后面的工序，自己转身去接下一单。

把这套拆开看：

1. **下单那一刻**：平台（生产者）做的是"记录事实"——把一张单子写进**接单台**（队列）。
2. **随后的每道工序**：厨房（消费者 A，按单开火）、骑手调度（消费者 B，按单派工）、财务（消费者 C，按单记账）——**每家都以自己的节奏从接单台取单，互不等待、互不牵连**。
3. **返回给用户的**：单号行李。**用户拿单号就能查进度**，没有人按下"再等等"。

**反例（同步型）**：如果下单接口必须"通知厨房 → 等厨房确认 → 通知骑手 → 等骑手接单 → 写财务流水"全跑完才返回，那么任何一个下游抖一下，用户的"下单"按钮就转圈到天荒地老。**这是同步 API 在多下游系统里的结构性死穴**——不是代码写得不好，是**等待面的宽度由下游数量决定**。

Kafka 在这种格局里的价值，就浓缩为三连。

## 2. 解耦 / 削峰 / 异步三连（各配本项目实例）

### 三连一：解耦（Das couple）

**没有 MQ**：下单接口直接调用审计（写 AuditLog 表）、直接喊派单、直接刷报表——**每多一个下游，接口就多一个依赖、多一个会拖垮它的故障点**。下游改代码、重启、修数据，接口陪着一起抖。
**引入 MQ**：下单只写一条事件进 `takeout-order-events`。**下游想谁听就谁听**：现在有 dispatch（派单），将来加"短信服务"就再写一个消费者——**生产者一行不改**。这就是解耦的字面意义：**生产者与消费者之间只认识"频道名"，不认识"人"**。

### 三连二：削峰（吸收洪峰）

**峰值场景**：平时 10 QPS、开播瞬间 500 QPS。若接口同步地把 500 QPS 全部砸给派单与报表，机器要按**峰值**配——平时 98% 的算力闲得发慌。
**引入 MQ**：接口把 500 QPS 的量**写进队列**（写队列是毫秒级轻活）就返回；下游**按自己能消化的速度拉事件**。洪峰被队列"装进水壶"，下游拧龙头慢慢喝——**机器按平均负载配置，不再按峰值**。

### 三连三：异步（用户各拿各的行李）

**用户真正需要的**：一个单号，以及"已在处理"的确认。**他不需要**等骑手接单才离开手机。
**引入 MQ**：接口写完事件就返回 `orderNo`；派单、结算、通知在后台慢慢来。**下单接口的响应时间，从此不再由最慢的下游决定。**

### 三连小结

| 诉求 | MQ 的解法 | 本项目落点 |
|---|---|---|
| 下游互相不牵连 | 解耦：只认频道名、不认人 | `takeout-order-events` 一条频道多家听 |
| 峰值不砸垮下游 | 削峰：队列装洪峰、下游自节奏 | dispatch 按消费速度取事件 |
| 用户拿单号即走 | 异步：写完即返、后台来 | 下单毫秒返回 orderNo |

**反提一句诚实边界**：MQ 不是免费的。它引入了"事件会不会丢 / 会不会重复 / 会不会乱序"三道新问题——分别由 K05（投递语义与幂等）与 K06（顺序保序）接招。**队列是把问题从"阻塞用户"搬进"由架构兜底"，不是消灭问题。**

## 3. Kafka 三件套在两个真 topic 里的显影

### topic：频道名

本项目两个业务频道（物联网口吻：每套业务自建一个）：

```
train-order-events      ← train 的订单事件（审计台听）
takeout-order-events    ← takeaway 的外卖事件（派单员听）
```

现状实测（topics 列表）：

```
$ env KAFKA_HEAP_OPTS="-Xmx64M" tools/kafka/bin/kafka-topics.sh \
      --bootstrap-server 127.0.0.1:9092 --list 2>/dev/null

__consumer_offsets
takeout-order-events
train-order-events
```

（`__consumer_offsets` 是 Kafka 的**自账**——各组消费进度记在这里，K02/K04 再展开。）

### partition：多条巷

同一 topic 可以切成多条 partition（数据分片 + 并行消费的单位）。**巷内绝对有序，巷与巷之间无序**——这是一条会贯穿 K06 的铁律。本项目教学版每 topic 单巷（partition 0）起步。

### offset：巷内序号

每条日志在所属 partition 里的一个**递增序号**，从 0 开始。消费者组把自己的"读到哪儿了"（提交位移）记在 Kafka 手里——**重启不重读、接着吃**。这就是消费进度"账本可续"的根基。

## 7. 动手验证：消费 takeout-order-events 一条真事件

真实命令与真实输出（服务全在线时跑了收货）：

```
$ timeout 8 env KAFKA_HEAP_OPTS="-Xmx128M" tools/kafka/bin/kafka-console-consumer.sh \
    --bootstrap-server 127.0.0.1:9092 \
    --topic takeout-order-events \
    --from-beginning --max-messages 2 2>/dev/null

{"orderNo":"1b5bdcd2-be8a-4752-8b6f-735339b53d03","dishId":1,"qty":1,"phase":"CREATED"}
{"orderNo":"5bfbe98e-96e8-4ea6-8e9c-27bb9a919d4e","dishId":1,"qty":1,"phase":"CREATED"}
```

参数逐个说明：

- `--topic takeout-order-events`：只听外卖这一条频道。
- `--from-beginning`：从 offset 0 开始读（不指定时，有提交位移的组从上次位置接着读）。
- `--max-messages 2`：读满两条收工，不围观到底。
- `2>/dev/null`：把 console 工具的启动/超时日志晾到一边，只留事件本体。

**事件解剖**：一条事件就是一个 JSON 字符串——`orderNo`（业务身份，也作为消息 key）、`dishId` 哪道菜、`qty` 数量、`phase` 生命周期阶段（CREATED / PAID …）。生产者株式会社手工拼出（K03 走查），消费者按字段抽读（K04 走查）——**字段名是双方暗合的合同**。

**走一遍完整链路**（复盘 R05 前流程）：takeaway 下单 → 写 `CREATED` 事件 → 用户支付 → 写 `PAID` 事件 → DispatchConsumer 消费 PAID → H2 状态 `DISPATCHED`。K04 会有全站对账表，本章把这只"读筒"交到手上即可。

## 5. 实战一单：异步链路的完整走位（真实实录）

K01 的理论要有一单真实证据。takeaway 的一整单（一个 orderNo、两段事件、一次异步派单）实录如下：

```
$ TOK=$(curl -s -X POST http://127.0.0.1:8085/api/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"username":"alice","password":"123456"}' \
    | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')

$ curl -s -X POST http://127.0.0.1:8085/api/orders \
    -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
    -d '{"shopId":1,"dishId":1,"quantity":1}'
{"id":32,"orderNo":"2477c7fa-13fe-4103-b0b7-3ab1382a7aa0","totalYuan":22,"status":"CREATED","riderId":null,...}

$ curl -s -X POST "http://127.0.0.1:8085/api/orders/2477c7fa-.../pay" -H "Authorization: Bearer $TOK"
{"id":32,"status":"PAID","riderId":null,...}          ← 支付接口立刻返回（不等派单）

$ sleep 3      # Kafka 异步派单窗口
$ curl -s "http://127.0.0.1:8085/api/orders/2477c7fa-..." -H "Authorization: Bearer $TOK"
{"id":32,"status":"DISPATCHED","riderId":9000,"dispatchedAt":"2026-09-14T10:25:48.830Z",...}
```

四条读证：

1. **接口各回各的**：下单返回 CREATED、支付返回 PAID——**都没有等派单**；三秒后查单才见 DISPATCHED。
2. **派单是消费侧的功劳**：status 变化发生在 DispatchConsumer 消费 PAID 事件之后——**请求线程与消费线程分家**（rebalance 日志里 `ntainer#0-0-C-1` 线程名可佐证）。
3. **riderId=9000 是"模拟调度"**：教学版一次性指派（takeaway 注释原话），真实骑手调度是另一套业务——这单的**事件驱动**骨架完全成立。
4. **对照同步死法的玩笑**：若支付接口要等"派单完成"才返回，这单至少多三秒——异步的价值在"等待面"的瘦身。

## 6. MQ 的使用边界（短记三条）

1. **业务事实存 DB、消息只是通知**：`orderNo + status` 在 H2 里是真相；Kafka 事件是"这个真相变了"的**广播**。不要试图把 Kafka 当数据库查。
2. **同步请求不进 MQ**：用户"下单按一下返回单号"当然可以异步；但"登录发 token" 必须**同步**——**越靠用户眼前的动作，越要同步；越靠后台的事情，越要 MQ**。
3. **每条消息都该能被"重放一遍"扛得住**：从第一天起就按"消息可能重放"设计消费逻辑（K05 幂等），不要等事故再补。

## 11. 本节小结

- **三连一笔总**：解耦 = 下游互不牵着（只认频道名）；削峰 = 写快读慢（洪峰进壶）；异步 = 用户拿单号即走。
- **三件套**：topic（频道）、partition（巷，巷内保序）、offset（巷内序号与消费进度）。两个真 topic（takeout-order-events / train-order-events）已现场确认。
- **边界三遗**：业务事实在 DB、消息只是广播；同步靠前异步靠后；消费必须按"会重放"设计（K05 承接）。
- **一条真事件**已现场收货：`{"orderNo":"...","dishId":1,"qty":1,"phase":"CREATED"}`。

## 附录 A：一条事件的 anatomy 全图

以本章实收的一条真事件为例，把每个字段的"谁写的、谁读的、干什么用"拆开：

```
{"orderNo":"1b5bdcd2-be8a-4752-8b6f-735339b53d03","dishId":1,"qty":1,"phase":"CREATED"}
```

| 字段 | 类型 | 生产者怎么写 | 消费者怎么读 | 业务含义 |
|---|---|---|---|---|
| orderNo | 字符串（UUID） | `orderCreated(...)` 第 1 参 | `extract(payload,"orderNo")` | 订单的唯一业务身份；**也是消息 key**（保序的种子） |
| dishId | 数字 | 第 2 参 | （dispatch 不用它） | 哪道菜 |
| qty | 数字 | 第 3 参 | （dispatch 不用它） | 数量 |
| phase | 字符串常量 | 第 4 参（受控值：CREATED / PAID / CANCELLED） | `extract(payload,"phase")` + 门二校验 | 生命周期阶段——**消费行为的开关** |

**外层三件套也标一下**：这条事件落在 **topic=takeout-order-events**、**partition=0**（单巷）、**offset=某递增数**（连同前后事件排成一线）。**字段名是生产者与消费者的合同**——合同任何一方改字段，对账表立刻断账。

## 附录 B：同步 vs 异步的对照表（一张收全）

| 维度 | 同步型接口 | 异步型（MQ）接口 |
|---|---|---|
| 返回时机 | 全部下游干完 | 写完事件即返 |
| 下游数量与响应时间 | 下游越多越慢（等待面 = 下游数） | 与下游数无关 |
| 下游故障的影响 | 直接表现为接口失败/超时 | 下游慢只影响滞后,不影响接口 |
| 用户拿到的 | 可能要长时间转圈 | 立刻一个 orderNo |
| 新增下游的成本 | 改接口代码 | 加一个消费者,生产者不动 |
| 新引入的问题 | 转圈与超时 | 消息丢失/重复/乱序（K05/K06 承接） |
| 本项目实例 | —— | takeaway 下单三秒内 DISPATCHED（异步派单） |

## 附录 C：术语速查（本章两套系统的角色对号）

点外卖里的角色，落在 Kafka 词汇里分别是：**你**=用户（下单即走）、**平台接单台**=topic、**小票的一格一格序号**=offset、**多条出餐通道**=partition、**厨师与骑手调度**=不同消费者组、**学徒盯着单子一单一单做**=组内分工、**抄一份完整单 forall 各班组**=组间广播。这套对号表建议放在手边——K02 到 K06 全系复用。

## 1. 全链顺序图（12 步，编号即依赖顺序）

```
 [浏览器 takeout-ui]          [nginx 9090]        [takeaway 8085]           [Kafka 9092]         [Redis 6379]
       │                           │                     │                       │                    │
 ① 用户点"下单"（order(d)）        │                     │                       │                    │
 ② axios POST /apitakeout/api/orders ──> 反代 ──────────> OrderController.create            │                    │
 ③                                                      OrderService.create                        │                    │
 ④                                                      ├─ H2: INSERT orders(status=CREATED)       │                    │
 ⑤                                                      └─ kafka.send(takeout-order-events,        │                    │
                                                             key=orderNo, phase=CREATED) ──>  ①号事件落盘                │
 ⑥ 返回订单 JSON（status=CREATED）<─────  <─── <─── <─── <──                   │                    │
 ⑦ 前端接着 POST /orders/{orderNo}/pay ─> OrderService.pay                    │                    │
 ⑧                                                      ├─ transition: CREATED→PAID                 │                    │
 ⑨                                                      ├─ Redis DECR takeaway:dish:1:stock ──────────────────────────> 5→4
 ⑩                                                      └─ kafka.send(..., phase=PAID) ─────────> ②号事件落盘               │
 ⑪ DispatchConsumer.onOrder 收到 PAID 事件 <──────────────────────────────────────────── 拉取消费                │
    ├─ 查 H2：订单存在且 status=PAID
    └─ 改 status=DISPATCHED，riderId=9000，save
 ⑫ 前端 loadMine()（每 3 秒轮询 GET /orders/mine）──> 看到骑手 9000 出现！
```

**时间尺度**：①-⑩ 是毫秒级同步链；⑪ 由 Kafka 异步完成（实测约 1 秒内）；⑫ 最坏要等 3 秒轮询间隔。

## 2. 前端两步：点击与支付（App.vue）

`frontend/takeout-ui/src/App.vue` 的核心函数：

```js
async function order(d) {
  if (!token.value) { alert('请先登录'); return }
  const o = await api.post('/orders', { shopId: d.shopId, dishId: d.id, quantity: 1 })
  msg.value = `订单 ${o.orderNo.slice(0, 8)} 已创建（CREATED），去支付`
  await api.post(`/orders/${o.orderNo}/pay`)            // 教学简化：点完单立刻"支付"
  msg.value += '，已支付！等待骑手派单…'
  loadMenu(); loadMine()
}
```

教学取舍直说：**真实外卖支付是跳第三方支付页再回调**；这里把"支付"压成第二个 HTTP 调用，让你专注状态机与消息链。

轮询（App.vue:54-57）：

```js
// 轮询：由于派单是 Kafka 异步的，下单后要"过会儿再看"
onMounted(() => { loadMenu(); timerId = setInterval(loadMine, 3000) })
onUnmounted(() => clearInterval(timerId))
```

**为什么轮询而不是 SSE/WebSocket？** demo-chat（8082）已经演示过 SSE 推模型；外卖这里选轮询是因为派单是"分钟级不需要实时"的弱实时场景，3 秒轮询实现最简单、断线自愈（下次请求自然恢复）。代价：N 个开着的页面 = 每秒 N/3 次 `/orders/mine` 查询——W05 的缓存思路（同款数据挡在 Redis）在这里同样适用。

token 从哪来？`api.js` 的 axios 拦截器（api.js:5-9）每次请求自动带上 `Authorization: Bearer <localStorage 里的 token>`。

## 3. 后端创建订单（步②-⑥）

`OrderController.create`（OrderController.java:28-30）：

```java
@PostMapping("/orders")
public Order create(@RequestBody OrderService.BookReq req, HttpServletRequest http) {
    return service.create((Long) http.getAttribute("uid"), req);
}
```

`uid` 是拦截器从 JWT 里解出来挂上的（S13 讲过）。业务核心 `OrderService.create`（OrderService.java:46-65）做四件事：

1. 校验数量 ≥ 1，查 Dish（不存在抛异常）；
2. **服务端回填 shopId 与总价**（`o.shopId = dish.shopId`、`o.totalYuan = dish.priceYuan * qty`）——前端传来的数字一律不信；
3. `@Transactional` 包裹下 INSERT（status=CREATED）；
4. 发 Kafka 事件 `phase=CREATED`。


## 4. 支付步（步⑦-⑩）：状态 + 库存 + 广播三连

`OrderService.pay`（OrderService.java:67-81）：

```java
public Order pay(Long userId, String orderNo) {
    Order o = orders.findByOrderNo(orderNo).orElseThrow(...);
    if (!o.userId.equals(userId)) throw new IllegalStateException("不是你的订单");
    transition(o, "PAID");                       // ← 白名单校验：CREATED→PAID 合法
    o.paidAt = Instant.now();
    Long left = redis.opsForValue().decrement("takeaway:dish:" + o.dishId + ":stock");
    if (left != null && left < 0) {              // ← 扣穿了：回滚库存并拒绝
        redis.opsForValue().increment("takeaway:dish:" + o.dishId + ":stock");
        throw new IllegalStateException("库存不足，请稍后再试");
    }
    producer.orderCreated(o.orderNo, o.dishId, o.quantity, "PAID");   // ← 广播事实
    return orders.save(o);
}
```

**实测：Redis 库存真实变化**

```
扣减前：$ redis-cli GET takeaway:dish:1:stock   → 3
下单+支付后：                                 → 2
```

**实测：Kafka 事件确认**（消费组视角，offset 推进 = 事件被消费）：

```
$ tools/kafka/bin/kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 --describe --group dispatch
GROUP     TOPIC                 PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
dispatch  takeout-order-events  0          8               8               0
```

LAG=0 表示消费者已追平最新消息——步⑪完成的直接证据。

## 6. 故障演练：每一步断了会怎样（对照表）

| 断点 | 用户体感 | 系统现状 | 恢复手段 |
|---|---|---|---|
| ② nginx 挂 | 页面报网络错 | 后端还活着 | 重启 nginx（infra/nginx-reload.sh） |
| ④ H2 INSERT 失败 | 500 | 无脏数据（事务回滚），Kafka 事件未发 | 修库重启 |
| ⑤ Kafka 挂 | 下单仍成功！ | 订单永远停在 CREATED | 重启 Kafka；事件丢了（教学：fire-and-forget） |
| ⑨ Redis 挂 | 支付 500 | 状态已 PAID 但库存没扣——**不一致** | 修 Redis；人工对账（教学引出 W06 补偿事务） |
| ⑪ 消费者崩 | 单卡在 PAID | 消息留在 Kafka，重启后**继续消费**（offset 已提交的不会丢） | 自动恢复 |
| ⑫ 前端关了 | 看不到 9000 | 订单照常流转（后台不受前端影响） | 重开页面即可看到最新态 |

注意 ⑤ 和 ⑨ 暴露的真相：**同步链和异步链的不一致窗口**是分布式系统的常态，W06 的"最终一致性"就是讲怎么补这个洞。

## 8. 练习（H/F/M 三层）

- **H（热身）**：用浏览器 DevTools 的 Network 面板走一遍完整点单，数一数从点击到出现"骑手 9000"共发出几个请求。
  验收：能看到 2 个 POST（orders、pay）+ 若干轮询 GET。
- **F（进阶）**：给 `order(d)` 增加防连点：点击后按钮 disabled 直到两个请求都返回。
  提示：Vue 的 `:disabled` 绑定一个 ref；finally 里恢复。
  验收：狂点"下单"不会产生重复订单（`/orders/mine` 里只有一单）。
- **M（硬核）**：写一个脚本模拟 20 个并发用户同时支付同一道库存=3 的菜，统计成功支付次数。
  提示：Python threading + requests；支付接口是 `POST /orders/{no}/pay`；先批量下单 20 单再并发支付。
  验收：恰好 3 个 200、17 个 500"库存不足"，且 `GET takeaway:dish:{id}:stock` 不为负。

### 参考答案要点

- 思考 1：JWT 证明"你是谁"，订单归属校验证明"这单是你的"——两者缺一不可。没有归属校验，任何登录用户都能支付/取消别人的单（水平越权）。
- 思考 2：能换，但会引入"事件已广播、库存却没扣成"的更脏窗口——消费者会基于一个可能被回滚的支付去派单。先扣库存（失败即中断）再广播，让广播成为"事实已定"的信号。
- 思考 3：先撑不住的是数据库连接池/H2（每请求一次 `findByUserId...` 查询）。救法：把订单列表也 cache-aside（W05 同款），或轮询改 SSE。
- 思考 4：可能是 CREATED（transition 在内存、未落库）也可能 PAID，取决于 `orders.save` 是否执行。收敛手段：把"改状态+落库+发消息"放进一个方法里按序执行，重启后以数据库为准；真正的工业方案是"先写库后发消息 + 对账任务兜底"（W06 主题）。

## 9. 附一：给这条链"计时"——各步耗时实测

衡量一条链，除了顺序还要知道**时间花在哪**。curl 的 `%{time_total}` 分站实测（本机 localhost，量级有参考意义、绝对值偏小）：

```
$ curl -s -o /dev/null -w "POST /orders     耗时=%{time_total}s\n" \
    -X POST 127.0.0.1:8085/api/orders -H "Authorization: Bearer $TOK" \
    -H 'Content-Type: application/json' -d '{"dishId":5,"quantity":1}'
POST /orders     耗时=0.052s        ← H2 写库 + Kafka send

$ curl -s -o /dev/null -w "POST /pay        耗时=%{time_total}s\n" \
    -X POST "127.0.0.1:8085/api/orders/$(...)/pay" -H "Authorization: Bearer $TOK"
POST /pay        耗时=0.048s        ← 校验+状态+Redis DECR+Kafka send+save

$ curl -s -o /dev/null -w "GET /orders/mine  耗时=%{time_total}s\n" \
    127.0.0.1:8085/api/orders/mine -H "Authorization: Bearer $TOK"
GET /orders/mine  耗时=0.009s       ← 读列表，无缓存（W02 思考 3 的优化点）
```

派单环节的耗时用"状态轮询"测（smoke.py 的同款等法）：**实测约 1 秒**（支付后第 1 秒轮询即 DISPATCHED）。分解 = Kafka 生产 flush（毫秒）+ consumer 拉取（由 `fetch.min.bytes` 等参数决定，Spring 默认即时触发）+ H2 事务落库。

三个结论：

1. 同步段（下单/支付）50ms 级——数据库写>MVC 框架开销；
2. 异步段 ~1s——Kafka 消费的默认投递节奏，完全够用；
3. 轮询响应 9ms 是链上最便宜的一格——所以"3 秒轮询一次"的方案养得起，这也是轮询被选择的技术底气。

## 10. 附二：链路上的"数据形态变化"对照表

理解一条链，除了步骤顺序，还要看**数据在各站长什么样**。同一张订单，六种形态：

| 站点 | 形态 | 关键字段样例（真实值） | 谁能看见 |
|---|---|---|---|
| 浏览器点击 | JS 对象 | `{shopId:1, dishId:1, quantity:1}` | 前端代码 |
| HTTP 请求体 | JSON 字符串 | `{"shopId":1,"dishId":1,"quantity":1}` | 网络抓包可见（http 明文） |
| Controller 入参 | BookReq record | `BookReq[shopId=null, dishId=1, quantity=1]` | JVM 内存 |
| Service 落库 | Order 实体/H2 行 | `orderNo=14bd0a5c-…, totalYuan=22, status=CREATED` | 数据库 |
| Kafka 事件 | JSON 字符串 + key | `key=14bd0a5c-…`，payload `{"orderNo":"…","phase":"PAID"}` | broker 磁盘 |
| 轮询响应 | Order JSON | `{"status":"DISPATCHED","riderId":9000,...}` | 前端 |

三个值得品的细节：

1. **shopId 在请求里是 null 也行**（OrderController 的 CreateReq 允许缺）——服务端从 dish 回填（W01 讲过的"不信前端"原则）。
2. **Kafka 事件故意很小**：只有 orderNo/dishId/qty/phase 四个字段。消费者要更多数据？自己查库（DispatchConsumer 正是这么做的）。**事件是"信号"，不是"全量数据副本"**——胖事件与瘦事件的取舍在 K06 有专论。
3. **id 与 orderNo 的分工**在前端可见：`o.orderNo.slice(0, 8)` 显示短码（App.vue:25），`o.id` 从不出现——对外标识与内部主键分离在 UI 层也贯彻。

## 本节小结
- 12 步链路：前端点击 →（nginx）→ Controller → Service（H2 + Redis + Kafka）→ Consumer → 轮询回显。
- 同步段（毫秒级）负责"记账"，异步段（秒级）负责"派单"——两者由 Kafka 事件衔接。
- 每一步都有实测证据可抓：curl 输出、Redis 数值、consumer offset、日志行。
- 不一致窗口（Kafka 挂、Redis 挂）是下一章 W03 和 W06 的正题。

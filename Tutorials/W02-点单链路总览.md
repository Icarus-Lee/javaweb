## 1. 全链顺序图（12 步，编号即依赖顺序）

```
 [浏览器 takeout-ui]          [nginx 9090]        [takeaway 8085]           [Kafka 9092]         [Redis 6379]
       │                           │                     │                       │                    │
 ① 用户点"下单"（order(d)）        │                     │                       │                    │
 ② axios POST /apitakeout/api/orders ──> 反代 ──────────> OrderController.create  │                    │
 ③                                                      OrderService.create       │                    │
 ④                                                      ├─ H2: INSERT orders(CREATED)                   │
 ⑤                                                      └─ kafka.send(takeout-order-events,             │
 ⑥ 返回订单 JSON（status=CREATED）<───── <─── <─── <───        key=orderNo, phase=CREATED) ──> 事件落盘  │
 ⑦ 前端接着 POST /orders/{no}/pay ─> OrderService.pay       │                    │
 ⑧                                                      ├─ transition: CREATED→PAID                    │
 ⑨                                                      ├─ Redis DECR takeaway:dish:2:stock ────────────> 4→3
 ⑩                                                      └─ kafka.send(..., phase=PAID) ─────────> ②号事件落盘
 ⑪ DispatchConsumer.onOrder 收到 PAID 事件 <───────────── 拉取消费    │
    ├─ 查 H2：订单存在且 status=PAID
    └─ 改 status=DISPATCHED，riderId=9000，save
 ⑫ 前端 loadMine()（每 3 秒轮询 GET /orders/mine）──> 看到骑手 9000 出现！
```

**时间尺度**：①-⑩ 毫秒级同步链；⑪ Kafka 异步（实测约 1 秒）；⑫ 最坏等 3 秒轮询间隔。

## 2. 概念最小人话 + 前端两步

一句人话：**同步链负责"记账"，异步链负责"干活"，中间靠一条小消息握手交棒。**

`frontend/takeout-ui/src/App.vue:22-28`：

```js
async function order(d) {
  if (!token.value) { alert('请先登录'); return }
  const o = await api.post('/orders', { shopId: d.shopId, dishId: d.id, quantity: 1 })
  msg.value = `订单 ${o.orderNo.slice(0, 8)} 已创建（CREATED），去支付`
  await api.post(`/orders/${o.orderNo}/pay`)            // 教学简化：点完单立刻"支付"
  loadMenu(); loadMine()
}
```

轮询（App.vue:56）：派单是异步的，下单后要"过会儿再看"，所以 3 秒轮询；断线自愈（下次请求自然恢复）。轮询而非 SSE 的取舍：派单是弱实时场景，3 秒轮询最简单；代价是 N 个页面 = 每秒 N/3 次 `/orders/mine`。token 由 `api.js` 的 axios 拦截器每次自动塞 `Authorization: Bearer`。

## 3. 后端创建与支付走查

`OrderController.java:27-30` 收下单请求，`uid` 由拦截器从 JWT 解出（S13 同款）。业务核心 `OrderService.java:46-65` 四件事：校验数量 ≥1 与菜品存在、**服务端回填 shopId 与 totalYuan**（不信前端）、事务内 INSERT(CREATED)、发 Kafka 事件。

支付步（`OrderService.java:67-81`）：

```java
public Order pay(Long userId, String orderNo) {
    Order o = orders.findByOrderNo(orderNo).orElseThrow(...);
    if (!o.userId.equals(userId)) throw new IllegalStateException("不是你的订单");
    transition(o, "PAID");                       // ← 白名单校验：CREATED→PAID 合法
    o.paidAt = Instant.now();
    Long left = redis.opsForValue().decrement("takeaway:dish:" + o.dishId + ":stock");
    if (left != null && left < 0) {              // ← 扣穿了：回滚库存并拒绝
        redis.opsForValue().increment("takeaway:dish:" + o.dishId + ":stock");
        throw new IllegalStateException("库存不足，请稍后再试");
    }
    producer.orderCreated(o.orderNo, o.dishId, o.quantity, "PAID");   // ← 广播事实
    return orders.save(o);
}
```

**实测：Redis 库存真实变化**（2026-09-15）：

```text
扣减前：$ redis-cli GET takeaway:dish:2:stock   → 4
下单+支付后：                                 → 3
```

## 4. 工程实录：手动按下 Kafka 的暂停键（2026-09-15 真机完整实录）

**问题假设**：都说"Kafka 挂了不影响下单支付"——这句话的**幻觉边界**在哪？我们真把 Kafka 杀掉，只留两个后端活着，逐秒观察。

**第一步：制造现场**。记下 dispatch 组的 offset（重启前 `--describe --group dispatch`：CURRENT=26 / LOG-END=26 / LAG=0，全链健康），然后：

```text
$ kill $(cat logs/kafka.pid)          # 只停 Kafka，后端与 Redis 不动
$ ss -ltn | grep 9092                  # （无输出 = 9092 没了）
```

**第二步：下单 + 支付，看哪几步还活着**：

```text
$ 创建订单 → {"orderNo":"95d1e84b-...","status":"CREATED",...}     ← 步②-⑥ 全部正常！
$ 支付 → status=PAID                                              ← 步⑦-⑩ 也正常！
$ sleep 8 → GET /orders/{no} → status=PAID, riderId=null          ← 8 秒后骑手没来
```

**第三步：观察点——日志里"派单行"的缺席**：

```text
$ grep -c "派给骑手" logs/takeaway.log        → 10（没有一条含 95d1e84b）
$ tail -5 logs/takeaway.log   （生产者与消费者的哀嚎）：
2026-09-15T13:01:23 WARN ... [Producer clientId=takeaway-producer-1] Connection to node 1
  (localhost/127.0.0.1:9092) could not be established. Node may not be available.
2026-09-15T13:01:24 WARN ... [Consumer clientId=consumer-dispatch-1, groupId=dispatch]
  Node 1 disconnected.
```

**读数**：同步链（H2 记账 + Redis 扣减）对 Kafka 完全无感——订单是真创建了、钱是"真付了"、库存是真扣了；但 ⑪ 永远不来，**订单永远卡在 PAID**。用户体感："付了钱没动静"。这就是"fire-and-forget 广播"的代价现场：**成功与可见之间隔了一整个消费者**。

**第四步：重启 Kafka，看"自愈"到底发生什么**：

```text
$ bash infra/start-all.sh
== 2) Kafka (KRaft 单节点) ==  kafka: up ...（其余"已在线"跳过）
```

重启后真相出现了两层（这次实测**比预期更狠**，值得引出下一段）：

```text
$ tools/kafka/bin/kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 --describe --group dispatch
dispatch  takeout-order-events  0   0  0  0   ← offset 与事件双双归零！
$ GET /orders/95d1e84b-... → status=PAID, riderId=null（又等 20 秒仍然 PAID）
```

那单**永远卡 PAID**，连"重启后补派"都没机会——原因见后续修复段：dispatch 组变成"无 offset 组"触发 `auto-offset-reset=latest`（W03 的语义），历史事件不再重放；而这次历史事件**根本没了**（原因见实录 B 的修复 diff）。

**第五步：人工兜底——补投重放消息修复订单**（最终一致性的手工版）：

```text
$ echo '{"orderNo":"95d1e84b-df65-47d8-8067-2b56c9996acb","dishId":2,"qty":1,"phase":"PAID"}' \
    | tools/kafka/bin/kafka-console-producer.sh --bootstrap-server 127.0.0.1:9092 --topic takeout-order-events
$ sleep 3 → GET /orders/95d1e84b-... → status=DISPATCHED, riderId=9000 ✅
$ tail -1 logs/takeaway.log → [dispatch] order=95d1e84b-... → 派给骑手 9000
```

三重 guard 对这条"迟到的事实"完全接纳（订单确实 PAID）——**消息驱动系统的好处：事实重放即可重算结果**。

### 修复与防御 diff

本次实测顺带抓到 infra 脚本一个真 bug：Kafka 4.x 把格式化标记从 `cluster.meta.properties` 更名成了 `meta.properties`，而 start-all.sh 判断的是旧名——**永远成立**，于是"Kafka down 时重启"会 `rm -rf` 数据目录并重新格式化，事件与 offset 全被洗掉。真机证据：

```text
$ ls data/kafka/kraft/
bootstrap.checkpoint  meta.properties  ...      ← 没有 cluster.meta.properties
$ ls -la data/kafka/kraft/takeout-order-events-0/*.log   # 13:03 全新空文件
```

修复 diff（infra/start-all.sh:24）：

```diff
-  if [ ! -f "$KAFKA_DATA/cluster.meta.properties" ]; then
+  if [ ! -f "$KAFKA_DATA/meta.properties" ] && [ ! -f "$KAFKA_DATA/cluster.meta.properties" ]; then
```

防御注释：**"重启 = 万能修复"是时序幻觉**。本次实拍：重启往往只修好了自己，却把问题钉死（PAID 永卡）。兜底思路三层：①对账任务发现"卡在 PAID > 5 分钟的单"；②补偿重发事件（上面第五步的手工版自动化）；③冒烟测试把"支付后 N 秒 DISPATCHED"写成断言（smoke.py 已有）。

## 5. 模式对比：每步挂了的用户体感（对照表）

| 断点 | 用户体感 | 系统现状 | 恢复手段 |
|---|---|---|---|
| ② nginx 挂 | 页面报网络错 | 后端还活着 | 重启 nginx（infra/nginx-reload.sh） |
| ④ H2 INSERT 失败 | 500 | 无脏数据（事务回滚），事件未发 | 修库重启 |
| ⑤ Kafka 挂 | **下单支付仍成功** | 订单卡 PAID（本站实录），事件丢失或留存视进程生死 | 修 Kafka；人工兜底重放 |
| ⑨ Redis 挂 | 支付 500 | 状态已 PAID 库存没扣——不一致 | 修 Redis；人工对账（W06 补偿事务） |
| ⑪ 消费者崩 | 单卡 PAID | 消息留在 Kafka，offset 已提交，重启继续消费 | 自动恢复 |
| ⑫ 前端关了 | 看不到 9000 | 订单照常流转 | 重开页面 |

注意 ⑤ 和 ⑨：**同步链与异步链的不一致窗口**是分布式常态，W06 的"最终一致性"就是讲怎么补这个洞。

三个结论：同步段 50ms 级（数据库写开销 > MVC 框架开销）；异步段 ~1s（Kafka 默认投递节奏，完全够用）；轮询 9ms 是全链最便宜的一格——"3 秒轮询一次"养得起的技术底气。**生产上要看 p99 而非均值**（长尾被代理与 GC 放大），本机均值仅作量级参考。

### 6.2 链路上的"数据形态变化"对照表（同一张订单，六种形态）

| 站点 | 形态 | 关键字段样例 | 谁能看见 |
|---|---|---|---|
| 浏览器点击 | JS 对象 | `{shopId:1, dishId:1, quantity:1}` | 前端代码 |
| HTTP 请求体 | JSON 字符串 | `{"shopId":1,"dishId":1,"quantity":1}` | 网络（http 明文可抓） |
| Controller 入参 | BookReq record | `BookReq[shopId=null, dishId=1, quantity=1]` | JVM 内存 |
| Service 落库 | Order 实体/H2 行 | `orderNo=14bd0a5c-…, totalYuan=22, status=CREATED` | 数据库 |
| Kafka 事件 | JSON 字符串 + key | key=orderNo，`{"orderNo":"…","phase":"PAID"}` | broker 磁盘 |
| 轮询响应 | Order JSON | `{"status":"DISPATCHED","riderId":9000,...}` | 前端 |

三个值得品的细节：① shopId 在请求里为 null 也行——服务端从 dish 回填（"不信前端"原则）；② **Kafka 事件故意很小**（orderNo/dishId/qty/phase 四字段），消费者要更多数据自己查库（DispatchConsumer 正是如此）——事件是"信号"不是"全量副本"，胖瘦事件取舍在 K06；③ id 与 orderNo 的分工在 UI 也贯彻：短码显示、id 不出现。

## 7. 思考题

1. 支付接口为什么还要查一次 `o.userId`（OrderService.java:70）？JWT 里不是有 uid 吗？
2. `pay()` 里 Kafka 发消息放在 Redis 扣减**之后**，顺序能换吗？换了引入什么新问题？
3. 轮询 3 秒改 300ms，后端哪层先撑不住？怎么救？
4. 步⑧状态进 PAID 后进程 kill（save 未执行），重启后订单是什么状态？这个"半步"问题怎么收敛？
5. 本站实录里"重启反而钉死 PAID"与"补投重放修好"，你如何判断什么时候**敢**自己动手重放一条事件？

### 参考答案要点

- 思考 1：JWT 证明"你是谁"，订单归属校验证明"这单是你的"——缺一即水平越权。
- 思考 2：能换，但会引入"事件已广播、库存没扣成"的更脏窗口。先扣库存（失败即中断）再广播，让广播成为"事实已定"的信号。
- 思考 3：H2 与连接池先撑不住。救法：订单列表 cache-aside（W05 同款）或轮询改 SSE。
- 思考 4：可能是 CREATED（未 save）也可能 PAID；收敛手段是"改状态+落库+发消息"按序在一个方法里，重启以数据库为准；工业方案是"先写库后发消息 + 对账兜底"（W06）。
- 思考 5：重放前确认①订单当前状态允许该事件（幂等 guard 会挡重复）；②消息是"事实的记录"而非"指令"——重任务是让系统重新看到同一事实，而不是伪造一条指令。

## 9. 本节小结

- 12 步链路：前端点击 →（nginx）→ Controller → Service（H2 + Redis + Kafka）→ Consumer → 轮询回显。
- 实录：Kafka 停机时同步链体面运行、终点永不来是幻觉边界；[dispatch] 行缺席 + Connection refused 日志是两张现场证据。
- "重启=自愈"是幻觉：事件与 offset 的生死取决于磁盘与启动脚本细节；手工补投重放是可观测的兜底。

## 1. 两个问题，两种解法（人话开场）

**问题 A（削峰）**：顾客下单后跑了，订单永远挂 CREATED。谁来关？不可能雇人盯——需要**闹钟**（定时任务）；且关单动作独立成批，不打扰正常请求——这就是削峰：**把"必须现在做"变成"可以晚点做"**。

**问题 B（补偿）**：`pay()` 一笔操作横跨 H2（状态）/Redis（库存）/Kafka（广播）三个系统，没有共同的大事务。工业界两条路：分布式事务（2PC/TCC/Seata，强一致、极高复杂度）vs **补偿事务（Saga）**——每步本地事务，失败执行已完成步骤的反向操作。教学项目选 2。

## 2. 超时关单模板：train 的 closeExpired()（可直接抄）

`backend/train/src/main/java/com/javaweb/train/service/BookingService.java:104-110`：

```java
/** 超时关单：UNPAID 超过 5 分钟自动取消（定时任务每 15 秒扫一次）。 */
@Scheduled(fixedDelay = 15_000, initialDelay = 20_000)
public void closeExpired() {
    for (Booking b : bookings.findByStatus("UNPAID")) {
        if (b.createdAt.isBefore(Instant.now().minus(Duration.ofMinutes(5)))) {
            cancel(b.userId, b.orderNo);
        }
    }
}
```

四个设计点（抄到外卖要改的四处）：

1. **`fixedDelay` 而非 `fixedRate`**：上一轮跑完再计时——关单批次大不叠罗汉；`initialDelay=20s` 等应用起稳。
2. **只扫"可能需要关"的单**：数据量大的进化版是 `findByStatusAndCreatedAtBefore(status, deadline)` 让数据库过滤。
3. **复用 `cancel()`**：超时关单 = 用户取消的无人版，副作用（回余票 INCR、发 CANCELED 事件，BookingService.java:96-99）必须一模一样——**不为定时任务写平行的取消代码**。
4. **幂等天然成立**：取消过的单 `cancel()` 里 `if ("CANCELLED".equals(b.status)) return b;` 短路。

外卖版：状态词换 `CREATED`；OrderRepo.java:10 已有现成的 `findByStatus(status)`；**唯一缺的**是 takeaway 的取消逻辑散在 Controller 里（OrderController.java:37-44），抄模板前先收编进 Service（练习 F）。

## 3. 补偿事务心智模型：一张表看懂

以 pay() 的三步为账本：

| 步骤 | 正向操作 | 失败时的补偿 | 本项目现状 |
|---|---|---|---|
| 1. H2 改状态 PAID | transition + save | 本地事务自动回滚 | ✅ |
| 2. Redis 扣库存 | DECR | INCR 补回 | ✅ 扣穿时有；进程崩溃时无（对账兜） |
| 3. Kafka 发 PAID 事件 | send | 发冲正事件 / 重放 | ⚠️ fire-and-forget（W02 实录全见） |
| 4. （未来的）真实扣款 | 调支付网关 | 调退款接口 | 用假支付，不涉及 |

**Saga 口诀**：正向链走多远，补偿链就往回退多远。与"大事务"的本质区别：补偿期间全世界能看见中间状态，最终一致 = "晚几秒对上"，不是"从没错过"。

## 4. 工程实录：退款分支的状态机对照与"默认拒绝"实测（2026-09-15）

### 4.1 实测：CANCELED→REFUNDED 为什么被拒

W04 的教学实验端点（try-to）把拒绝路径量了出来：

```text
$ curl -s -H "Authorization: Bearer $TOK" ".../api/orders/$ON2/try-to/REFUNDED"
{"from":"CANCELED","to":"REFUNDED","ok":false,
 "rejected":"非法状态流转: CANCELED -> REFUNDED"}
$ 对同一单真实再次取消：
{"from":"CANCELED","to":"CANCELED","ok":false,
 "rejected":"非法状态流转: CANCELED -> CANCELED"}
```

### 4.2 为什么默认拒绝：业务事故对照表

`PAID → REFUNDED` 这条边**此刻不在白名单**（此时白名单的 5 条边没有它），一切"达到 REFUNDED"的尝试都被拒。这不是疏忽，而是**fail-safe 设计在异常分支上的原则体现**。逐格对照可能的事故：

| 若表面放行这条边 | 对应真实事故 | 默认拒绝如何避免 |
|---|---|---|
| CANCELED→REFUNDED | 已退款单被"再退一次"——双倍退款，财务事故 | 状态机拒绝（本次实测 500/拒） |
| CREATED→REFUNDED | 没付过钱也退——凭空给钱 | 没有 CREATED-REFUNDED 边 |
| DELIVERED→REFUNDED | 吃完的汉堡被退——恶性薅羊毛通道 | 白名单没有该边；真实退款要客服审单（工单系统） |
| REFUNDED→REFUNDED | 重试风暴打爆退款网关 | 终态无出边，天然幂等闸门 |
| 恢复路径 CANCELED→CREATED | 撕掉的单复活重付 | 异常分支只出不进 |
| PAID→CANCELED 却不回库存 | （现状的坑）顾客占配额 | W06 作业④补 INCR——**拒绝正确但副作用失衡** |

**读法**：白名单的"默认拒绝"让每个事故都停在第一道闸。**审计语义说来**：`CANCELED` 与 `REFUNDED` 是两个终态——前者是"用户撤销"，后者是"事实退款"，财务报表与审计台（train 的 audit 思路）对两者要求不同的凭证链；把 REFUNDED 融进 CANCELED 会让"钱到底退没退"不可追问，所以教学把它拆成独立状态。

### 4.3 实现路径：REFUNDED 退款分支（本站动手作业）

语义：`PAID → REFUNDED` 一步到位（教学简化）。四处改动（提示清单，代码自己写）：

**① 白名单加边**（OrderService.java:20-21）：

```java
"PAID-REFUNDED");                          // ← 新增：只有 PAID 能退款
```

**② Service 加 refund 方法**（约 12 行）：签名对齐 pay()；三道校验同 pay（存在/归属/transition 白名单自动挡 DELIVERED/CANCELED 的退款）；**补偿动作** `redis...increment("takeaway:dish:"+o.dishId+":stock")`；发 `phase=REFUNDED` 事件；打 `refundedAt` 时间戳（ddl-auto 自动加列）。

**③ Controller 加端点**（约 6 行）：`@PostMapping("/orders/{orderNo}/refund")` 照 cancel() 抄；顺手把两个接口的归属校验收编进 Service。

**④ cancel 补库存回滚**（1 行 INCR）——对照 train 的 cancel()（BookingService.java:96-99）。

**一个必须想通的问题**：为什么"回库存"放在 transition **之后**？反着想：先 INCR 再改状态，若 transition 拒绝（非 PAID），库存白加——钱没退库存先回来更离谱。**补偿操作放在状态确认之后**，让状态机成为补偿的开关。INCR 后进程崩了呢？状态已 REFUNDED 库存没回——最终一致的残余窗口，交给思考 4 的对账任务。

### 4.4 验收标准（做完必须全过）

```text
# 1. 退款成功路径
POST /api/orders/{no}/refund → 200, status=REFUNDED
redis GET takeaway:dish:{id}:stock → 比退款前 +1

# 2. 白名单拒绝路径
对 DELIVERED / CANCELED 的单退款 → 拒绝（4.1 的实测输出）
重复退款（REFUNDED → REFUNDED）→ 拒绝，库存不再 +1

# 3. 全局回归
bash infra/smoke.sh → 23/23 依旧全绿
```

### 4.5 错误答案展廊（先看再写）

1. **先 INCR 后 transition**：拒绝时库存白加。
2. **忘记发 Kafka 事件**：退款静默完成，审计失明。
3. **没有幂等标记**：连点两次 → 库存 +2！白名单挡住第二次救了命，但带副作用的操作应自带幂等标记（`refunded:{orderNo}` key）。
4. **把退款写成删除订单**：订单流水**永不删除**——删除让对账与审计双双失明。

| 武器 | 思想 | 本项目位置 | 挡的峰 |

### 5.1 本机实测：cancel 与库存的"三个数字"（2026-09-15）

W04 §4.4 的悬案收个半程——变成可复现三步实验：

```text
支付前：  redis-cli GET takeaway:dish:4:stock → 6
支付后：                                 → 5    （pay() 的 DECR 生效）
取消后：                                 → 5    （cancel 没有任何库存动作 ← 悬案）
作业完成后应为：                         → 6    （作业④ 的 INCR 补偿生效）
```

**为什么把"缺一步"当教材**：亲手补上扣减-回补环路时会同时面对三个问题——回补放 transition 前还是后（W04 §4.4）、要不要幂等标记（连点两次取消会不会加两次）、CANCELED 与 REFUNDED 是否都回补。一行 INCR 牵出整个补偿心智模型。

### 5.3 "顺手做"与"专门做"的对比（反模式）

```java
// 反模式：读单时顺手检查超时（读路径藏写动作！）
public Order find(String orderNo) {
    Order o = ...;
    if (o.status.equals("CREATED") && 超过5分钟) { transition(o, "CANCELED"); ... }
    return o;
}
```

三宗罪：读接口意外变慢且有副作用；没人读的单永远不关（**幽灵单**）；测试路径与真实触发不一致。@Scheduled 15 行模板把关单变成独立、可观测、幂等的专职操作。

### 5.2b 定时扫描 vs 延迟消息的两栏对照（思考 2 的正文版）

| | @Scheduled 扫描（train/takeaway 方案） | Kafka 延迟消息 |
|---|---|---|
| 实现成本 | 15 行，@EnableScheduling 即有 | Kafka 无原生延迟：要定时轮/多 topic + 转发消费者 |
| 精度 | 扫描间隔级（15s） | 消息级（精确到秒） |
| 膨胀风险 | 无（扫的是状态表） | 每单一消息，百万单即积压 |
| 量级适用 | 百万单内足够 | 海量高频、精度敏感 |
| 失败重试 | 天然（下一轮再扫） | 事件失败要死信 + 重投 |

**判断句**：量级没到、精度要求不细 → 扫描；两者都要 → 引入专门调度中间件（时间轮/云函数定时触发），不会再回 Kafka 天然延迟。这与削峰表"定时批量"一行呼应：**先选方案面，再写代码面**。

### 5.4 对账与人工单的落地口诀（思考 4/5 的展开）

对账任务的最小形态是三条：**以数据库为准**（订单表是真相源，Kafka/Redis 是影子）；**幂等标记先行**（`refunded:{orderNo}` 这类 key 先抢后补）；**扫错了要可再扫**（checkpoint 只记录扫描水位，失败可从 checkpoint 重入）。人工单队列的最小落地：一张 `manual_tickets` 表（orderNo、失败原因、重试次数、状态）+ 告警 + 后台人工处理后接口重放补偿。**机器解决不了的单，必须有序地交给人**——这一点在实战里比任何消息中间件参数都重要。

### 5.5 最终一致性的四个承诺

| 承诺 | 内容 | 本项目兑现者 |
|---|---|---|
| **会收敛** | 不一致是暂时，终态一致 | 消费者追平 LAG / 对账任务 |
| **可观测** | 知道目前不一致有多少 | LAG 数值 / 状态分布查询 |
| **有兜底** | 超时未收敛的被拯救 | 人工单队列（思考 5） |
| **有顺序** | 同一实体操作不乱序 | key=orderNo 分区有序（W03） |

## 6. 思考题

1. @Scheduled(fixedDelay) 跑到一半进程被 kill，重启后会漏单吗？
2. 超时关单为什么不用 Kafka 延迟消息？各适合什么量级？
3. closeExpired() 直接调 `cancel(b.userId, ...)` 的隐患是什么？
4. 设计对账任务：每分钟比对"REFUNDED 订单数"与"Redis 库存增量"。伪代码 10 行以内。
5. 补偿也失败的单该去哪？描述人工单队列的落地。

### 参考答案要点

1：下一轮重新扫描全部 UNPAID，"漏"只持续一个周期。2：Kafka 无原生延迟消息（要轮/多 topic），百万单内扫描足够。3：依赖调用者传对参数；更稳是 cancel(orderNo) 内部自取 b.userId 或单独 internalCancel()（定时任务是系统身份）。4：`for (Order o : findByStatus("REFUNDED")) if (!redis.hasKey("refunded:"+o.orderNo)) { redis.incr(stockKey); redis.set("refunded:"+..., "1"); }`。5：落库标记 + 告警 + 人工重放补偿；机器解决不了的单必须**有序地交给人**。

## 1. 生活类比与动机：没人守着，就得靠闹钟和补救

两个问题，两种解法：

**问题 A（削峰）**：顾客下单后跑了，订单永远挂在 CREATED。谁来关它？——不可能雇人盯着，需要**闹钟**（定时任务）。更进一步：如果 10 万人同一秒下单、30% 的人跑了，关单动作如果放在"下一个请求顺手处理"会拖慢所有正常请求；**独立定时任务**把这 3 万次关单摊平到每 15 秒一批，用户请求完全无感——这就是削峰。

**问题 B（补偿）**：`pay()` 一笔操作横跨三个系统：H2（状态）、Redis（库存）、Kafka（广播）。Redis 扣完库存后进程崩了，H2 里的状态回滚但 Redis 不会——**三个系统没有一个共同的"大事务"**。工业界两条路：

1. **分布式事务**（2PC/TCC/Seata）：强一致，成本高、复杂度高；
2. **补偿事务（Saga 思路）**：每步都是本地事务；失败了就执行已完成步骤的**反向操作**（扣了库存→补回库存；发了事件→发冲正事件）。短暂不一致（几秒）换取实现简单、吞吐高。

教学项目选 2，且只实现其中最关键的一小段——但心智模型一次讲全。

## 2. 超时关单模板：train 的 closeExpired()（可直接抄）

`backend/train/src/main/java/com/javaweb/train/service/BookingService.java:104-113`：

```java
/** 超时关单：UNPAID 超过 5 分钟自动取消（定时任务每 30 秒扫一次）。 */
@Scheduled(fixedDelay = 15_000, initialDelay = 20_000)
public void closeExpired() {
    for (Booking b : bookings.findByStatus("UNPAID")) {
        if (b.createdAt.isBefore(Instant.now().minus(Duration.ofMinutes(5)))) {
            cancel(b.userId, b.orderNo);
        }
    }
}
```

四个设计点（也是你抄到外卖时要改的四处）：

1. **`fixedDelay` 而非 `fixedRate`**：上一轮跑完再计时——关单批次大也不会叠罗汉。`initialDelay=20s` 等应用完全起稳。
2. **`findByStatus("UNPAID")`**：只扫"可能需要关"的单，不全表扫。数据量大时的进化版是 `findByStatusAndCreatedAtBefore(status, deadline)` 让数据库过滤（OrderRepo 里同款派生查询即可）。
3. **复用 `cancel()` 而不是重复写取消逻辑**：超时关单 = 用户取消的无人版，取消的全部副作用（回余票 INCR、发 CANCELED 事件）必须一模一样。**不要为定时任务再写一份平行的取消代码**。
4. **幂等天然成立**：已支付的单不在 UNPAID 列表里；取消过的单 `cancel()` 里有 `if ("CANCELLED".equals(b.status)) return b;` 直接返回——**扫一万遍也不会重复关**。

### 外卖版要改什么（作业预告）

外卖的状态词是 `CREATED`（不是 UNPAID），仓库方法是现成的 `orders.findByStatus(status)`（OrderRepo.java:7 已经有了！），超时阈值建议 5 分钟一致。唯一缺的：**takeaway 的 OrderService 里没有 cancel 方法**——取消逻辑散在 Controller 里（OrderController.java:37-44），抄模板前先把它收编进 Service（练习 F）。

## 3. 补偿事务心智模型：一张表看懂

以 pay() 的三步为账本（W04 走查过），补上每一步的"反向操作"：

| 步骤 | 正向操作 | 失败时的补偿 | 本项目现状 |
|---|---|---|---|
| 1. H2 改状态 PAID | `transition + save` | 事务自动回滚（本地事务） | ✅ 已有 |
| 2. Redis 扣库存 | `DECR` | `INCR` 补回 | ✅ 扣穿时有；进程崩溃时无（对账兜） |
| 3. Kafka 发 PAID 事件 | `send` | 发 `phase=REFUND` 冲正事件 / 消费端幂等 | ⚠️ fire-and-forget（丢了就丢） |
| 4. （未来的）真实扣款 | 调支付网关 | 调退款接口 | 本模块用假支付，不涉及 |

**Saga 的口诀**：正向链走多远，补偿链就往回退多远。步骤 1 失败→什么都不用补（本地事务自己回滚）；步骤 2 失败→补步骤 2 自己（INCR）；步骤 3 失败→视业务容忍度（外卖广播丢了 = 骑手没派单 = 补偿是"人工催派"或对账任务重发）。

**与"大事务"的本质区别**：补偿期间**全世界能看见中间状态**（库存短暂少 1），最终一致 = "晚几秒对上"，不是"从没错过"。

## 4. 实现路径：REFUNDED 退款分支（本站动手作业）

### 4.1 业务语义先说清

- **CANCELED**：没付钱（CREATED）或付了但未履约（PAID，库存已扣）的取消。当前代码 PAID 取消**不回库存**——这个坑一并补。
- **REFUNDED**：钱已退给用户。语义链：`PAID → CANCELED（回库存+退款入账）→ REFUNDED（退款到账）`，或简化为 `PAID → REFUNDED` 一步到位（教学选简化版）。

### 4.2 四处改动（提示清单，代码自己写）

**改动 ①：白名单加一条边**（OrderService.java:20-21）

```java
private static final Set<String> LEGAL_NEXT = Set.of(
        "CREATED-PAID", "PAID-DISPATCHED", "DISPATCHED-DELIVERED",
        "CREATED-CANCELED", "PAID-CANCELED",
        "PAID-REFUNDED");                          // ← 新增：只有 PAID 能退款
```

**改动 ②：Service 加 refund 方法**（新建，约 12 行）

提示要点（不看这四点先自己写）：
- 签名对齐 `pay()`：`public Order refund(Long userId, String orderNo)`；
- 三道校验同 pay：订单存在、归属本人、`transition(o, "REFUNDED")`（白名单自动挡 DELIVERED/CANCELED 的退款请求）；
- **补偿动作**：`redis.opsForValue().increment("takeaway:dish:" + o.dishId + ":stock")`——这是"支付扣库存"的反向操作（Saga 的反向链）；
- 发一条 Kafka 事件 `phase=REFUNDED`（producer.orderCreated 现成可用，phase 只是字符串）；广播的意义：未来审计台/财务消费者靠它记账；
- 打时间戳：给 Order 加 `refundedAt` 字段（`ddl-auto: update` 自动加列）。

**改动 ③：Controller 加退款端点**（OrderController，约 6 行）

```java
@PostMapping("/orders/{orderNo}/refund")
public Order refund(@PathVariable String orderNo, HttpServletRequest http) { ... }
```

照着 cancel() 抄即可——注意 cancel 里的归属校验逻辑与 refund 重复，顺手收编：两个接口都改调 Service 方法（校验进 Service，Controller 只传 uid）。

**改动 ④：顺手补 cancel 的库存回滚**（1 行）

`OrderController.cancel` 现在只调 `transition(o, "CANCELED")`；把取消逻辑收编进 Service 后，在 CANCELED 分支里加上 INCR 回库存——对照 train 的 `cancel()`（BookingService.java:96-103）逐行抄。

### 4.3 验收标准（做完必须全部通过）

```
# 1. 退款成功路径
POST /api/orders/{no}/refund   → 200, status=REFUNDED, riderId 之前为 null
redis-cli GET takeaway:dish:{id}:stock   → 比退款前 +1

# 2. 白名单拒绝路径（知识内 500/409）
对 DELIVERED 的单退款     → 拒绝（PAID-REFUNDED 不含 DELIVERED 起点）
对 CANCELED 的单退款      → 拒绝
重复退款（REFUNDED→REFUNDED）→ 拒绝

# 3. 幂等/一致性
退款后再次退款 → 状态拒绝，库存不再 +1

# 4. 全局回归
bash infra/smoke.sh   → 23/23 依旧全绿
```

### 4.4 一个必须想通的问题（写代码前读）

**为什么 refund 里"回库存"放在 transition 之后而不是之前？** 反过来想：先 INCR 再改状态，若 transition 抛异常（非 PAID），库存被白加了——钱没退库存先回来，比"状态退了库存没回"更离谱。**补偿操作放在状态确认之后**，让状态机成为补偿的开关。再深一层：INCR 之后进程崩了呢？——状态已是 REFUNDED 但库存没回：这就是最终一致性的残余窗口，交给思考题 4 的对账任务。

## 5. 附：削峰的三种武器与本项目用到的位置

削峰（防止瞬时洪峰打到脆弱层）在本项目出现了三次，形态不同、思想一致——**把"必须现在做"变成"可以晚点做"**：

| 武器 | 思想 | 本项目位置 | 挡的是什么峰 |
|---|---|---|---|
| 定时批量处理 | 攒一批慢处理 | train/takeaway 的 @Scheduled 关单 | 用户请求被"顺手关单"拖慢 |
| 消息队列缓冲 | 写快读慢 | 下单瞬间只发 Kafka 事件，派单后台慢慢消费 | 派单风暴打爆数据库 |
| 缓存回源控制 | 少数人回源 | W05 的空哨兵/互斥锁 | 全员穿透打爆 H2 |

### 5.1 "顺手做"与"专门做"的对比（代码味）

新手常把超时处理写成"读单时顺手关"：

```java
// 反模式：读订单时顺手检查超时
public Order find(String orderNo) {
    Order o = orders.findByOrderNo(orderNo).orElseThrow(...);
    if (o.status.equals("CREATED") && 超过5分钟) {   // 读路径上藏了一个写动作！
        transition(o, "CANCELED"); ...
    }
    return o;
}
```

三宗罪：读接口意外变慢且带副作用；没人读的单永远不关（**幽灵单**）；测试路径与真实触发路径不一致。@Scheduled 的 15 行模板把"关单"变成**独立、可观测、幂等**的专职操作——这就是"削峰"的完整含义：不只削流量峰，也削"职责蔓延"。

### 5.2 最终一致性的四个承诺（验收一个系统是否"最终一致"用这张表）

| 承诺 | 内容 | 本项目的兑现者 |
|---|---|---|
| **会收敛** | 不一致是暂时的，终态一致 | 消费者追平 LAG / 对账任务 |
| **可观测** | 能知道"目前不一致的有多少" | consumer LAG 数值 / 状态分布查询 |
| **有兜底** | 超过时限仍未收敛的会被拯救 | 思考题 5 的人工单队列 |
| **有顺序** | 同一实体的操作不乱序 | key=orderNo 分区有序（W03） |

以后你在任何系统里听到"我们已经最终一致了"，就用这四问反问——答不上来的都是假的最终一致。

### 5.3 补偿作业的"错误答案展廊"（先看再写，避免踩同一批坑）

实现 REFUNDED 时最常交出这四种作业，提前打预防针：

1. **先 INCR 后 transition**：transition 抛异常时库存白加（4.4 讲过）。
2. **忘记发 Kafka 事件**：下游财务/审计台永远不知道这笔退款——退款静默完成。
3. **没有幂等标记**：连点两次退款按钮 → 库存 +2！白名单挡住第二次（REFUNDED→REFUNDED 非法）救了命，但**带副作用的操作应自带幂等标记**（如 Redis key `refunded:{orderNo}`）。
4. **把退款写成删除订单**：`orders.delete(o)` 看起来更"干净"——错！订单流水**永不删除**，退款只是状态变化；删除让对账与审计双双失明。

### 5.5 削峰数字从哪来：一次"洪峰"的账面实验（思路）

不需要 JMeter，用 bash 就能做洪峰压力的可视化（思路演示，正确数字留给练习）：

```
$ for i in $(seq 1 50); do curl -s -o /dev/null -w "%{time_total}\n" \
    127.0.0.1:8085/api/menus/1 & done | sort -rn | head -3
0.041   ← 50 并发下的最长响应（对比单发 0.002s，放大 20 倍）
0.037
0.033
```

**读法**：50 个并发读把单发 2ms 顶成 41ms——H2/连接池在洪峰下排队。如果菜单走了缓存（本机 Redis 单发 1.3ms），排队的正是 1.3ms 不是 50ms，**这就是"缓存其实是削峰"的实验证据**。把本节思路移植到下单接口（POST /orders）就是你的首份压测报告雏形（T06 的完整版在火车模块）。

### 参考答案要点

- 思考 1：不会永久漏——fixedDelay 下一轮会重新扫描全部 UNPAID，"漏"只持续一个周期。@Scheduled 的代价就是轮询间隔级的延迟。
- 思考 2：延迟消息精确但需要 broker 支持（Kafka 无原生延迟，要上定时轮/多 topic + 消费转发），且每单一消息在百万单时膨胀；定时扫描实现 15 行、量级百万单内足够（扫 UNPAID 有索引）。量级再大才换延迟消息或分片扫描。
- 思考 3：cancel 内部有归属校验 `if (!b.userId.equals(userId)) throw`——超时关单传的是单主本人的 userId，恰好通过。隐患是**依赖调用者传对参数**：更稳的设计是 cancel(orderNo) 内部自取 b.userId，或单独的 internalCancel() 不做归属校验（定时任务是系统身份，不是冒充用户）。
- 思考 4：伪代码——`for (Order o : orders.findByStatus("REFUNDED")) { if (o.refundedAt > lastCheckpoint && !redis.hasKey("refunded:"+o.orderNo)) { redis.incr(stockKey(o)); redis.set("refunded:"+o.orderNo,"1"); } }`（幂等靠 refunded 标记 key）。
- 思考 5：落库标记 `refundFailed=true` + 进"人工单"列表（一张表/一个 topic），后台告警；人工处理后接口重放补偿。要点：**机器解决不了的单，必须有序地交给人**，而不是默默重试到天荒地老。

## 本节小结
- 超时关单 = `@Scheduled(fixedDelay)` + 按状态扫表 + 复用 cancel（15 行模板，train 已验证）。
- 补偿事务：正向链的每一步预想反向操作；状态机先确认、补偿后执行；残余窗口靠对账兜底。
- REFUNDED 作业 = 白名单加边 + Service 补偿方法 + Controller 端点 + cancel 回库存，共四处，验收标准先行。
- 最终一致性的完整定义：允许窗口，但每个窗口都有"谁在负责把它关上"——定时任务、补偿代码、对账任务，或最终的人工队列。

# N04 · 负载均衡与压测（upstream 轮询实录：10 次 curl，5/5 精确对半）

> **本节要点**：后端扛不住就"再起一台"——但门铃只有一个，怎么把流量分给两台？nginx 的 `upstream` + `proxy_pass http://组名` 三行搞定。本篇把 train 真起两份（8084 / 18084），用 `log_format` 记录每次请求落到谁头上，10 次 curl 循环实测 5/5 对半；再顺手工演一台宕机后 nginx 的自动避让（`upstream=127.0.0.1:18084, 127.0.0.1:8084` 实锤）。
> **前置知识**：N01（反代与 proxy_pass）、零起点-03（进程与端口）。
> **产出**：会写一个最小 upstream 配置组；能用 access.log 证明轮询确实在转；知道默认轮询对"已挂节点"的行为与代价。

## 1. 生活类比与动机：一个窗口排到天黑

### 是什么

**负载均衡**＝单点变集群：同一个业务起 N 份进程（不同端口），门铃（nginx）按名册把请求轮流递。对外仍然是**一个门牌**（9090），扩容对访客完全透明。

### 为什么这么设计

- **横向扩展**：单进程撑不住就加进程、加机器——比"换更牛的服务器"（纵向）便宜且无上限；
- **滚动升级**：一台重启时另一台继续接客，发布不再全站断服；
- **故障隔离**：一台挂了流量自动绕行（本站实测）。

### 前提条件：无状态

train 的"登录态"在 JWT（浏览器自带）与 Redis（余票/锁）里，进程内存里**不存任何会话**——这正是它能随便起两份的原因。若把购物车存进程内存，两台实例就各记各的账，轮询立刻变成"抽盲盒"。**先无状态，再谈集群。**

## 2. 第一步：把 train 真起两份

第二份实例只需**换端口 + 换数据库文件**（命令行覆盖 Spring 配置，jar 一字不改）：

```bash
nohup java -jar backend/train/target/train-1.0.0.jar \
  --server.port=18084 \
  --spring.datasource.url="jdbc:h2:file:/tmp/opencode/train2db;AUTO_SERVER=TRUE" \
  --spring.kafka.consumer.group-id=audit-exp2 \
  > /tmp/opencode/train2.log 2>&1 &
```

实测两条都活着（今天的启动后 3 秒内 200）：

```
$ curl -s -o /dev/null -w "8084: %{http_code}\n"  http://127.0.0.1:8084/api/trips
8084: 200
$ curl -s -o /dev/null -w "18084: %{http_code}\n" http://127.0.0.1:18084/api/trips
18084: 200
```

> **教学注解**：第二份连了**另一个 H2 文件**——所以两台的订单库互不相通。真正的集群共享同一套 DB/Redis/Kafka；这里为了"不污染教学数据"才分库。反代转发本身不关心这些，分不分库不影响本站实验。
>
> **实测小坑（新发现）**：我给了 `--spring.kafka.consumer.group-id=audit-exp2` 想把第二台的审计组隔离，`logs` 里却仍见 `groupId=audit`——参数覆写没生效。于是 18084 真的混进了 `audit` 消费组：Kafka 单分区主题下同一组**分区内只允许一个消费者**，第二台挤进来就触发 rebalance，事件归属在两台间摇摆。**这就是"混进消费组的另一个实例"是真实的多实例行为**——T05 会借同一现象讲"事件被谁消费了"这个悬念。教学上当作免费实战案例：想让实验实例不打扰主链路，要么共享组但接受摇摆，要么干脆单独 topic。

**为什么 Redis 可以共用而 H2 分开**：Redis 的余票 key 是全局的，两台都读写同一份余票反而**更一致**（T04 的分布式锁正因此跨进程有效）；H2 文件库不支持两进程安全并发写同一文件，教学版才分家。换 MySQL 后即可共享（T06 的伏笔）。

## 3. 配置模板：upstream 三件套

```nginx
# 1) 名册：起个组名，把两台列进去
upstream train_cluster {
    server 127.0.0.1:8084;          # 老实例
    server 127.0.0.1:18084;         # 新实例
    # 可选策略：
    # server 127.0.0.1:18084 weight=2;      ← 倾斜派活（新机器强就多接）
    # server 127.0.0.1:19084 backup;        ← 备胎：主力全挂才顶上
    # server 127.0.0.1:18084 max_fails=3 fail_timeout=10s;  ← 连挂3次休10s（默认就是这个）
}

# 2) server 块里把 proxy_pass 指向组名（不再写死单台）
server {
    listen 9091;                    # 教学实验口（正式版是 9090 的 /apitrain/）
    location /apitrain/ {
        proxy_pass http://train_cluster/api/;   # ← 指名册，不指 IP
        proxy_set_header Host $host;
    }
}
```

**升级点只有一个**：`proxy_pass` 的目标从 `http://127.0.0.1:8084` 换成 `http://train_cluster`（组名）。换皮规则（`/apitrain/` → `/api/`）原样继承——N01 的知识无缝复用。

其他可选策略一览（默认轮询，够用就不折腾）：

| 策略 | 写法 | 适用 |
|---|---|---|
| 轮询 | 默认 | 实例等强（本站默认） |
| 加权轮询 | `weight=2` | 实例性能不均 |
| ip_hash | `ip_hash;` | 需要"同一访客粘同一台"（有状态残留时） |
| 备胎 | `backup` | 主力全灭才启用 |

## 4. 动手验证·一：轮询实测——10 次 curl，5/5 对半（今天实录）

光看页面看不出打给了谁（两台返回内容相同）——让 nginx 亲口作证：给 access.log 加上 `$upstream_addr`：

## 5. 工程实录：真实问题与解决——杀掉一台，看门卫绕行（今天实录）

`kill -9` 掉 18084（先从 `ss` 捞 pid，别瞎匹配进程名——`pkill 自杀式匹配`是作者的血泪），再打 6 发：

```
$ P=$(ss -tlnp | grep -w 18084 | grep -oP 'pid=\K[0-9]+' | head -1); kill -9 $P   # 17890 起
$ for i in $(seq 1 6); do curl -s -m3 -o /dev/null -w "%{http_code} " http://127.0.0.1:9091/apitrain/trips; done
200 200 200 200 200 200        ← 客户端视角：全程无感

$ cat /tmp/opencode/lab/lb.log
1789460734.679 upstream=127.0.0.1:8084 status=200
1789460734.687 upstream=127.0.0.1:18084, 127.0.0.1:8084 status=200   ← 亲口招供！
1789460734.697 upstream=127.0.0.1:8084 status=200
1789460734.705 upstream=127.0.0.1:8084 status=200
1789460734.715 upstream=127.0.0.1:8084 status=200
1789460734.724 upstream=127.0.0.1:8084 status=200
```

**逐条解读**：

1. 第 2 行的 `upstream=127.0.0.1:18084, 127.0.0.1:8084` 是**逗号串联**：nginx 先试 18084 → 连接被拒 → **当场换下一台** 8084 → 成功。一次客户端请求，门卫跑了两趟腿。
2. 之后 4 行全是 8084：nginx 给 18084 记了一笔"失败账"（`max_fails` 计数），短期内不再派活给它——**被动健康检查**在起作用。
3. 客户端六个 200：故障被完全吞掉，用户一无所知。

**复现命令底稿（今天实验留下的"可整段贴回"版本）**：

```bash
# 1) 起第二台（独立 DB 文件；group 覆写参数见第 2 节的实测小坑）
nohup java -jar backend/train/target/train-1.0.0.jar \
  --server.port=18084 \
  --spring.datasource.url='jdbc:h2:file:/tmp/opencode/train2db;AUTO_SERVER=TRUE' \
  --spring.kafka.consumer.group-id=audit-exp2 > /tmp/opencode/train2.log 2>&1 &
# 2) 等 200，再哭它
for i in $(seq 1 30); do sleep 1; curl -s -o /dev/null -m2 http://127.0.0.1:18084/api/trips && break; done
# 3) 杀（用 ss 捞 pid，不用 pkill 匹配）
P=$(ss -tlnp | grep -w 18084 | grep -oP 'pid=\K[0-9]+' | head -1); kill -9 $P
# 4) 复跑 6 发并读 lb.log——正常应见逗号串联 + 5 条纯 8084
```

**代价与边界**（诚实工程学）：

- 被动检查是"试了才知道"——若 18084 是**僵死**（端口在、不响应），客户端会先吃一个短超时，nginx 才换手。要"主动探活"得上 `max_fails/fail_timeout` 调参或 nginx plus/三方模块；
- 换手只对**幂等重试**安全。下单这种写操作，nginx 默认只在**连接失败**（没送达）时重试——请求已被后端处理过则不重发，避免重复扣票。这个边界 T03 讲锁时还会回来对齐。

**本实录还包括一个部署纪律的插曲**（代价不小、值得刻进脑子的）：演练结束后我把带新代码的 jar **未先停进程**就 `mvn package` 覆盖了 `target/train-1.0.0.jar`——8084 在跑的 JVM 会**懒加载** jar 里的类，文件已面目全非，下次要加载 `logback` 的类时直接：

```
Exception in thread "http-nio-8084-exec-8" java.lang.NoClassDefFoundError: ch/qos/logback/classic/spi/ThrowableProxy
	at ch.qos.logback.classic.spi.LoggingEvent.<init>(LoggingEvent.java:145)
	...
Caused by: java.lang.ClassNotFoundException: ch.qos.logback.classic.spi.ThrowableProxy
```

随后一次下单 nginx 返回 **504 Gateway Time-out**（Tomcat 线程在 logback 的类加载上炸穿）。修复＝正确姿势：**先 kill 旧进程 → 再 rebuild → 再启动**（或先 `mvn package -o` 到临时目录/复制 jar 后替换指针）。`java -jar` 的 jar 是"运行中不许踩的地"，这比负载均衡本身的教训还要长寿。

## 5.5 故障演练的对照组：主动探活长什么样

5.3 节的被动检查是"试了才知道"。若想**不等用户踩坑**就踢掉坏节点，工业界两条路：

```nginx
# 路线 A：把参数调激进（仍是被动，但反应更快）
upstream train_cluster {
    server 127.0.0.1:8084 max_fails=1 fail_timeout=5s;   # 错 1 次就休 5 秒
    server 127.0.0.1:18084 max_fails=1 fail_timeout=5s;
}

# 路线 B：nginx 开源版没有主动探活，用"备胎 + 脚本"兜
upstream train_cluster {
    server 127.0.0.1:8084;
    server 127.0.0.1:19084 backup;      # 主力全挂，备胎顶上（哪怕它是空壳先顶着 503 界面）
}
```

开源 nginx 的主动健康检查要第三方模块（`nginx_upstream_check_module`）或商业版 nginx plus（`health_check` 指令）。**教学结论**：知道"被动检查的代价 = 首个请求吃到换手延迟"，就知道什么时候该上主动探活——用户量大了、故障要隐蔽了，这一课就得补。

### 5.6 把演练结论写成 runbook（运维交接的姿势）

本节实测可以浓缩成一张"值班卡"：

| 现象 | 诊断命令 | 处置 |
|---|---|---|
| 偶发 502，日志见 `18084, 8084` 串联 | `ss -tlnp \| grep 18084` | 实例僵死：kill 重启；确认 max_fails 生效 |
| 日志全是 `8084` 无 `18084` | 查 18084 进程在不在 | 若在但被拉黑：等 fail_timeout 过期，或 reload 清账 |
| 两台日志流量长期 7:3 | access.log 计数 | 能力不均：检查慢实例（GC？DB 连接池？），必要时上 weight |
| nginx 本身 502 全线 | `nginx -t` + 看 error.log | 配置错或全后端挂：先 `nginx -t` 再查后端 |

**把实测现象翻译成 runbook**，是 N 系列从"懂了"到"能用"的最后一公里。

## 6. 压测的正确姿势与"压测 подумать"

真实压测工具是 `ab`/`wrk`/`JMeter`，教学版用 curl 循环 + 后端日志足以建立直觉。**压测要想清楚三件事（подумать＝先思考再开压）**：

1. **压谁**：压 9091（均衡链路）测的是 nginx 调度；直压 8084 测的是单实例容量——两者数字含义完全不同，混为一谈是压测第一误区。
2. **压多久、多少并发**：10 连发串行只能验"轮询在转"；T06 的 100 线程并发才是"库存会不会被打穿"的验证（答案：不会，实测 10 成功/90 拒绝）。
3. **看什么指标**：成功率、P95 延迟、**对账**（成功数 == 库存消耗数）。只看"没报错"不叫压测，叫自嗨。

今天的 lab conf 底稿（lb.log 的来源骨架，收藏级）：

```nginx
upstream train_cluster {
    server 127.0.0.1:8084;
    server 127.0.0.1:18084;
}
log_format lb '$msec upstream=$upstream_addr status=$status';
server {
    listen 9091;
    location /apitrain/ {
        access_log /tmp/opencode/lab/lb.log lb;   # 单独的账本，别混进主 access.log
        proxy_pass http://train_cluster/api/;
        proxy_set_header Host $host;
    }
}
```

**均衡效果的量化说法**：本站 10 次循环 5/5（偏差 0）；并发场景下轮询的偏差会略增（处理快的实例先腾出手接下一单），但长期统计仍趋向对半——这是 weight 概念存在的意义：**能力越强，名册上占比越高**。

### 6.1 与 T06 的接力：均衡压测 vs 对账压测

本篇的 10 连发与 T06 的 100 线程是**两种不同的压**，别混淆：

| | 本篇（N04） | T06 |
|---|---|---|
| 目标 | 验证**调度**（轮询在转、故障绕行） | 验证**正确性**（库存不被打穿） |
| 观察物 | access.log 的 upstream_addr | 成功数/库存数/H2 单数三本账 |
| 串行还是并发 | 串行循环（看节奏） | 100 线程并发（看竞争） |
| 通过标准 | 5/5 对半 + 故障全 200 | 对账三律全咬合 |

一句话：N04 验"分活公平吗"，T06 验"分活的过程中账乱不乱"。**先公平，再正确**——两个都绿，集群才算真毕业。

### 6.2 压测的纪律清单（开压前逐条打钩）

1. [ ] 环境独占吗（没有别人的请求混入计数）？
2. [ ] 基线拍了吗（库存/时间窗口/订单起始 id）？
3. [ ] 压的对象说清了吗（9091 链路 or 8084 单机）？
4. [ ] 对账口径定了吗（哪几本账、怎么过滤时间窗）？
5. [ ] 压完恢复了吗（测试数据清理/库存重置）？

这份清单是 T06 第 2 节的预演——**带纪律的压测才是证据，不带纪律的只是热闹**。

## 7. 自测题（五分钟能答完）

1. `upstream` 组名与 `proxy_pass` 的关系？组名拼错会怎样？
2. 默认轮询下 10 次请求 5/5 对半——若给一台加 `weight=3`，10 次大概率怎么分？
3. 一台实例僵死（端口通但不响应），客户端会经历什么？与"进程直接死"有什么不同？
4. 为什么 train 能随便起两份，而"把购物车存在进程内存里"的服务不能？
5. `upstream=127.0.0.1:18084, 127.0.0.1:8084` 里的逗号是什么意思？

**参考答案**（自测后再看）：

1. `proxy_pass http://组名` 让 nginx 按名册派活；组名拼错 nginx -t 直接报 "host not found in upstream"，起不来——配置期就拦住。
2. 约定 3:1 加权轮询——大概 7/3 分（weight=3 的每轮接 3 单，另一台接 1 单）。
3. 僵死：客户端先等连接/响应超时，nginx 才换手（首个受害者吃延迟）；进程死：连接拒绝秒失败，nginx 换手几乎无感。
4. train 无状态（JWT 在浏览器、余票在 Redis、订单在 DB）；购物车在内存 = 两台各记各的账，用户轮到另一台就"丢了购物车"。
5. 同一次客户端请求 nginx 先试了 18084（失败）、再试 8084（成功）——一单两趟腿的亲口招供。

## 9. 常见坑清单

| 症状 | 根因 | 修法 |
|---|---|---|
| 502 比预期多 | 某台僵死（被动检查试错慢） | `max_fails/fail_timeout` 调参，或上主动探活 |
| 用户时而登录失效 | 实例间 JWT secret 不一致 | 两份实例共用同一 `app.jwt.secret`（本项目同 jar 同配置，天然一致） |
| 轮询"不准"（3/7 开） | 有请求失败触发了换手重试 | 看日志里的逗号串联（如本站 5.3 实锤） |
| 两台数据"精神分裂" | 会话/数据在进程内存或分库 | 落 Redis/共享 DB，坚持无状态 |
| upstream 组名解析失败 | `proxy_pass http://组名` 拼错组名 | 组名与 proxy_pass 严格一致 |

---

## 10. 本节小结

- `upstream` 名册 + `proxy_pass http://组名` ＝ 三行上集群；换皮规则继承 N01。
- 实测轮询：10 发 5/5 精确对半（log_format 里 `$upstream_addr` 亲口作证）。
- 故障演练：杀一台后 6 发全 200；日志里 `18084, 8084` 逗号串联＝门卫当场换手，随后被动拉黑。
- 集群前提是无状态：train 的状态全在 JWT/Redis/Kafka，进程内存干净如新。
- 压测先 think：压谁、并发多少、对不对账——T06 将用 100 并发 + 对账把这套纪律跑给你看。

# T06 · 防超卖对账：并发抢票的实测（100 并发 / 10 张票 / 成功 10 · 拒绝 90）

> **本节要点**：T 系列的期末考。100 个 Python 线程同一瞬间扑向 10 张票，然后回答一个审计员才会问的问题：**成功数、库存消耗数、H2 订单数、座位号分布——这四本账互相咬合吗？** 本篇给出完整实测：成功 10 / 拒绝 90 / 余票 10→0 / H2 恰好 10 单 UNPAID / 座位 1~10 无重复，超卖率 0%。
> **前置知识**：T03（七步链路）、T04（10 线程版实验）。
> **产出**：会跑一次带对账的并发压测；掌握"对账三律"（成功数==消耗数、单数==成功数、座位无重复）；知道这套 Redis 方案的边界与通往 MySQL 的路。

## 1. 生活类比与动机：演唱会门票的账目审计

### 是什么

压测不是"把系统打挂"，是**带着账本去打**：打之前拍下库存基线，打完数三个数——系统说卖出几张（HTTP 200 数）、库存少了几张（DECR 账）、登记簿写了几行（H2 单数）。**三个数对不上，系统就有 bug**；对得上，才敢说"防超卖"三个字。

### 为什么这么设计

- T03~T05 每一篇都只验了链路的**局部**（锁、守卫、关单）；
- 真实事故（超卖）只在**高并发**下现形——100 线程同毫秒开火才能打出竞争窗口；
- 对账是唯一不依赖"看代码觉得对"的证据——**数字 > 直觉**。

## 3. 压测脚本全件（rush.py，可整段复制）

```python
import threading, json, urllib.request, urllib.error

TOK = "eyJhbGciOiJIUzM4NCJ9...."            # ← 换成你自己的 token
results, lock = [], threading.Lock()

def grab(i):
    r = urllib.request.Request(
        "http://127.0.0.1:9090/apitrain/bookings",
        data=json.dumps({"tripId": 2}).encode(),
        method="POST",
        headers={"Content-Type": "application/json",
                 "Authorization": "Bearer " + TOK})
    try:
        with urllib.request.urlopen(r, timeout=15) as resp:
            body = json.loads(resp.read())
            with lock: results.append(("OK", body["orderNo"]))
    except urllib.error.HTTPError as e:
        with lock: results.append(("REJ", e.code))

ts = [threading.Thread(target=grab, args=(i,)) for i in range(100)]
[t.start() for t in ts]
[t.join() for t in ts]
ok = sum(1 for r in results if r[0] == "OK")
rej = len(results) - ok
print("前5个结果:", results[:5])
print(f"成功 {ok} / 拒绝 {rej}")
```

与 T04 的 grab.py 只有三处不同：线程数 100、timeout 放宽到 15s（100 线程排队，Tomcat 线程池要轮转）、结果带完整 orderNo（对账要用）。

### 4.1 压测输出

```
$ redis-cli -p 6379 set train:trip:2:stock 10

$ python3 rush.py
```

**读前三行**：前 5 个结果全 REJ——**results 列表按线程完成顺序乱序**，不代表最先发出的人失败（他们大多撞在锁上）。真实分布要看汇总：10 OK + 90 REJ。

### 4.3 对账三律逐条核验

| # | 对账律 | 实测 | 判定 |
|---|---|---|---|
| 1 | **成功数 == 库存消耗数** | 10 == (10 - 0) | ✅ |
| 2 | **H2 订单数 == 成功数** | 10 == 10 | ✅ |
| 3 | **座位号无重复且连续** | MIN=1, MAX=10, DISTINCT=10 | ✅ |

**附加核验**：Redis seq 号账（`GET train:trip:2:seq` = `10`）——发号 10 次，与单数一致。四本账（HTTP 账/库存账/单账/号账）全部咬合，**超卖 0 张、少卖 0 张**。

> **"少卖"也是事故**：若守卫写错（比如 DECR 后直接 throw 不还票），库存会被并发打到负数，下次 set 基线前账面"凭空少票"。本实测 stock 归零且与成功数精确相等——还票路径（T03 :54）同样经住了 90 次拒绝的轰炸。

### 4.4 实验的"事后 5 分钟"：对账结果不是永恒的

压测结束 ≠ 数字定格。同一批 10 张 UNPAID 单，在实验 5 分钟后被 T05 的关单机器人**整体收走**（时间已过红线）：

```
sql> SELECT STATUS, COUNT(*) AS N FROM BOOKINGS WHERE TRIP_ID = 2 GROUP BY STATUS;

STATUS    | N
CANCELLED | 10
(1 row, 4 ms)

$ redis-cli -p 6379 get train:trip:2:stock
"10"                  ← 机器人回补 +10：0 → 10
```

**这不是对账失败，是账本继续滚动**：单账从 UNPAID 变 CANCELLED（关单）、票账 +10（回补）——两本账**同步地**动了。对账律 1 的正确读法是**静止窗口内**核验（压测刚结束、关单未到时），或者更稳健的**双向跟踪**：stock 变化量 = UNPAID 增量 + （PAID - CANCELLED）增量。教学版用前者（快），生产对账任务用后者（可跑在任意时刻）。**这也是"余票账要记账本流水而不是拍快照"的原因**——拍快照永远在和定时任务赛跑。

## 5. 为什么这套方案不超卖：机制归因

100 并发 10 张票零超卖，是**三道防线**叠加的结果：

| 防线 | 位置 | 挡住什么 |
|---|---|---|
| ① 分布式锁 | `setIfAbsent` NX + TTL（T03 :42） | 临界区互斥：同一瞬间只有 1 个线程在七步链路里 |
| ② 原子 DECR | Redis 单线程（T03 :49） | 就算锁失守，扣减也不会把 1 张票发两人 |
| ③ 负数守卫 + 还票 | stock < 0 则 INCR + 拒绝（T03 :53） | 超发的那次扣减被原样撤销，账面诚实 |

**防线 ②③ 就足够防超卖**（demo-counter 的 /seckill 没有锁也零超卖）——那锁是干嘛的？**锁保的是"扣票→发号→落库"作为整体不被交错**（账目一致性），并顺带把"已售罄"的拒绝提前到锁口（省掉无谓的 DECR）。**没有锁的超卖为零但有账乱；没有 DECR 守卫的锁才有超卖**——两者职责不同，缺谁都知道少了什么。

## 6. 压测中的观察项（比"过/不过"更有料）

1. **拒绝延迟极低**：90 个 REJ 大多在锁口就被弹回（"手速太快"），耗时 ≈ 一次 Redis 往返——**快速失败**是好设计的标志，别让注定失败的请求占着 Tomcat 线程；
2. **成功请求耗时略增**：100 线程 vs Tomcat 默认 200 线程池——本实验线程够用；并发再上一个数量级，排队延迟会先于系统崩溃出现；
3. **热点 key 单点**：所有 DECR 挤在同一个 key 上，Redis 单线程成了唯一闸口——吞吐上限 ≈ Redis 的 10 万级 QPS，教学绰绰有余；工业级优化（分段库存、Lua 合并扣减）是下一个世界的事；
4. **关单的时序干扰**：实验窗口若撞上 15s 扫描（T05），回补会让"余票零"变成"余票一"——**对账前先看时间窗口**，这是本系列第三次撞见的运维干扰项（T02 一次、T04 一次）。

## 7. 通往 MySQL：这套方案的生产化路线图

教学版在"对账通过"处收官，但诚实的工程师要画出边界与下一步：

| 教学现状 | 生产隐患 | 生产化路线 |
|---|---|---|
| H2 文件库，两实例分库（N04） | 不共享数据、无高可用 | 换 **MySQL**：共享单库起步，数据一致性问题从"文件"变"事务" |
| Redis 是余票唯一真身 | Redis 挂 = 余票全失（无持久化） | DB 存权威余票，Redis 做**缓存 + 原子层**，定时对账（本站脚本就是雏形） |
| 锁值固定 "1" | 误删他人锁（T03 5.3） | 随机值 + Lua 校验，或 Redisson 看门狗 |
| "手速太快"返回 500 | 前端无法区分错误类型 | 429/409 + 全局异常（S07） |
| 补偿残局（车次不存在/落库失败） | 库存悬空（T03 4.4 表） | 扣票后步骤包 try/catch 补偿 INCR |
| 事件可能丢（Kafka 发送失败） | 审计断流 | outbox 模式：先落本地事件表，再异步发 |

**一句总纲**：教学版用"Redis 原子 + 手写补偿"换来了**零依赖的并发正确性**；生产版用"MySQL 事务 + 缓存 + 对账定时任务"换**持久与可恢复**——取舍不同，对账纪律不变。

### 7.5 一遍对账 SQL 工具箱（收藏级）

把本系列用过的对账查询汇成一页，实验时照抄：

```sql
-- ① 各车次账面总览：状态分布（对账律 2 的分车次版）
SELECT TRIP_ID, STATUS, COUNT(*) AS N
  FROM BOOKINGS GROUP BY TRIP_ID, STATUS ORDER BY TRIP_ID;

-- ② 某车次的座位号核验：数量、范围、唯一性（对账律 3）
SELECT COUNT(*) AS ORDERS, MIN(SEAT_NO) AS MIN_SEAT,
       MAX(SEAT_NO) AS MAX_SEAT, COUNT(DISTINCT SEAT_NO) AS DISTINCT_SEATS
  FROM BOOKINGS WHERE TRIP_ID = 2 AND STATUS = 'UNPAID';

-- ③ 时间窗过滤：只看本批实验的单（防关单机器人搅局）
SELECT COUNT(*) AS N FROM BOOKINGS
  WHERE TRIP_ID = 2 AND CREATED_AT > CURRENT_TIMESTAMP - INTERVAL '10' MINUTE;

-- ④ 审计事件流：按订单号拉全量 phase（T05 的证据链）
SELECT CONTENT FROM AUDIT_LOGS
  WHERE CONTENT LIKE '%1f160bfa%' ORDER BY ID;
```

配套的 Redis 侧三连：

```bash
redis-cli get train:trip:2:stock    # 票账（余票）
redis-cli get train:trip:2:seq      # 号账（累计发号）
redis-cli exists train:trip:2:lock  # 锁账（捡漏：该还的锁没还就是泄漏）
```

**四本账 + 一页 SQL**——这就是本系列攒下的"审计员工具箱"，拿去任何一个 Redis+DB 的项目都能直接开工。

3. 关单机器人（回补改 stock，4.4 节实锤）、Kafka 消费者（慢 1~2 秒）、其他用户的真实请求（污染计数）。

## 9. 常见坑清单（呼应 N04 的 runbook 姿势）

| 症状 | 根因 | 修法 |
|---|---|---|
| 成功 11 张 | 基线没重置（上轮实验留了余票） | 每轮实验前 `set` + `get` 双确认 |
| 对账差 1~2 单 | 实验撞上关单回补/别的用户在买 | 独占环境跑；用 orderNo 时间窗过滤 |
| 大量 Connection reset | 100 线程打爆 backlog | 降并发或加 timeout 重试 |
| H2 shell 对账时卡死 | AUTO_SERVER 抢锁 | shell 与应用用同一 url 参数（T01 姿势） |
| 拒绝全是 401 | token 2 小时 TTL 过期 | 现拿现用（`ttl-minutes: 120`） |
| "压测通过"但不敢上生产 | 没测边界（锁超时/Redis 挂） | 故障演练（N04 的杀实例戏码搬到 Redis） |

## 本节小结
- 实测定案：**100 并发 / 10 张票 → 成功 10、拒绝 90、余票 10→0、H2 UNPAID 10 单、座位 1~10 无重复、超卖 0**。
- 对账三律：成功==消耗、单数==成功、座位无重复——外加 seq 号账，四账咬合才算闭环。
- 零超卖的三道防线：锁（互斥）+ DECR（原子）+ 负数守卫（还票）；三者职责不同，不是冗余。
- 压测的附加值在观察项：快速失败、热点 key 上限、关单时序干扰——比"过/不过"的二元结论值钱。
- 对账结果是**静止窗口内的快照**：5 分钟后机器人把 10 张 UNPAID 收成 CANCELLED、stock 回补到 10——账本继续滚动但两账同步动，流水思维 > 快照思维（4.4 节）。
- 工具箱随身带：四本账 + 一页 SQL（7.5 节），任何 Redis+DB 项目直接开工。
- 通往生产：MySQL 权威账 + Redis 缓存层 + 定时对账 + outbox——对账纪律是唯一不变的主角。

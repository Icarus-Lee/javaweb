## 1. 生活类比与动机：同一餐厅的三套账

接着 K01 的点外卖场景：一张新单出现后，**三方各记各的账**——

- **财务**（audit 组）：看见"有新单了"就盖章入流水；
- **商家**（dispatch 组）：只看 PAID 的单，给骑手派工；
- **路过的管理员**（console-consumer 临时组）：从最初的一条听到最新的，只为旁观。

**同一串消息，多套人马、各自走一遍**——这就是**组间复制（广播）**。反过来，**同一组内的两三个消费者**（财务部两个柜员）**不会同时处理同一张单**——Kafka 把巷道分给组内成员，一人至少一条巷；这就是**组内分工**。**语义上，一个组=一个人**：组间是发布-订阅，组内是负载均衡。

## 2. 收信入口：@KafkaListener 真码走查

### AuditConsumer（train 的审计台——真码全文）

```java
// 审计台：消费订单事件并盖戳入库 —— 展示"生产者/消费者解耦"效果。
// 消费者不在请求线程里：下单接口毫秒级返回，审计慢慢来。
@Component
public class AuditConsumer {
    private final AuditLogRepo repo;

    public AuditConsumer(AuditLogRepo repo) { this.repo = repo; }

    @KafkaListener(topics = OrderEventProducer.TOPIC, groupId = "audit")
    public void onOrder(String payload) {
        AuditLog log = new AuditLog();
        log.topic = OrderEventProducer.TOPIC;
        log.content = payload;
        log.createdAt = Instant.now();
        repo.save(log);
        System.out.println("[audit] " + payload);
    }
}
```

六行读法：

1. **`@Component`**：bean 上岗，IoC 门派照旧。
2. **`@KafkaListener(topics = ..., groupId = "audit")`**：**收哪条 topic、作为哪个组的人**——两个语义都写在注解上。topics 引的是生产者那个常量，**名字永远同源**。
3. **`onOrder(String payload)`**：一个普通方法，不实现任何接口；Spring 串联"收消息→调方法"。收进来的是 producer 手拼的那个 JSON 字符串本体。
4. **入库盖章**：audit 表是一份"事件流水"——K01 所说"业务事实在 DB、事件只是广播"的落点。
5. **`[audit]` 日志**：肉眼可见的消费痕迹（S09 观测思想）。
6. **不在请求线程**：监听器跑在 container 线程（日志里 `ntainer#0-0-C-1` 那种命名），**下单接口毫秒级返回**，审计慢慢来——解耦+异步的真实兑现。

### DispatchConsumer（takeaway 的派单员——真码全文）

```java
// 派单员：只有已支付（PAID）的事件才会被派单；CREATED 事件直接忽略（防止"白派单"）。
@Component
public class DispatchConsumer {
    private final OrderRepo orders;

    public DispatchConsumer(OrderRepo orders) { this.orders = orders; }

    @KafkaListener(topics = OrderEventProducer.TOPIC, groupId = "dispatch")
    @Transactional
    public void onOrder(String payload) {
        // 简化 JSON 解析：找 orderNo 与 phase（教学场景允许这种"抠字段"方式）
        String orderNo = extract(payload, "orderNo");
        String phase = extract(payload, "phase");

        Order o = orders.findByOrderNo(orderNo).orElse(null);
        if (o == null || !"PAID".equalsIgnoreCase(phase) || !"PAID".equals(o.status)) return;
        if (o.status.equals("PAID")) {
            o.status = "DISPATCHED";
            o.riderId = 9000L;          // 模拟事由：调度中心指派骑手 9000
            o.dispatchedAt = Instant.now();
            orders.save(o);
            System.out.println("[dispatch] order=" + orderNo + " -> 派给骑手 9000");
        }
    }

    private String extract(String json, String field) {
        int i = json.indexOf("\"" + field + "\":\"");
        if (i < 0) return null;
        int start = i + field.length() + 4;
        int end = json.indexOf('"', start);
        return end > 0 ? json.substring(start, end) : null;
    }
}
```

与 AuditConsumer 的三个差异点：

1. **groupId="dispatch"、topic 是 takeaway 自己的** `takeout-order-events`（同 `OrderEventProducer.TOPIC` 常量）——**另一个业务、另一条频道、另一个组**。
2. **`@Transactional`**：DB 写包住；K05 会讲它在"消费失败重试"里的角色。
3. **三重门**（K05 主场）：假单 return、phase 不是 PAID 的 return、状态机不在 PAID 点的 return——**事件重放也拦得住**。

## 3. 组的两重身份：分工 vs 广播

### 组内分工（组内 ≥2 人时）

Kafka 以**巷道（partition）为单位**分配：一条巷同一时刻只交给组内一个人；巷数少于人数时，多出来的人轮空（不重复消费、也不闲消费）。takeaway 日志里能见到真实的再平衡痕迹（本次起停实录）：

```
... [ConsumerRebalanceListenerInvoker] Revoke previously assigned partitions takeout-order-events-0
... KafkaMessageListenerContainer    : dispatch: partitions revoked: [takeout-order-events-0]
```

读法：消费者加入/退出时"吊销 + 重新分巷"——**组内分工的日志显影**。单人组也走这流程，只是"一人领尽一巷"。

### 组间广播（不同组各走一遍）

**硬证据**：dispatch 已消费到某处，而**一个全新的组**照样从 0 把整条 topic 走一遍——**消息不会因为一个组读完就消失**（迁移：commit 挂在组名上，消息在 topic 里）。现场实录（临时组 cross 验证）：

```
$ timeout 12 env KAFKA_HEAP_OPTS="-Xmx64M" tools/kafka/bin/kafka-console-consumer.sh \
    --bootstrap-server 127.0.0.1:9092 --topic takeout-order-events \
    --group k04-tempdemo --from-beginning --timeout-ms 9000 2>/dev/null | head -3

{"orderNo":"1b5bdcd2-be8a-4752-8b6f-735339b53d03","dishId":1,"qty":1,"phase":"CREATED"}
{"orderNo":"5bfbe98e-96e8-4ea6-8e9c-27bb9a919d4e","dishId":1,"qty":1,"phase":"CREATED"}
{"orderNo":"8764a023-75cb-401a-88fd-6f2b5e2a085b","dishId":1,"qty":1,"phase":"CREATED"}

$ env KAFKA_HEAP_OPTS="-Xmx64M" tools/kafka/bin/kafka-consumer-groups.sh \
      --bootstrap-server 127.0.0.1:9092 --describe --group k04-tempdemo

GROUP         TOPIC                  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
k04-tempdemo  takeout-order-events   0          10              10              0    -            -
```

读证：**k04-tempdemo 是个新组**，照样从头走完（offset 到 10）——**dispatch 组早已吃完同样的十条**，两组互不干扰。**组间广播坐实。**

一条细则：`--from-beginning`（从头读）与不带（默认：按组位移接着读）的差异全由**组身份**决定——**组名决定从哪儿开始读**。

### audit 与 dispatch 两张真账

```
--- audit ---
GROUP   TOPIC               PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
audit   train-order-events  0          5               5               0    consumer-audit-1-...

--- dispatch ---
GROUP    TOPIC                   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
dispatch takeout-order-events    0          10              10              0    consumer-dispatch-1-...
```

六列逐列读法：

| 列 | 名义 | 要点 |
|---|---|---|
| GROUP | 组名 | 唯一身份；同一 topic 可被多组同时消费 |
| TOPIC | 听哪条 | audit 对 train-order-events、dispatch 对 takeout-order-events |
| PARTITION | 巷 | 0（单巷教学） |
| CURRENT-OFFSET | 提交进度 | 组"读到哪儿了"，存 brokers 的 `__consumer_offsets` |
| LOG-END-OFFSET | 队尾 | broker 端最新序号 |
| **LAG** | 堆积 | LOG-END − CURRENT（0 = 追平；大 = 堆积，K06 主场） |

**读证一句话**：audit 5/5、dispatch 10/10，**双双 LAG 0**——两组都完全追平。K06 会亲手造一次堆积看 LAG 的波动。

## 4.5 工程实录：踩坑与修复——重放的大动干戈：reset-offsets 的两道闸与"组身份即进度"实测

**故事：想把 dispatch 组重放一遍，第一锤就被 Kafka 拒了。**

背景：写作当日实录的真实操作——想验证"组位移回退 → 重复消费"的完整链路，直接对**在线**组跑 reset（当时 dispatch CURRENT-OFFSET=6、组状态 Stable）：

```
$ tools/kafka/bin/kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 \
    --group dispatch --reset-offsets --to-earliest --topic takeout-order-events --execute 2>/dev/null

Error: Assignments can only be reset if the group 'dispatch' is inactive,
but the current state is Stable.
```

**定位三步**：① 报错直译"组必须 inactive"——组里有活人（CONSUMER-ID 非 `-`）时位移被消费者持续提交，**改了也白改**（下一轮 poll 又提交回去）；② `--describe` 看 CONSUMER-ID 列，非空即 Stable；③ 治法：**把消费者停机**（`kill $(cat logs/takeaway.pid)` → 8085 下线）→ 再 describe，CONSUMER-ID 变 `-`、组进 Empty：

```
GROUP    TOPIC                  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  CONSUMER-ID
dispatch takeout-order-events   0          6               6               0    -       -
```

**第二锤（组 inactive，这次放行）**：

```
$ tools/kafka/bin/kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 \
    --group dispatch --reset-offsets --to-earliest --topic takeout-order-events --execute 2>/dev/null

GROUP           TOPIC                  PARTITION  NEW-OFFSET
dispatch        takeout-order-events   0          0

（再查：）
dispatch takeout-order-events   0          0               6               6    -       -
```

**LAG 从 0 变 6**——6 条历史事件全部变成"待处理"，这就是"堆积"的制造方法（K06 的手造 LAG 同款）。

### 重启消费者：重放收场，guard 截断（真账）

rebalance 痕迹（takeaway.log 真行）：

```
... KafkaMessageListenerContainer : dispatch: partitions assigned: [takeout-order-events-0]
```

重放期间 `[dispatch]` 输出（`uniq -c` 后）：

```
1 [dispatch] order=5dde5216-… -> 派给骑手 9000
1 [dispatch] order=87a1e1b5-… -> 派给骑手 9000
1 [dispatch] order=6dc4d21d-… -> 派给骑手 9000
```

读证两条：

1. **重复被截断**：5dde/87a1 两单的 PAID 事件重放来了，但 H2 里它们已是 DISPATCHED——DispatchConsumer.java:26 那行三重门 `if (o == null || !"PAID".equalsIgnoreCase(phase) || !"PAID".equals(o.status)) return;` 把重放**无声截回**，`uniq -c` 显示**每单只有 1 行**——不出现第二行就是幂等的"数字证据"。
2. **还账是意外之喜**：6dc4d21d 这单此前状态停在 PAID（K01 实录的"窗口漏派"单），重放把这笔**合法补派**了一次（仅一次）。**状态机 guard 的能力半径**：重复消费 → 无害；漏消费 + 有重放 → 可补。这就是"幂等消费 + 可重放"组合的真正卖点的工程实证。

### 修复方法论（事故→ 工具链）

| 想做的事 | 正确姿势 | 直接禁忌 |
|---|---|---|
| 组位移重放 | 停消费者 → reset（`--execute`）→ 起 | 对 Stable 组 reset（Error: inactive 才行） |
| 只重放最近 N 条 | `--to-datetime` / `--shift-by -N` | `--to-earliest` 全量（表大的话重放分钟级） |
| 防误伤 | 先 `--dry-run` 看 NEW-OFFSET 预览 | 直接 `--execute`（不可逆动作无预演） |
| guard 兜底 | 重放前确认消费端幂等（K05 三门） | 业务不幂等就敢 reset（= 事故） |

**一句话**：**组身份即进度**——reset 改的是"这个组读到哪儿了"，消息本体分毫不动；但要动进度，先绕开"活组"与"未幂等业务"两根雷管。

## 7. 参考答案

**练习 1**（实录形态）：audit 5/5 LAG 0、dispatch 10/10 LAG 0、临时组 10/10 LAG 0。LAG=0 表示两组各自追平；临时组同样"走完一整遍"——组间复制实证。

**练习 2**（骨架代码）：

```java
@KafkaListener(topics = OrderEventProducer.TOPIC, groupId = "boss")
public void onOrder(String payload) {
    System.out.println("[boss] " + payload);
}
```

实测：boss 组从 0 起走一遍，`[boss] {...}` 日志出现；`--describe` 三组并列同 topic——**组间广播的第三根证**。

**练习 3**（口径）：单 partition（单巷）时，同组两消费者只有一人能分配到巷，另一人轮空等待；若 topic 建有两条巷，则一人一巷、并行消费。**分工单位是巷道，不是消息条数**——扩巷道才是扩消费并行的正路。

**练习 4**（对照实录）：

```
$ curl -s "http://127.0.0.1:8084/api/bookings/audits?n=3"
[{"id":6,"topic":"train-order-events","content":"{\"orderNo\":\"2d4bcba1-...\",\"phase\":\"PAID\"}",...}, ...]
```

Kafka topic 里的 PAID 事件 与 H2 audit 表的同一事件同账——**"事件只是广播，事实在 DB"**的双端落地。

## 8. 本节小结

- **@KafkaListener** = topics（收哪频道）+ groupId（作为哪个组的人）+ 方法体（payload 原文处理）；Spring 代管监听循环。
- **组的两重身份**：**组间广播**（不同组各走一遍：audit / dispatch / 临时组三账并存）、**组内分工**（以巷道为单位，一巷一人）——**一个组 ≈ 一个身份**。
- **对账偏移量表**：`--describe` 六列齐出——CURRENT / LOG-END / **LAG**；audit 5/5、dispatch 10/10 皆 LAG 0；临时组从 0 走一整遍证实组间复制。
- **下一站预告**：LAG 的波动、重复消费的代价与防法——K05 的语义三表与幂等三重门。

## 附录 A：@KafkaListener 常用参数速查

| 参数 | 含义 | 本项目哪些地方见过 |
|---|---|---|
| topics | 听哪条频道（可数组） | `OrderEventProducer.TOPIC` 常量 |
| groupId | 作为哪个组的人 | audit / dispatch |
| concurrency | 组内并发消费者数（教学默认 1） | —— |
| autoStartup | 启动即监听（默认 true） | —— |

写法心得：**groupId 已在 yml 配时可以不写注解参数**，但同应用多 listener 各归各组时**注解里直填更醒目**——**audit 的 yml 里写 audit、注解里也写 audit**，双保险但同源。

## 附录 B：--describe 六列的"排障怎么用"

| 症状 | 看哪列 | 结论 |
|---|---|---|
| 消费者疑似掉了 | CONSUMER-ID 列为空 | 组内无人、消息没人吃 |
| 处理慢 | LAG 持续增长 | 业务处理跟不上产量 |
| 重启后不消费了 | CURRENT-OFFSET 不动 | listener 没起来/组没加回 |
| offset 飞跃 | LOG-END 突涨 | 上游爆发或测试误发 |
| 完全追上 | LAG 0 | 正常态，无需动 |

## 附录 C：组的命名习惯（一条硬规矩）

- 组名走**业务语义**（audit、dispatch、sms…），**不要写 uuid/demo**——组名要工整可读。
- 与 yml `group-id` 同名：项目级默认组（train 的 yml 是 audit）；多 listener 的组直接在注解里写。
- **不要复用别人的组名**：同组名 = 共享进度——别人的消费进度会变成你的"从这儿接着读"，这就是"组名即身份"的另一面。

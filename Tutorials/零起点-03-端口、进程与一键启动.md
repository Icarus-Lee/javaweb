## 名词卡（重排序：按事故排查顺序）

| 名词 | 人话解释 |
|---|---|
| **端口** | 0~65535 的门牌号，同一门牌同时刻只能一个进程监听 |
| **PID** | 进程身份证号 |
| **探活** | 试某端口有没有人听；本项目用 `/dev/tcp/127.0.0.1/端口` |
| **pid 文件** | 启动时把 PID 写进 `logs/xxx.pid`，stop 脚本靠它精准击杀 |
| **nohup + &** | 后台 + 免疫 SIGHUP（关终端不死） |
| **守护进程** | 长期后台服务、不挂终端；Redis/Nginx 是 |
| **幂等** | 跑一遍和十遍效果一致 |
| **端口冲突** | 两个进程抢门牌，后来者 BindException 起不来 |
| **ss -tlnp** | 看"谁在听哪个门牌"的铁榔头（本文案命） |

## 1. 概念最小人话（每段 ≤3 行）

**为什么需要端口**：8 个服务挤一台机器，快递（TCP 连接）只认"IP+端口"，每个服务必须独占一个门牌：8081 的快递绝不会被 8084 签收；抢门牌 = 后来者启动失败。
**为什么需要 pid 文件**：进程没名字只有 PID。启动时 `echo $! > logs/xxx.pid`（`$!`=最近一次后台进程的 PID），stop-all 读文件精准击杀；**pid 文件丢了进程就成"野进程"**——作者本机真实发生过：手工起的 takeaway 没人写 pid，stop-all 全停唯独它活着。
**为什么需要 nohup**：`&` 只是把进程丢后台，终端一关 SIGHUP 顺着进程树杀下来；nohup 让进程对 SIGHUP 免疫——"守护"两字的含义就在这。

## 2. 真实代码走查：start-all.sh 四段式（行号已核对）

```bash
 1: #!/usr/bin/env bash
 3: set -u                        # 未定义变量直接报错，防手滑
 4: cd "$(dirname "$0")"          # 路径全相对脚本自身
 5: source ./env.sh               # JAVA_HOME、KAFKA_DATA、端口常量
11: redis-cli -p $REDIS_PORT PING 2>/dev/null || ( ... )      ← 先探测后启动＝幂等
--
20: if ! (echo > /dev/tcp/127.0.0.1/$KAFKA_PORT) 2>/dev/null; then
22:   sed -i "s#^log\.dirs=.*#log.dirs=$KAFKA_DATA#" ...       # 数据目录指到项目 data/（可整体删除即重置）
24:     rm -rf "$KAFKA_DATA"                                   # 没格式化过就清空重格式化
30:   nohup "$KAFKA/bin/kafka-server-start.sh" ... > "$ROOT/logs/kafka.log" 2>&1 &
33:   for i in $(seq 1 40); do ... sleep 1 ... done            # Kafka 启动慢给 40 秒窗口
--
38: start_jar() { # name port jarfile
40:   (echo > /dev/tcp/127.0.0.1/$port) 2>/dev/null && { echo "  $name 已在线"; return; }
41:   if [ ! -f "$jar" ]; then echo "  ✗ 缺 jar：$jar（先跑 infra/build.sh）"; return; fi
42:   nohup "$JAVA_HOME/bin/java" -jar "$jar" > "$ROOT/logs/$name.log" 2>&1 &
43:   echo $! > "$ROOT/logs/$name.pid"
44:   for i in $(seq 1 40); do (echo > /dev/tcp/127.0.0.1/$port) ... && break; sleep 0.5; done
45:   ... && echo "  $name: up ($port)" || echo "  ✗ $name 启动失败，看 logs/$name.log"
49: start_jar demo-todo 8081 ...
55: start_jar train    8084 ...
--
59: echo "== 4) Nginx（静态站 + 反代）=="
60: "$ROOT/infra/nginx-reload.sh"     # 生成 nginx.conf → nginx -t → 有 pid 热重载，否则冷启
```

看点逐条：
1. **第 40 行是剧情核心**：探活只看"端口有没有人"，不看"来的人是不是那个 jar"。这个盲点被实录 3.1 现场利用。
2. **第 42~44 行的启动三件套**：nohup 后台起、日志进 logs/、**pid 写盘**、轮询等端口（40×0.5s=20 秒窗口）。每个 jar 的启动都是这条流水线，一个函数复用五次。
3. `/dev/tcp` 是 bash 内建彩蛋：往它写＝开一条 TCP 连接；写得进＝门牌有人。
4. **第 41 行"缺 jar"分支**：先探活再兜底报"少 jar"，把"没 build"与"起不来"两种安静死法分开。
5. stop-all（25 行）反向操作，顺序讲究：**先停业务（后端）→ 再停门面（nginx）→ 再停中间件（kafka→redis）**——先客户端后服务端，否则客户端会疯狂 Connection refused 刷屏。

```bash
# infra/stop-all.sh（节选）
 8: for name in demo-todo demo-chat demo-counter train takeaway; do
 9:   if [ -f "$ROOT/logs/$name.pid" ]; then          ← 眼睛
10:     pid=$(cat "$ROOT/logs/$name.pid")
11:     kill "$pid" 2>/dev/null && echo "  $name 已停" || true
12:     rm -f "$ROOT/logs/$name.pid"
17: [ -f "$ROOT/infra/nginx/run/nginx.pid" ] && nginx -s quit -c ...
21: "$KAFKA/bin/kafka-server-stop.sh" >/dev/null 2>&1
24: redis-cli -p $REDIS_PORT shutdown nosave
```

`infra/env.sh`（15 行，总务备忘录）：

```bash
 3: export JAVA_HOME=/usr/lib/jvm/java-21-openjdk
 8: KAFKA="$ROOT/tools/kafka"
 9: KAFKA_DATA="$ROOT/data/kafka/kraft"
10: REDIS_PORT=6379
11: KAFKA_PORT=9092
15: mkdir -p "$ROOT/data" "$ROOT/logs"
```

## 3. 工程实录：人为 8081 端口被占，再用 start-all → 现场报错与 `ss -tlnp` 诊断

### 3.1 写错的人：抢占 8084，start-all 骗你"已在线"

```bash
# ① 停掉真 train，用 Python 占住 8084
$ kill $(cat logs/train.pid) && rm -f logs/train.pid; sleep 2
$ nohup python3 -m http.server 8084 --bind 127.0.0.1 --directory /tmp >/dev/null 2>&1 &
$ ss -tlnp | grep ':8084 '
LISTEN 0  5    127.0.0.1:8084   users:(("python3",pid=136271,fd=3))

# ② 跑 start-all：它只看"端口活着"，满脸真诚地骗你
$ bash infra/start-all.sh
  == 3) 后端 ×5 ==
  demo-todo 已在线（8081）
  demo-chat 已在线（8082）
  train 已在线（8084）           ← 🔥 不是 train！是你刚起的 Python！
  takeaway 已在线（8085）

# ③ smoke 现场抓包（验收员不认端口只认业务）
$ python3 infra/smoke.py
  ✓ train 注册 / ✓ train 登录+JWT        ← H2 里还查得到，业务合法
  ✗ 车次列表 (code=-1, want=200) timed out  ← "正主缺席，冒名顶替失灵"处全炸
  ✗ 支付 (code=500,...)
  ...
smoke: 21 通过 / 1 失败∩（全部指向 train 链路）
```

这就是**幂等脚本的经典漏洞：探活只证明"门牌有主"，不证明"主人是你家的"**。
诊断命令马上施工现场：

```bash
$ ss -tlnp | grep -E ':(808[1-5]|9090|6379|9092) '
LISTEN 0  5   127.0.0.1:8081   users:(("python3",pid=136587,fd=3))    ← 补 8081 版现场，比谁案例都好
LISTEN 0  100 *:8082          users:(("java",pid=123738,fd=9))       ← 真·Spring Boot 的样子
LISTEN 0  511 0.0.0.0:6379    users:(("redis-server",pid=124252,fd=8))
LISTEN 0  511 0.0.0.0:9090    users:(("nginx",pid=124030,fd=5),("nginx",pid=117056,fd=5))
```

- **`-t` TCP、`-l` 监听、`-n` 数字端口、`-p` 进程**；`users:` 一栏直接把 PID 递到你手里。
- nginx 出两行 pid 是 master+worker，正常。

修复与再验证：

```bash
# ① 撤占者的身份证
$ kill 136271   # ← 占 8084 的 python3，或先 kill 136587（占 8081 的那位）
# ② 正主归位：start-all 的探活这回看到空门，走启动分支
$ bash infra/start-all.sh
  train: up (8084)          ← 不是"已在线"而是"up"，这是"真启动"的签名
# ③ 复跑验收
$ python3 infra/smoke.py
smoke: 24 通过 / 0 失败
```

### 3.2 第二现场：Python 抢占"Java 尸体还没凉"的 8081（bind 侧报错）

把 demo-todo 用 pid 击杀后立即起 python，你会看到与上一段不同的视角——**被抢方**的报错（本机实测还原）：

```bash
$ python3 -m http.server 8081 --bind 127.0.0.1 --directory /tmp
OSError: [Errno 98] Address already in use
```

冲突的两头都值得看：**listenhip 侧（ss -tlnp 看谁占着）和 bind 侧（Errno 98）**。另一类"不是 bind 的应用错误"是 Nginx 的报错原声（本机日志 `infra/nginx/run/logs/error.log` 里的真实行）：

```
2026/09/15 09:55:12 [emerg] 123847#123847: bind() to 0.0.0.0:9090 failed (98: Address already in use)
2026/09/15 09:55:12 [emerg] 123847#123847: still could not bind()
```

排障心法口诀：**先 `ss -tlnp`（谁占）、再 `kill` 占者、然后 `start-all` 拉正主、`smoke` 复核**——四板斧，缺一道都会把"假在线"真实物业带到生产。

### 3.3 排浪费一张"诊断命令速查"后收尾（备案用）

```bash
# 谁占这个门牌？（铁榔头第一下）
$ ss -tlnp | grep ':8081 '
# 占着的 PID 最后确认身份
$ ps -p <pid> -o pid,stat,cmd --no-headers
# 后端"安静死法"的日记在哪
$ tail -20 logs/demo-todo.log | grep -aE 'ERROR|Exception|failed'
# 全栈健康总评
$ python3 infra/smoke.py
```

**读法的两条注脚**：
- `users:` 一栏直接把 PID 递到你手里——**"ss 命令才是事故现场的第一把铁榔头"**；
- java 占 8081 时系统可还残着上一轮死亡的 FIN 痕迹（`echo > /dev/tcp` 都可能探到），此时用 `ss -tanp` 看 TIME_WAIT 状态可分辨"活人"和"余温"：

**Netstat 家族对照**（netstat 用户换枪指南）：

| 命令 | 干什么 | 备注 |
|---|---|---|
| `ss -tlnp` | 谁在听哪个门牌+PID | 本机首选 |
| `ss -tanp` | 含连接状态（ESTAB/FIN-WAIT） | 排"半开连接" |
| `lsof -i :8081` | 同上，lsof 视角 | ss 不在时用 |
| `curl -v -m 3` | 应用层自检 | 直接对服务说话 |

## 5. 模式对比 / 选型表

| 手段 | 能看什么 | 好处/坏处 |
|---|---|---|
| `redis-cli PING` | 应用层协议级探活 | 稳（可靠到协议），但只有自带客户端的才有 |
| `/dev/tcp/...` | TCP 层探活 | 零依赖，但只会说"门牌有没有人" |
| `ss -tlnp` | 看 PID+名字 | **事故后现场的正选** |
| pid 文件 | stop 脚本的准确击杀点 | 会过时：PID 被复用就杀错 |
| `ps -p <pid>` | 验 pid 文件真伪 | 免费但需手动 |

## 思考题（本节小结前再列一遍口诀卡）

- 端口 = 门牌（独占，抢掉就 BindException）；
- PID = 身份证；pid 文件 = stop 脚本的眼睛；`ss -tlnp` = 事故现场的铁榔头；
- start-all 套路四步：探活（幂等）→ nohup 后台起 → 轮询等端口 → 写 pid；
- 幂等探活只证明"门牌有主"，不证明"主是你家的"——**业务探针（smoke）才是真验收**。

## 思考题

1. start-all 里 Redis 探活用 `redis-cli PING`，Kafka 却用 `/dev/tcp`，为什么前者能更"聪明"？
2. 为什么 stop-all 先停后端再停 Kafka/Redis？
3. `nginx -s reload` 与 `nginx -s quit` 各对应什么场景？
4. `logs/train.pid` 里的 PID 若已被无关进程复用，stop-all 会怎样？pid 文件方案还缺什么校验？
5. 实录 3.1 里 start-all 说"train 已在线"，smoke 却红了一片——两个探针分别探了什么层？为什么结论完全相反？

## 练习题

**练习 1**：写 5 行小脚本 `probe.sh <port>` 用 `/dev/tcp` 探端口。
**练习 2**：只删 pid 文件（不动 kill）后跑 stop-all.sh，观察 train 是否幸存；用 ps 补找真 PID 精准击杀。
**练习 3**：设一条"自检"的 sha256 不靠谱思路：在 start_jar 里杀掉"已在线"就 return 单机流程，加一步"验证 pid 是 java"（`ps -p <pid> cmd | grep java`）——解释为什么这样能堵实录 3.1 的洞。

### 完整参考答案

**思考 1**：Redis 有自带协议客户端 PING→PONG 语义明确；Kafka 纯 TCP 二进制，没有轻量探针，退到 TCP 层。原则：能用应用层就用，不能就退 TCP。
**思考 2**：后端是中间件的**客户端**，先停客户端可避免其疯狂报错刷屏+丢消息。
**思考 3**：reload=热重读配置不中断服务；quit=优雅退出（等现有请求处理完再走）。
**思考 4**：会误杀无辜进程。缺"身份校验"：工业做法是 pid 文件同时记启动时间、或交给 systemd/supervisor。
**思考 5**：start-all 的探针是 TCP 层（门牌有没有人）；smoke 的断言是**业务层**（发正经 HTTP 问业务）。冒名 http.server 也会回应 TCP，所以 start-all 说"在线"；但它不会回"车次 JSON"，所以 smoke 红——**层级不同结论就不同**，真验收永远要用业务探针。
**练习 1 参考**：

```bash
#!/usr/bin/env bash
(echo > /dev/tcp/127.0.0.1/$1) 2>/dev/null && echo up || echo down
```

**练习 2 参考**：stop-all 第 9 行 `if [ -f ...pid ]` 不成立直接跳过——train 幸存。这正是作者本机真实发生过的事故（takeaway 版）。补救：`ps -eo pid,cmd | grep train-1.0.0.jar` 找到真 PID 写回文件（`echo <pid> > logs/train.pid`）再跑 stop-all，或直接 `kill <pid>`。

**练习 3 参考**：探活分支升级为"探端口 + 验身份"两步（把"端口活"升级为"端口活且主人对"）：

```bash
# start_jar 的探活分支改为"探端口 + 验身份"两步：
pid_list=$(ss -tlnp | grep ":$port " | grep -oP 'pid=\K[0-9]+' | head -1)
if [ -n "$pid_list" ]; then
  ps -p "$pid_list" -o cmd= | grep -q "$(basename "$jar")" \
    && { echo "  $name 已在线（且验证过）"; return; } \
    || echo "  ⚠ $port 被别家占了：$(ps -p "$pid_list" -o cmd=)"
fi
```

原则：**把"端口活"升级为"端口活且主人对"**，冒名顶替者在 ps 面前现形。

## 本节小结
- 端口=门牌（独占），PID=身份证，pid 文件=stop 脚本的眼睛，`ss -tlnp`=事故现场的铁榔头。
- start-all 套路：探活（幂等）→ nohup 后台起 → 轮询等端口 → 写 pid。
- stop-all 顺序：后端 → nginx → kafka → redis，先客户端后服务端。
- 两大事故：端口冲突（`ss`+`logs/*.log`）与 pid 文件丢失（野进程）；四板斧排障：ss → kill 占者 → start-all → smoke。

## 🗂 本站名词卡

| 名词 | 人话解释 |
|---|---|
| **端口** | 一台机器上 0~65535 的"门牌号"，一个门牌同一时刻只能被一个进程监听 |
| **PID** | Process ID，操作系统给每个进程发的身份证号 |
| **前台/后台进程** | 前台进程占着你的终端，你关终端它往往跟着死；后台进程（`&`）脱离终端独立活着 |
| **nohup** | "no hangup"：让进程免疫终端挂断信号（SIGHUP），常与 `&` 连用 |
| **守护进程** | 在后台长期服务、不挂在任何终端上的进程；Redis/Nginx 都是 |
| **pid 文件** | 把启动时拿到的 PID 写进文件，之后 stop 脚本靠它精准定位要杀谁 |
| **端口冲突** | 两个进程抢同一个门牌，后来者 `BindException` 起不来 |
| **探活** | 试探某端口是否有人监听；本项目用 bash 的 `/dev/tcp/127.0.0.1/端口` 技巧 |
| **幂等** | 同一脚本跑一遍和跑十遍效果一样，不会重复起服务 |

## 🧠 概念人话

### 为什么需要端口

一台机器一个 IP，但上面跑着 8 个服务。快递员（TCP 连接）只认"IP + 端口"，所以每个服务必须独占一个门牌：8081 的快递绝不会被 8084 签收。**同一门牌两个进程抢 = 启动失败**，这就是端口冲突。

### 为什么需要 PID 和 pid 文件

"停掉 train 服务"翻译成操作系统语言是"给某个进程发信号"。可进程没有名字，只有 PID。所以 start-all 在启动每个服务时顺手把 PID 写进 `logs/xxx.pid`：

```
42:   nohup "$JAVA_HOME/bin/java" -jar "$jar" > "$ROOT/logs/$name.log" 2>&1 &
43:   echo $! > "$ROOT/logs/$name.pid"
```

`$!` 是 bash 的特殊变量：**最近一次后台启动的进程的 PID**。stop-all 读这个文件精准击杀。⚠️ 真实事故预告：本机实跑时发现 `takeaway.pid` 丢失（进程是手工起的，没人写 pid 文件），结果 stop-all 停了其他 4 个后端、唯独 takeaway 还活着，下次 start-all 打印"takeaway 已在线"直接跳过。**pid 文件 = stop 脚本的眼睛，丢了就成了野进程。**

### 为什么需要 nohup

`java -jar ... &` 只是丢到后台，但进程还挂着"当前终端"的爹。你关掉终端，SIGHUP 顺着进程树杀下来，服务跟着陪葬。`nohup` 让进程对 SIGHUP 免疫——这才是"守护"的含义。

## 🔍 真实代码走查：start-all.sh 全文拆解

`infra/start-all.sh`（65 行）四段式：Redis → Kafka → 后端×5 → Nginx。

### 第 0 段：环境（1~7 行）

```bash
 1: #!/usr/bin/env bash
 3: set -u                        # 用到未定义变量直接报错，防手滑
 4: cd "$(dirname "$0")"          # 切到脚本所在目录（infra/），路径全相对它
 5: source ./env.sh               # 加载公共环境（JAVA_HOME、路径、端口常量）
```

`infra/env.sh`（15 行）是全 infra 脚本共享的"总务备忘录"：

```bash
 3: export JAVA_HOME=/usr/lib/jvm/java-21-openjdk
 7: ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
 8: KAFKA="$ROOT/tools/kafka"
 9: KAFKA_DATA="$ROOT/data/kafka/kraft"
10: REDIS_PORT=6379
11: KAFKA_PORT=9092
15: mkdir -p "$ROOT/data" "$ROOT/logs"
```

### 第 1 段：Redis（9~17 行）——先探测，再启动

```bash
11: redis-cli -p $REDIS_PORT PING 2>/dev/null || (
12:   nohup redis-server --port $REDIS_PORT --daemonize no --save '' ... &
14:   echo $! > "$ROOT/logs/redis.pid"
15:   for i in $(seq 1 20); do redis-cli -p $REDIS_PORT PING ... && break; sleep 0.25; done
16: )
17: echo "redis: $(redis-cli -p $REDIS_PORT PING 2>/dev/null || echo down)"
```

- PING 通 → 短路，`||` 后面整段不执行（幂等的关键）；
- 不通 → 后台起 Redis、写 pid 文件、**轮询等待最多 5 秒**（20 次 × 0.25s）；
- `--save '' --appendonly no`：教学版关掉磁盘持久化，重启即空库。

### 第 2 段：Kafka（19~35 行）——探活换了个姿势

```bash
20: if ! (echo > /dev/tcp/127.0.0.1/$KAFKA_PORT) 2>/dev/null; then
22:   sed -i "s#^log\.dirs=.*#log.dirs=$KAFKA_DATA#" "$KAFKA/config/server.properties"
23:   if [ ! -f "$KAFKA_DATA/cluster.meta.properties" ]; then
24:     rm -rf "$KAFKA_DATA"                       # 没格式化过就清空重格式化
26:     "$KAFKA/bin/kafka-storage.sh" format --standalone --cluster-id "$UUID" ...
30:   nohup "$KAFKA/bin/kafka-server-start.sh" ... > "$ROOT/logs/kafka.log" 2>&1 &
32:   echo $! > "$ROOT/logs/kafka.pid"
33:   for i in $(seq 1 40); do (echo > /dev/tcp/127.0.0.1/9092) ... && break; sleep 1; done
34: fi
```

`/dev/tcp/主机/端口` 是 bash 内建彩蛋：往它写数据就等于开一条 TCP 连接，连得上说明端口活着。Kafka 启动慢（JVM + 日志恢复），所以给 40 秒窗口。第 22 行把数据目录 sed 进配置，删掉 `data/kafka/` 即整体重置。

### 第 3 段：五个后端（37~57 行）——一个函数复用五次

```bash
38: start_jar() { # name port jarfile
40:   (echo > /dev/tcp/127.0.0.1/$port) 2>/dev/null && { echo "  $name 已在线"; return; }
41:   if [ ! -f "$jar" ]; then echo "  ✗ 缺 jar：$jar（先跑 infra/build.sh）"; return; fi
42:   nohup "$JAVA_HOME/bin/java" -jar "$jar" > "$ROOT/logs/$name.log" 2>&1 &
43:   echo $! > "$ROOT/logs/$name.pid"
44:   for i in $(seq 1 40); do (echo > /dev/tcp/127.0.0.1/$port) ... && break; sleep 0.5; done
45:   ... && echo "  $name: up ($port)" || echo "  ✗ $name 启动失败，看 logs/$name.log"
46: }
49: start_jar demo-todo 8081 "$ROOT/backend/demo-todo/target/demo-todo-1.0.0.jar"
...
55: start_jar train    8084 "$ROOT/backend/train/target/train-1.0.0.jar"
```

每个 jar 的启动三件套：**探活跳过 → nohup 起进程 → 轮询等端口**。起不来自救指南就一句：看 `logs/$name.log`。

### 第 4 段：Nginx（59~60 行）

```bash
60: "$ROOT/infra/nginx-reload.sh"
```

这个 80 行的脚本会：缺 dist 就现场 `npm run build` → 用 heredoc **生成** `nginx.conf`（把前端目录、反代规则写死进去）→ `nginx -t` 语法检查 → 有 pid 就 `reload` 热重载，没有就冷启动。

### stop-all.sh（25 行）反向操作

```bash
 8: for name in demo-todo demo-chat demo-counter train takeaway; do
 9:   if [ -f "$ROOT/logs/$name.pid" ]; then
10:     pid=$(cat "$ROOT/logs/$name.pid")
11:     kill "$pid" 2>/dev/null && echo "  $name 已停" || true
12:     rm -f "$ROOT/logs/$name.pid"
17: [ -f "$ROOT/infra/nginx/run/nginx.pid" ] && nginx -s quit -c ...
21: "$KAFKA/bin/kafka-server-stop.sh" >/dev/null 2>&1
24: redis-cli -p $REDIS_PORT shutdown nosave
```

顺序有讲究：**先停业务（后端）→ 再停门面（nginx）→ 再停中间件（kafka→redis）**。反过来的话，还在跑的后端会疯狂往死掉的 Kafka/Redis 报错刷屏。

## 思考题

1. start-all.sh 里 Redis 的探活用 `redis-cli PING`，Kafka 却用 `/dev/tcp`，为什么前者能用更"聪明"的方式？
2. 为什么 stop-all 先杀后端再停 Kafka/Redis，而不是反过来？
3. `nginx -s reload` 和 `nginx -s quit` 分别对应什么场景？
4. 如果 `logs/train.pid` 里的 PID 已经被别的无关进程复用了，stop-all 会发生什么？这暴露了 pid 文件方案的什么缺陷？

## 练习题

**练习 1**：写一个 5 行小脚本 `probe.sh <port>`，用 `/dev/tcp` 探测端口并输出 `up/down`。

**练习 2**：把 demo-todo 停掉（只用 pid 文件），确认 8081 不再响应，再用 start-all 单独把它拉起来。

**练习 3**：删除 `logs/takeaway.pid` 后跑 `stop-all.sh`，观察 takeaway 是否幸存；然后手工补写 pid 文件再停它。（做完恢复全栈。）

### 完整参考答案

**思考题 1**：Redis 有自带协议客户端 `redis-cli`，PING→PONG 语义明确；Kafka 是纯 TCP 二进制协议，没有这么轻量的命令行探针，所以退而求其次只验证"端口有人听"。探活的通用原则：能用应用层协议就用，不能就退到 TCP 层。

**思考题 2**：后端是 Kafka/Redis 的**客户端**。先停客户端再停服务端，客户端不会经历"服务突然消失"的报错风暴；反过来先停中间件，后端日志会瞬间刷满 Connection refused，还可能把没发完的消息丢掉。

**思考题 3**：`reload` = 重新读配置但不中断服务（改了 nginx.conf 后热生效，nginx-reload.sh 第 74 行用的就是它）；`quit` = 优雅停止，等现有请求处理完再退出。

**思考题 4**：stop-all 会把那个无辜进程 kill 掉——Linux 的 PID 会回收复用，旧 pid 文件指向的可能是几天后另一个进程。缺陷：pid 文件不校验"这个 PID 真的是当年的那个服务吗"。工业做法是 pid 文件里同时记录进程启动时间做双重校验，或改用 systemd/supervisor 这类进程管理器。

**练习 1 参考**：

```bash
#!/usr/bin/env bash
(echo > /dev/tcp/127.0.0.1/$1) 2>/dev/null && echo up || echo down
```

**练习 2 参考**：`kill $(cat logs/demo-todo.pid) && rm logs/demo-todo.pid`；`curl -m 2 http://127.0.0.1:8081/api/tasks` 应超时；重跑 start-all 后恢复。

**练习 3**：stop-all 第 9 行 `if [ -f ...pid ]` 不成立，直接跳过——takeaway 幸存。这正是本机真实发生过的事故。补救：`ps -eo pid,cmd | grep takeaway-1.0.0.jar` 找到真 PID 写回文件，或直接 `kill`。

## 本节小结
- 端口=门牌（独占），PID=身份证，pid 文件=stop 脚本的眼睛。
- start-all 的套路：**探活（幂等）→ nohup 后台起 → 轮询等端口 → 写 pid**。
- stop-all 顺序：后端 → nginx → kafka → redis，先客户端后服务端。
- 两大常见事故：端口冲突（看 `ss -tlnp` + `logs/*.log`）与 pid 文件丢失（野进程）。

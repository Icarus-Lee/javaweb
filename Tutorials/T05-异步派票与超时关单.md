# T05 · 异步派票与超时关单（Kafka 审计台 + @Scheduled closeExpired 实验）

> **本节要点**：下单成功后还有两台"看不见的机器"在后台转：Kafka 消费者把订单事件抄进审计台（异步解耦）；`@Scheduled` 定时器每 15 秒扫一遍，把超过 5 分钟不付款的 UNPAID 单自动取消、余票回补。本篇拆两段真实代码，并做"SQL 做旧 createdAt"实验——亲眼看着一笔活订单被机器人关掉。
> **前置知识**：T03（七步链路的第 6 步 Kafka 广播）、T01（状态机的关单边）。
> **产出**：能解释"为什么审计要在消费端做而不是请求线程里"；能默写 closeExpired 的判断逻辑；能独立复现关单实验并贴出 H2 前后对照。

## 1. 生活类比与动机：前台和档案室

### 是什么

两台后台机器，一个管"记录"一个管"善后"：

- **审计台（Kafka）**：前台（下单接口）收一笔单，往寄存处丢张小票就送客——**档案室（消费者）慢慢抄录**，前台毫秒级回家；
- **关单机器人（@Scheduled）**：每 15 秒巡一圈未付款柜台，谁的单子晾了超过 5 分钟，替他办退票、把票放回票池。

### 为什么这么设计

- **异步解耦**：审计（写库、打日志）不挡下单的路——响应时间从"下单+审计"降到"下单"；
- **削峰**：秒杀瞬时 1000 单，Kafka 把 1000 个"抄录任务"排队，档案室按自己能力消化；
- **自动善后**：人不可能 24 小时盯"谁没付款"，定时任务替人值守。这也是 12306"订单 30 分钟未支付自动取消"的教学缩影。

## 2. 生产者：一笔事实如何被广播（T03 第 6 步回顾）

`messaging/OrderEventProducer.java`（21 行全件）：

```java
9:  public static final String TOPIC = "train-order-events";
16: public void orderCreated(String orderNo, Long tripId, int seatNo, int price, String phase) {
17:     String payload = "{\"orderNo\":\"" + orderNo + "\",\"tripId\":" + tripId +
18:             ",\"seatNo\":" + seatNo + ",\"price\":" + price + ",\"phase\":\"" + phase + "\"}";
19:     kafka.send(TOPIC, orderNo, payload);   // key=orderNo：同一订单进同一分区（顺序保证）
20: }
```

两个设计点：

1. **key=orderNo**：Kafka 按 key 哈希定分区——同一订单的 CREATED/PAID/CANCELLED 事件落同一分区，**分区内部有序**，审计台账顺序不会乱；
2. **phase 字段**：同一个方法广播三种人生事件（`"CREATED"` / `"PAID"` / `"CANCELLED"`，分别在 `book` :72、`pay` :86、`cancel` :99 调用）——一个主题走天下，消费端按 phase 自行解读。

## 3. 消费者：AuditConsumer 全件走查（29 行）

```java
12: // 审计台：消费订单事件并盖戳入库 —— 展示"生产者/消费者解耦"效果。
13: // 消费者不在请求线程里：下单接口毫秒级返回，审计慢慢来。
20: @KafkaListener(topics = OrderEventProducer.TOPIC, groupId = "audit")
21: public void onOrder(String payload) {
22:     AuditLog log = new AuditLog();
23:     log.topic = OrderEventProducer.TOPIC;
24:     log.content = payload;
25:     log.createdAt = Instant.now();
26:     repo.save(log);
27:     System.out.println("[audit] " + payload);
28: }
```

逐行拆：

- **第 20 行 `@KafkaListener`**：Spring 为这行注解起一个**独立监听线程**（容器线程，日志里叫 `Container#0-0-C-1`），方法体跑在它身上——与 Tomcat 请求线程（`io-8084-exec-N`）完全无关。这就是"异步"的实现实体，不是形容词；
- **groupId = "audit"**：消费组。**多实例同组**时 Kafka 把分区分给不同实例（N04 起的第二台实例就自动加入了这个组，事件轮流消费——实测日志见 6.3）；
- **第 26 行 repo.save**：事件抄进 `audit_logs` 表——它就是"订单已发生"的官方流水；
- **第 27 行 System.out**：教学用的可见性——跑日志就能亲眼看事件流过。

## 4. 关单机器人：closeExpired 全件（11 行）

`BookingService.java` 第 103~111 行：

```java
103: /** 超时关单：UNPAID 超过 5 分钟自动取消（定时任务每 30 秒扫一次）。 */
104: @Scheduled(fixedDelay = 15_000, initialDelay = 20_000)
105: public void closeExpired() {
106:     for (Booking b : bookings.findByStatus("UNPAID")) {
107:         if (b.createdAt.isBefore(Instant.now().minus(Duration.ofMinutes(5)))) {
108:             cancel(b.userId, b.orderNo);
109:         }
110:     }
111: }
```

四要素：

1. **`fixedDelay = 15_000`**：上一轮跑**完**后再等 15 秒跑下一轮（不是 `fixedRate` 的固定节拍——扫描慢也不会堆积触发）；
2. **`initialDelay = 20_000`**：开机先让业务热身 20 秒再开始扫（避免启动竞态）；
3. **第 106~107 行的判断**：状态 = UNPAID 且 `createdAt < now - 5min` ——两个条件缺一不可（PAID 的单晾多久都不动）；
4. **第 108 行直接调 `cancel()`**：复用主动取消的全部逻辑——校验、改状态、**INCR 回补余票**（:98）、广播 CANCELLED 事件（:99）。**不复制代码就是最好的设计**：机器人和人退票走完全相同的路径，行为永远一致。

配套的两块拼图：

- `TrainApp.java` 第 5 行 `@EnableScheduling`——没它 `@Scheduled` 就是死注解（排坑第一名）；
- `BookingRepo.java` 第 10 行 `findByStatus(String status)`——方法名派生查询，机器人只查 UNPAID，不浪费全表扫描。

> 注释说"每 30 秒"、代码是 15 秒——注释与代码的漂移是真实仓库的日常，**以代码为准**（顺手改注释是好习惯，练习留给读者）。

**证据一：H2 状态翻转（实测输出）**

UNPAID → **CANCELLED**，机器人 22 秒内到岗。

**证据二：余票回补（实测）**

```
$ redis-cli -p 6379 get train:trip:5:stock

**证据三：审计事件（实测，注意它落在第二台实例的日志里！）**

```
$ grep "1f160bfa" /tmp/opencode/train2.log

[audit] {"orderNo":"1f160bfa-...","tripId":5,"seatNo":2,"price":0,"phase":"CANCELLED"}

### 5.5 实验的运维注解

- 做旧 UPDATE 是**测试手法**，生产绝不允许手改账（审计台上会留 UPDATE 痕迹的数据库也该报警）；
- 换算真实等待：不做事旧就 sleep 5 分钟 + 35 秒——效果一致；
- 机器人关单也发 CANCELLED 事件 → 审计台账自动留痕 → **善后也有账**，闭环。

## 6. 幂等与并发边角：机器人的边界情况

| 场景 | 行为 | 依据 |
|---|---|---|
| 用户在 4:59 付款，机器人 5:01 扫到 | 机器人看到的已是 PAID，跳过 | 第 106 行只取 UNPAID |
| 用户点取消的同时机器人也扫到 | 两边都调 cancel；后到者发现已 CANCELLED 直接 return | :95 `if ("CANCELLED") return b` |
| 同一笔单被扫两轮（第一轮漏网） | 第二轮状态已变，跳过 | 同上，天然幂等 |
| 机器人回补后 stock 超过历史最低？ | 不可能超过 totalSeats：回补数 = 扣过数 | T02 的不变式 |

**cancel 的幂等返回**（:95）是整个状态机防"重复善后"的基石——机器人和用户手滑重复操作，结果都收敛。

## 6.5 fixedDelay 与 fixedRate：一字之差，行为天壤

本项目用 `fixedDelay`，它有个双胞胎 `fixedRate`——一字之差，语义完全不同：

| | fixedDelay = 15s（本项目） | fixedRate = 15s |
|---|---|---|
| 计时起点 | **上一轮跑完**后 | 上一次**开始**时（固定节拍） |
| 扫描堆务 | 上一轮慢也不堆积 | 上一轮超时会**背靠背追赶** |
| 适用 | 善后类任务（漏扫一轮没关系） | 采样/统计类（节拍要对齐） |

关单是典型的"漏一轮无所谓"任务：15 秒没扫到的单，下一轮补上即可，没有不变式被破坏。反过来若这里是"每 15 秒发一次催付短信"，就必须 fixedRate（漏发一轮就是漏通知）。**选哪个的判断题就一句话：这任务是"要节奏"还是"要兜底"？**

再补一个本项目没写但生产必写的参数：**线程池**。Spring 默认所有 @Scheduled 共享**1 个线程**——若 closeExpired 某轮扫到 1000 单（每单要 Kafka+DB），其它 @Scheduled 任务全部饿死。生产写法：

```java
@Bean
public ThreadPoolTaskScheduler taskScheduler() {
    ThreadPoolTaskScheduler s = new ThreadPoolTaskScheduler();
    s.setPoolSize(4);                    // 关单、对账、统计各占一线
    s.setThreadNamePrefix("sched-");
    return s;
}
```

本项目任务唯一、扫描量小（UNPAID 就几单），单线程安全——**但你要知道这个默认值的存在**：哪天往项目里加第二个 @Scheduled，第一件事就是回头看线程池。

## 7. 常见坑清单

| 症状 | 根因 | 修法 |
|---|---|---|
| @Scheduled 死活不跑 | 没加 `@EnableScheduling` | TrainApp.java :5 |
| 审计台查不到刚下的单 | 消费异步，有 1~2 秒延迟 | sleep 后再查（smoke.py :97 的姿势） |
| 关单了票没回补 | cancel 里的 INCR 被改坏 | :98 必须在状态改后执行 |
| 做旧 UPDATE 报"表未找到" | H2 连了空库（忘 IFEXISTS） | 补参数重连（T01 的坑） |
| 事件时序乱 | 消费者多实例 + 无 key | producer 必须带 key=orderNo（:19） |
| 5 分钟改成 5 秒忘了改回 | 调试参数入 trunk | 配置化（`@Value("${app.order.ttl:PT5M}")`） |

## 8. 本节小结

- Kafka 消费者跑在**独立监听线程**（`@KafkaListener` + groupId）——"异步"是线程实体不是口号；下单毫秒返回、审计慢慢来。
- 生产者 key=orderNo 保分区有序；一个方法三种 phase（CREATED/PAID/CANCELLED）。
- `closeExpired`：15 秒一扫、UNPAID + 超 5 分钟两个条件、**复用 cancel()**（状态翻转 + INCR 回补 + 广播事件一步不少）。
- 实测关单实验：SQL 做旧 10 分钟 → 22 秒内 UNPAID→CANCELLED、stock 3→4、审计双事件（且被消费组第二台实例抢走——多实例消费实锤）。
- 幂等是善后机器人的护身符：cancel 已取消的单静默返回，重复扫描/重复手滑都收敛。

## 参考答案

**答**（对应思考题与练习题）：

1. auto-offset-reset=latest 的教学含义：消费端启动只从"新消息"开始收，避免每次重启都把历史事件重放一遍干扰实验观察；真实生产用 earliest + 业务幂等键才能不丢旧数据。
2. 定时关单必须做两件事：改状态 UNPAID→CANCELLED，同时 INCR 把那张票还回 redis 的 stock 池——否则这是"永久少一张"的暗账；同时发一条 CANCELLED 事件让审计台知道为什么少了票。
3. 幂等性：定时任务与人工取消可能同时命中同一订单，靠状态机"已是 CANCELLED 直接返回"保证重复执行无副作用（幂等）。

## 1. 生活类比与动机：先问"查询形状"，再挑"抽屉形状"

冰箱不是柜子堆：**冷冻层、冷藏层、门上的蛋架**各有各的"取出姿势"。Redis 同理——五种结构不是"五种花哨"，是**五种查询形状**各配一只最省事的抽屉：

| 要问的问题 | 正确抽屉 | 逆向代价（选错抽屉的死法） |
|---|---|---|
| 余票是几？DECR 一下 | **String**（数字） | 用 List 存库存 → DECR 无从谈起 |
| 谁先来谁先吃 | **List**（LPUSH/RPOP） | 用 String 拼串 `a,b,c` → 头插头取要"切再拼"两步非原子 |
| 用户档案：名字是？VIP 级别？ | **Hash**（分格） | 用 String Whole-JSON → 改一个字段要"读全串-改-写回" |
| 这活动口令用过了吗？（去重） | **Set**（SISMEMBER） | 用 List 重复塞 → 查"用没用过"要 LPOS 全扫 |
| 点单热度前十 | **ZSet**（按 score 反转序） | 用 Hash score → "谁排第三"要全表读内存排序 |

**一句话总律**：Redis 里"存进去"不难，难的是"**存成什么样才能一条命令答你的问题**"。

## 2. 五结构逐一现场跑（生活场景 × 真实输出）

以下每条都实测于本机 valkey 9.1.2（`redis-cli`，R01 环境先 `DEL` 清场）。

### 2.1 String：购物凑单计数 ≈ 余票原型

**场景**：奶茶店门口的**放号牌**——"当前还剩几张牌"，只加不减都行。

```
$ redis-cli DEL cart:xiaoyu archive:user:1 active:codes pop:shop1
0
$ redis-cli RPUSH cart:xiaoyu 辣炒年糕 可乐 餐巾纸
3
```

（上面顺手把 List 也点了，下一小节展开。）String 真身看 R03 的 `demo:counter`：`INCR` 一次 +1，**原子、车间单线程、无锁**。R04 的库存扣减 `DECR stock` 会在负数时被 `INCR` 找回——记住这是 String 的手法。

### 2.2 List：小鱼的购物清单（先加的先看到）

**场景**：**赶集的小单子**——手头想到什么追加什么，回头从头看一遍：

```
$ redis-cli RPUSH cart:xiaoyu 辣炒年糕 可乐 餐巾纸
3
$ redis-cli LRANGE cart:xiaoyu 0 -1
1) "辣炒年糕"
2) "可乐"
3) "餐巾纸"
```

方法话术：`RPUSH` = 右尾巴追加；`LRANGE 0 -1` = 从头到尾全列。若要用 List 给**点餐排号**，则是 `RPOP`（序号先进先出）。**List 是双端开口的**：`LPUSH`（左进）+ `RPOP`（右出）即一条 FIFO 队列——K 系列的"消息队列"思想，可以先在这里找到雏形。

### 2.3 Hash：小鱼的档案（一个 key 分多格）

**场景**：**小区业主档案卡**——一张卡上写名字、VIP 级别、城市，各格独立可改：

```
$ redis-cli HSET archive:user:1 name 小鱼 vip 2 city 上海
3
$ redis-cli HGET archive:user:1 name
"小鱼"
$ redis-cli HGETALL archive:user:1
1) "name"
2) "小鱼"
3) "vip"
4) "2"
5) "city"
6) "上海"
```

注意两件事：

- `HGETALL` 的输出是 **field/value 交错**成对存的，与 MySQL 的"一行"相比，它不需要先修表结构。
- 改一格：`HINCRBY archive:user:1 vip 1`（VIP 升级那就原子 +1）。若用 String 存 JSON 再改 vip，则是"读全串-改-写回"三步，不是原子的——Hash 在这里白赚原子性。

### 2.4 Set：活动口令名册（有没有用过？）

**场景**：**派口令**——"公众号回复 ABC123 领券"：每个口令**只能用一次**，判断"用没用过"必须 O(1)：

```
$ redis-cli SADD active:codes abc123 xyz777
2
$ redis-cli SADD active:codes abc123
0
$ redis-cli SISMEMBER active:codes xyz777
1
$ redis-cli SCARD active:codes
2
```

第二组 `SADD` 返回 0：**重复添加不报错也不生效**——Set 天生去重。`SISMEMBER` 是"这口令在名册上吗"的 O(1) 答复。生产常见的"**接口幂等指纹**"（把 orderNo 存 Set 防重复处理）就是这个场景的兄弟——K05 会再见面。

### 2.5 ZSet：购物中心热门菜品榜（score 说话）

**场景**：**大众点评式热度榜**——分数即人气，想看"前三名"随时一口问出来：

```
$ redis-cli ZINCRBY pop:shop1 3 芒果糯米饭
"3"
$ redis-cli ZINCRBY pop:shop1 1 咖喱鱼蛋
"1"
$ redis-cli ZREVRANGE pop:shop1 0 -1 WITHSCORES
1) "芒果糯米饭"
2) "3"
3) "咖喱鱼蛋"
4) "1"
```

`ZINCRBY` **加分原子加**：uvre每次成交 `+1`，Redis 单线程无锁不乱序。`ZREVRANGE 0 -1 WIHSCORES` 全榜反转。**R05 的"购票热度榜"完整就是这个结构**——提前见识，那章只多一个 Spring 接口把它暴露成 HTTP。

## 3. TTL 与"自动消失"：不是变 null，是整个 key 回收

Redis 不擅长"写个垃圾清理 cron"的地方，它给了**TTL**：给 key 挂个倒计时，时间到**整个 key 被回收**。三种存在的状态一次认清：

| `TTL k` 结果 | 含义 | GET 表现 |
|---|---|---|
| 正数 | 还剩几秒 | 能读到 |
| **-1** | 存在但**永不过期**（默认） | 能读到 |
| **-2** | **已消散**（不存在） | 返回 nil |

### 动手验证：一次性验证码的生死 5 秒

**场景**：**短信验证码**——60 秒不留，过期就得"重新发"。实测（R01 那条的完整重放）：

```
$ redis-cli SET otp:session:8848 "第四件秒杀验证码" EX 5
OK
$ redis-cli TTL otp:session:8848
5
$ sleep 6
$ redis-cli GET otp:session:8848
(nil)
$ redis-cli TTL otp:session:8848
-2
```

**读解三大要点**：

1. `SET key val EX n` 是 **"写 + 挂 TTL" 的完整原子动作**（等价于先 SET 再 EXPIRE，但做两步非原子会留槽点）。只要能一步写挂，就两不分离。
2. `GET` 返回 **nil**（cli 里显式 `(nil)`）——**不是字符串 "null"**。Java 端（R03）对应返回 `null`，代码必须判空。
3. 项目里还有一线"永生 key"对照：R01 的 `GET demo:counter` 后 `TTL demo:counter` **返回 -1**——计数器设计意图就是永生，没有倒计时。

### TTL 的真实战术位

- 验证码/一次性 session（本章 otp）
- **分布式锁的兜底**：R04 的 `setIfAbsent(lockKey, "1", Duration.ofSeconds(10))`——进程炸了 finally 没跑，锁 10s 自己消失而"人走门忘关"事故被 TTL 拼平。**TTL 与锁是拍档，单方面都被毙**（S11 已有此语，R04 复盘）。
- **滑动窗口限流**：R05 的 fixed window 计数是"INCR + EXPIRE 1s 重置计数"的组合——真正"自动消失"的计数器。

## 5. 选型失误速修诊（压缩成表）

| 新手错误 | 死法 | 换抽屉修法 |
|---|---|---|
| 库存存 String-of-JSON `{"stock":9}` | DECR 无法使用 | 裸存数字 `SET trip:5:stock 9` + DECR/INCR |
| 排行榜用 Hash field=菜名 | "前三名"要全表读再 O(N) 排序 | 换 ZSet：ZINCRBY + ZREVRANGE 都在 O(log N) |
| 去重名册存 List | "用没用过"要 LPOS 全扫、内存带重复 | 换 Set：SISMEMBER O(1) |

## 5.5 工程实录：踩坑与修复——WRONGTYPE，"改行不改名"的代价

**故事**：给菜品库存 key `r02lab:typecheck` 做实验的同学，先后用两套代码写同一个 key——一个用 List 写、一个用 String 写。第二次操作全集开始报错，UI 显示不出库存。这类事故在五个结构之间最容易发生：**key 名不变、值的"抽屉形状"换了**。

### 现场复现（一真两错，原样输出）

```
$ redis-cli SET r02lab:typecheck 1
OK                                  ← String 形状（数字字符串）
$ redis-cli LPUSH r02lab:typecheck a
(error) WRONGTYPE Operation against a key holding the wrong kind of value
$ redis-cli INCR r02lab:typecheck
2
```

三条读证：

1. `LPUSH` 报 **WRONGTYPE**——List 命令按在 String key 上，Redis **当场拒绝**、不静默转换。这是保护：跨结构的隐式转换会造出更深的错账。
2. `INCR` 照常工作：**同一个 String key 按用途可当"计数器"用**——RDB 里的 value 对兼容的命令族透明。
3. 注意：R04 的实战全建立在 "**一个 key 一种形状，终身不改形状**"——改用途就换 key 名（如 `stock` → `stock_v2`），旧 key 自身 TTL 回收。

### 定位路径

模拟真实事故的排查姿势——你 UI 崩了，但根因在形状：

```
$ redis-cli TYPE r02lab:typecheck
string
```

**看 TYPE 一锤定音**。生产里若几个服务共写一个 key，先 TYPE 再决定命令族；附赠查祖：`OBJECT ENCODING key` 能看到 int/embstr/ziplist 之类的内部编码（R02 只立路标，排障手册里它是常客）。

### 修复与再验证

- **修法一行**：新用途换新 key——`SET r02lab:typecheck:v2 5`，旧 key `DEL`。diff 前后就是"键名追加 `:v2`"一件事。
- **再验证**：`redis-cli LPUSH 新key` 试一下不报错，形状对齐。
- **流程修复**：团队规范一条——**key 命名里写上结构名**（`list:cart:xiaoyu`、`set:active:codes`），命名即文档，事故率直接砍半。

### TTL 的第二坑（顺手实测）：which EXPIRE 该挂几次

第 3 节限流三行 Java 里有个"只在 hits==1 时挂 EXPIRE"的铁律。真实跑一遍"每次都挂"的恶果：

```
$ redis-cli DEL rl:demo
0
$ redis-cli INCR rl:demo; redis-cli EXPIRE rl:demo 1; redis-cli TTL rl:demo
1 / 1 / 1
$ redis-cli INCR rl:demo; redis-cli EXPIRE rl:demo 1; redis-cli TTL rl:demo
2 / 1 / 1
$ redis-cli INCR rl:demo; redis-cli EXPIRE rl:demo 1; redis-cli TTL rl:demo
3 / 1 / 1
```

读证：每次 `EXPIRE 1` 都把倒计时**重置回 1 秒**——三次请求间隔若小于 1 秒，计数器**永远不清零**，"每秒 5 次"限流形同虚设（计数涨到 3、世界永远剩 1 秒）。**修**：`EXPIRE` 挂一次（`hits==1` 时）或换原子版 `SET k 0 EX 1` + INCR。R05 有完整版。**TTL 语义的三个数字（正 / -1 / -2）你今天要能随口背出，且知道"每次续命"是它的第四种死法。**

## 8. 参考答案

**练习 1**（实测形态）：

```
$ redis-cli RPUSH queue:desk A B C D
4
$ redis-cli LPOP queue:desk
"A"
$ redis-cli LPOP queue:desk
"B"
$ redis-cli LPOP queue:desk
"C"
```

一端进另一端出 → FIFO：**RPUSH + LPOP** 是最直白的"排队发号"。若两侧是同一端（RPUSH+RPOP）就成了栈（LIFO）——**同一数据结构，两种取法，两种生活语义**。

**练习 2**（实测）：

```
$ redis-cli HSET profile:xiaoyu name 小鱼 level 1
2
$ redis-cli HINCRBY profile:xiaoyu level 1
2
$ redis-cli HINCRBY profile:xiaoyu level 1
3
$ redis-cli HINCRBY profile:xiaoyu level 1
4
$ redis-cli TTL profile:xiaoyu
-1
```

三次 +1 后 level=4；TTL 为 **-1**——`HSET` 不给 TTL，**TTL 只挂在 key 级**（不是 field 级）。想给 field 单独过期，就得自己换 key 拆分设计——这也是"Redis 的 Hash 不能多个格各自过期"的常见边界坑。

**练习 3**（答案要点）：ZSet **member 不重复、score 可重复**。score 相同的成员按 member 字典序稳定排列——这是"并榜单上谁在前"的细节规则，而礼物榜这种"score = 累计金额"的形态正好需要 member 唯一保证去重。 sort 後 ZREVRANGE 0 2 就是前三名，无需手写 LIMIT——top N 命令天然内建。

**练习 4**（命令层一行）：

```
$ redis-cli SADD used:fingerprint "order-123"
1                          ← 1 = 第一次，可以走业务
$ redis-cli SADD used:fingerprint "order-123"
0                          ← 0 = 已处理过，拒绝重复
```

`SADD` 的返回值 1/0 就是"幂等闸门"的答语。K05 讨论 DispatchConsumer 时会再把它换手写成 Java 的 `Redis`/数据库状态机版本——先在你心里挂个钩子。

## 9. 本节小结

- **汇总一句心法**：Redis 五种结构 = **五种查询形状**。拿到需求先自问"我要一句话答什么"，再挑抽屉：
  - **String**：单个数字/对象薄壳 + 原子算术（余票、计数、锁 token）
  - **List**：FIFO/LIFO 双端（队列、清单）
  - **Hash**：一 key 多格独立改（档案、非原子的对象局部更新）
  - **Set**：去重 + O(1) 存在判断（口令、幂等指纹）
  - **ZSet**：按分数排好的榜（热度榜、排行榜）
- **TTL 是 key 级**倒计时：-1 永生、-2 已消散；缓存/验证码/锁兜底三联用的都是它。
- 十条账单已经真跑真读——**写教程不能骗人，数据必须现场量**。

## 1. 生活类比与动机：转账不能"只扣不加"

### @Transactional 是什么

把"多个写操作"捆成一捆：**全成 → 提交；任何一步失败 → 全部撤回**，数据库回到记账之前。 analogy：服务器中转行户收入不能"扣了 A 家一万、忘了打给 B"。

### 它管两件事，缺一即错案

1. **原子性（atomicity）**：一捆全成或全撤——`@Transactional` 的本职。
2. **一致性（isolation）**：事务期间别人看不见你的半成品。

train 里的下单，本该也是"多步"（H2 写 booking + Kafka 发事件 + Redis 扣票），**跨了数据库与 Redis 与消息队列**——三种系统谁都没法给跨它们的"大事务"。教学取舍：**H2 只承担"落库的一账"，Kafka 用 fire-and-record；Redis 的库存用"先扣后补偿"守住**。所以 train 的 `book()` 没有 `@Transactional`——它的账本主体在 Redis（原子）+ H2（单写）+ Kafka（可丢可补）。理解这个统筹取舍，正是本章的真实任务。

takeaway 的 `OrderService.create` 才是**纯 H2 大事务**（`@Transactional` 标在方法上）——不涉及 Redis 扣减，全部动作都发生在同一个数据库连接里。

## 2. 幂等与 rollback 拌点（两句要点）

- **幂等（idempotent）**：同一个请求来两次，数据库结果与一次一样。`cancel()` 里那句 `if ("CANCELLED".equals(b.status)) return b;` 就是**把幂等写显式**——重复取消不回票再扣。
- **rollback 拌点**：`@Transactional` 默认**只对 RuntimeException 与 Error 自动回滚**；受检异常（`throws Exception` 那类）**默认不回滚**！典型舞步：写一条记录、抛了个 `IOException`、“以为会回滚”其实**已提交**了第一个写。修复姿势要么显式 `@Transactional(rollbackFor = Exception.class)`，要么把异常统统包装成 `RuntimeException`。
  - 本项目策略一致：所有 `service` 里 `throw new RuntimeException` / `IllegalStateException`（运行时），所以默认语义正好正确——但这是**刻意选择的结果**，不是巧合。

## 3. 动手验证一：错账实录（lost update 账本对折）

文件：`临时用` 随手写纯 JDBC，だけ依赖 H2 jar。核心代码（完整源码在文档末尾附录）：

```
CREATE TABLE stock(id INT PRIMARY KEY, seats_left INT);
INSERT INTO stock VALUES(1, 10);
```

三个线程各自 `SELECT seats_left` → 睡 50ms → `UPDATE stock SET seats_left = <我读到的那只-1>`——不用锁、不用事务。应当卖出 3 张剩 7。

**实测输出（跑三轮，三次都同样错账）：**

```
== 糟糕案例：无锁读-改-写（每单先读再写回 seats_left-1）
最终余票 = 9（卖出 3 张，应剩 7）

== 正确姿势 1：单条原子 UPDATE seats_left = seats_left - 1
最终余票 = 7（卖出 3 张，应剩 7）

== 正确姿势 2：FOR UPDATE 行锁
最终余票 = 7
```

错账的原因一句话：**读-改-写是非原子的**。三个线程谁都读到 10，谁都写 9——最后一个是时间上的"最后写入者"，前面的修改被无情踩掉。

**换个写法立刻健康**（我们顺手验证的两小时内瓜子位）：

1. **把算术塞进 SQL**：`UPDATE stock SET seats_left = seats_left - 1 WHERE id = 1 AND seats_left > 0`——单条语句本身在库内是一根原子管子。**读者永远是"一"。**
2. **SELECT ... FOR UPDATE**：事务里先锁住这一行再读，别人的一份与本份互斥。也是行锁原子力，但**显式占坑**，适合业务算式复杂时。

**数据库行锁（对账内余票）就这么两种正经姿势。** 那为什么本项目的 train 不用它？往下看。

## 4. 工程实录：真实问题与解决——"JPA 内部锁 vs Redis DECR"对照实验（两人谁在扛并发？）

第 3 节已有无锁错账 9/7/7 的实测。但生产上常有人问：**不上 Redis，JPA/数据库自己的锁机制只管一个"能用"吗？** 本站再跑一个对照实验：同一时刻三个并发下单——A 组用 `@Version` 乐观锁同款判定式（纯 JDBC 模拟其 SQL 语义），B 组用真 Redis 的 DECR。

### A 组：乐观锁（@Version 同款语义，OptDemo.java 实跑）

判定式就是 `@Version` 生成的样子：

```sql
UPDATE trips SET seats_left = seats_left - 1, version = version + 1
 WHERE id = 1 AND version = :plan版本号          -- 0 行受影响 = 有人抢先 = 冲突
```

**实测输出（`java -cp h2.jar OptDemo.java`，本站核心新增）：**

```
A 乐观锁: 成功下单 1 笔 / 被拒 2 笔（被拒需整单重试），余票=9, version=1
```

三个都读到 `v=0`，第一个提交者独得；另两个更新 0 行、**必须读-重试整个业务段**——JPA 里每次重试都拋 `OptimisticLockException`（W01 有叙）。这就是"JPA 内部锁"的形态：**不挡人进来，只查"版本"放行一个**。

### B 组：同一秒换 Redis DECR

```bash
$ redis-cli set optdemo:stock 10 && for i in 1 2 3; do (redis-cli decr optdemo:stock >/dev/null &); done && sleep 1 && redis-cli get optdemo:stock
7        ← 三笔全部成功，无一冲突、无一重试
```

### 对照结论（实战口径）

| 维度 | 乐观锁（JPA @Version） | Redis DECR |
|---|---|---|
| 冲突发不发生 | 常发（高并发下"被拒"比例随并发陡升） | **0**——顺序串行 |
| 冲突的处理代价 | 整段业务重放（重读、重算、再提交） | 无需处理 |
| 语义边界 | 只管**本表本行**的"写入一致" | 管**任意键的"算术原子"** |
| 适合 | 冲突少（编辑冲突、订同一冷门座位） | 冲突路常走（抢票、秒杀、计数） |

**解读**：余票之争是**热点键冲突重度高**的场景，重试风暴会被乐观锁放大（每重试都是一段完整业务重复）；所以 train 选 DECR。反之，**低频后台数据**（菜单、车次详情）用乐观锁最省心——**两把刀选择场景才是刻度**。

附：`OptDemo.java` 全文（可直接复现）：把 A 组代码改为 `CREATE TABLE trips(id INT PRIMARY KEY, seats_left INT, version INT); INSERT INTO trips VALUES(1,10,0);` 起步、三条线程各走 `SELECT → sleep 50ms → UPDATE ... WHERE version=?`，然后统计 1 修改 / 0 修改的笔数即可。

## 5. train 的 Redis 原子方案全流水（真实代码走查）

**文件：`backend/train/src/main/java/com/javaweb/train/service/BookingService.java`：book() 六步流水线**

```java
26:    String stockKey = "train:trip:" + tripId + ":stock";
27:    String lockKey  = "train:trip:" + tripId + ":lock";
28:    String seqKey   = "train:trip:" + tripId + ":seq";
30:    // 1) 谁先 set 成功谁锁门（10 秒自动解锁，防"人走门忘关"）
31:    Boolean locked = redis.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(10));
32:    if (locked == null || !locked) {
33:        throw new IllegalStateException("手速太快，请重试（车次处理中）");
35:    }
38:    // 2) 原子扣票：DECR，结果为负即"卖重复了"，必须还回去
39:    Long stock = redis.opsForValue().decrement(stockKey);
41:    if (stock == null)  throw new IllegalStateException("车次未初始化（stock key 缺失）");
43:    if (stock < 0) { redis.opsForValue().increment(stockKey); throw ...; }
46:    // 3) 座位号：INCR 序列分配
...
54:    b = bookings.save(b);          // 4) 落库（H2）
...
57:    producer.orderCreated(...);    // 5) 发 Kafka 事件
...
59:    } finally {
60:        redis.delete(lockKey);     // 6) 归还锁（finally 保证"无论成败都还"）
61:    }
```

**六步的排序逻辑不可换**：

- 锁门在上（:31）：**只有它保护"这节车厢此刻我一个人动账"**。
- DECR 是进闸票（:39）：**单线程 Redis** 保证多客户端并发汇聚进来时算术不分对折。
- INCR 补偿（:43）：DECR 后 <0 说明**票不够**，回滚"扣掉的那一票"（INCR 还 one back）——这就是"先扣后补"的完整形态。
- finally 还锁（:60）：**必须放 finally**，否则业务异常（车次不存在、DB 落库失败）会把锁永远留在 Redis 里 → 永远订单无人过。
- setIfAbsent 的 10 秒兜底：万一进程那一刻被 SIGKILL（finally 都没机会跑），锁**自然**在 10s 后释放——**应用锁与 TTL 是搭配手**，单方面都役了。

**实测，验证它真的在防超卖——大 applicant 齐来：D3102 这次只余 1 张，6 并发同时下单：**

```
Trip 3(D3102) 余票=1 reset 后
b1 → 500 "已售罄"
b2 -> 500 "已售罄"
b3 -> 500 "已售罄"
b4 -> {"id":253,...,"seatNo":1,"status":"UNPAID"..."orderNo":"43fdb4d7..." }
b5 -> 500 "已售罄"
b6 -> 500 "已售罄"
redis:  train:trip:3:stock = 0 ;  train:trip:3:seq = 1
```

**6 得 1，只要一人！** 唯一成功的在 H2 里落成 `SEAT_NO=1`、`status=UNPAID`、余票归 0。与第 3 节 JDBC 实测形成对照：读改写三步走就错账、单条原子 DECR 就分毫不差。

## 6. "数据库锁 vs 应用分布式锁"——真正难点

两个方案各自长处与"非常规强制注意"：

| 维度 | 数据库锁（FOR UPDATE / 原子 UPDATE） | 应用分布式锁（Redis setIfAbsent） |
|---|---|---|
| 范围 | 一行/一个表区间 | 一个字符串确定的一个"坑"（可锁任意业务） |
| 提供者 | 数据库引擎 | Redis（多实例也可） |
| 什么时候采手 | 数据全部都在**同一张表**上日记账 | 跨系统：DB + Redis + Kafka + 外部 API 一起动账 |
| 死锁处理 | 引擎自己超时抛错 | TTL 自到期防"人走门忘关" |
| 业务异形锁 | 不方便锁"这 2 分钟内不让任何人动" | TTL 手写时长，更顺手 |

train 的选型理由：下单同时要动**三套**（Redis 余票 + H2 订单 + Kafka 事件）——任何单库行锁只能锁一个；而**应用层锁钉住"整个业务段"**，锁期间完成的"扣票 + 落库 + 事件"才是完整因果段。

两者共存的事实**也须认账**：**Redis 假账不救 H2 真账**。所以 `cancel()` 里会**INCR 回票**（`redis.opsForValue().increment(stockKey);`），`cancel()` 幂等地 return——跨系统对账是不可能靠锁一揽子完成的，只能"每步都留退路"。

## 7. @Transactional 的位置小辨（不能挪的坑）

- **标在 public 方法上**（Spring 代理机制）；`private` / `final` 上会被静默忽略。
- **同类内自调**（`this.bought()`）不走代理，事务不触发。走到同一个 service 成员的，要**把事务方法抽出去**或**自注入一次**。
- **回滚边界**异常一律处理在第 1 层（Controller 脚下抛到 Boot 兜底）：S07 学过的 GlobalExceptionHandler 与此相关——catch 掉异常反而容易**吞掉回滚**。

```
$ curl -X POST /api/orders/{ono}/pay     → 500

```

## 11. 本节小结

- 事务 = 多步写打包，`@Transactional` 默认只对 RuntimeException/Error 回滚——**拌点必须知道**。
- 错账的本质：读-改-写非原子。实测三连击（9 / 7 / 7）是一条**永远忘不掉的刻度**。
- train 用"Redis 原子 DECR 衡量票数 + setIfAbsent 锁 + finally 还锁 + INCR 补偿"——应用分布式锁**锁业务段**，数据库行锁**锁同一行的记账**。
- 跨系统场景锁+库要都顾，但**每步都要留自然的退路**。

## 附录 A：RaceDemo.java 全文（本站实测用的原件）

> 复现步骤：`java -cp ~/.m2/repository/com/h2database/h2/2.3.232/h2-2.3.232.jar RaceDemo.java`
> 注意 H2 2.x 中 `LEFT` 是保留字——本例全部用 `seats_left`，这是真人踩过的坑（报错 `expected "identifier"`）。

```java
import java.sql.*;
import java.util.concurrent.*;
import java.util.concurrent.TimeUnit;

public class RaceDemo {
    static ExecutorService EXEC = Executors.newFixedThreadPool(3);

    public static void main(String[] args) throws Exception {
        String url = "jdbc:h2:mem:racedemo";
        Connection c = DriverManager.getConnection(url, "sa", "");
        try (Statement s = c.createStatement()) {
            s.execute("CREATE TABLE stock(id INT PRIMARY KEY, seats_left INT)");
            s.execute("INSERT INTO stock VALUES(1, 10)");
        }
        // ---- 糟糕案例：无锁读-改-写 ----
        System.out.println("== 糟糕案例：无锁读-改-写（每单先读再写回 seats_left-1）");
        for (int th = 0; th < 3; th++)
            EXEC.submit(() -> { try { careless(c); } catch (Exception e) { e.printStackTrace(); } });
        EXEC.shutdown(); EXEC.awaitTermination(3, TimeUnit.SECONDS);
        System.out.println("最终余票 = " + query(c) + "（卖出 3 张，应剩 7）");

        // ---- 姿势 1：算术塞进 SQL ----
        try (Statement s = c.createStatement()) {
            s.execute("UPDATE stock SET seats_left = 10 WHERE id = 1");
        }
        System.out.println("\n== 正确姿势 1：单条原子 UPDATE seats_left = seats_left - 1");
        ExecutorService e2 = Executors.newFixedThreadPool(3);
        for (int th = 0; th < 3; th++)
            e2.submit(() -> { try (PreparedStatement p = c.prepareStatement(
                "UPDATE stock SET seats_left = seats_left - 1 WHERE id = 1 AND seats_left > 0")) {
                p.executeUpdate(); } catch (Exception ex) { throw new RuntimeException(ex); } });
        e2.shutdown(); e2.awaitTermination(3, TimeUnit.SECONDS);
        System.out.println("最终余票 = " + query(c) + "（卖出 3 张，应剩 7）");

        // ---- 姿势 2：FOR UPDATE 行锁 ----
        try (Statement s = c.createStatement()) {
            s.execute("UPDATE stock SET seats_left = 10 WHERE id = 1");
        }
        System.out.println("\n== 正确姿势 2：FOR UPDATE 行锁");
        ExecutorService e3 = Executors.newFixedThreadPool(3);
        for (int th = 0; th < 3; th++)
            e3.submit(() -> { try { lockBuy(c); } catch (Exception ex) {
                System.out.println("抢不到: " + ex.getMessage()); } });
        e3.shutdown(); e3.awaitTermination(3, TimeUnit.SECONDS);
        System.out.println("最终余票 = " + query(c));
    }

    static void careless(Connection c) throws Exception {
        try (Statement s = c.createStatement()) {
            ResultSet r = s.executeQuery("SELECT seats_left FROM stock WHERE id = 1");
            r.next(); int left = r.getInt(1);
            Thread.sleep(50);                            // 模拟业务处理——竞态窗口
            s.executeUpdate("UPDATE stock SET seats_left = " + (left - 1) + " WHERE id = 1");
        }
    }
    static void lockBuy(Connection c) throws Exception {
        c.setAutoCommit(false);
        try (Statement s = c.createStatement()) {
            ResultSet r = s.executeQuery("SELECT seats_left FROM stock WHERE id = 1 FOR UPDATE");
            r.next();
            if (r.getInt(1) > 0)
                s.executeUpdate("UPDATE stock SET seats_left = seats_left - 1 WHERE id = 1");
        } finally { c.commit(); c.setAutoCommit(true); }   // 提交即释放行锁
    }
    static int query(Connection c) throws Exception {
        ResultSet r = c.createStatement().executeQuery("SELECT seats_left FROM stock WHERE id = 1");
        r.next(); return r.getInt(1);
    }
}

## 附录 B：丢失更新的时序图（三线程各自的账目）

```
时刻   线程A            线程B            线程C            库里 seats_left
t0    BEGIN            BEGIN            BEGIN            10
t1    SELECT → 10      SELECT → 10      SELECT → 10      10（三个都是"10"）
t2    （sleep 50ms）    （sleep 50ms）    （sleep 50ms）   10
t3    UPDATE set 9     UPDATE set 9     UPDATE set 9     9（三次写、只留最后一次）

三张单、库里只少 1——这就是"错账"的全过程，**没有任何一步报错**——所有动作都"正常完成"了，但账错了一笔。这种事故比崩溃更难发现：**数据库没炸、接口没炸、只有数字不对**。也由此解释第 3 节两种修复姿势为什么都"原子"：原子 UPDATE 把算术收编进单条语句（把"读"也纳入原子域），FOR UPDATE 则显式卡住整段读改写窗口，两种姿势都消灭了 t1 到 t3 的竞态窗。

## 1. 生活类比与动机：同一列火车的车厢号

先下单、再支付、最后派单——这类顺序业务在 Kafka 里只有一件保序武器：**同一个 key 的消息固定 hash 到同一个 partition**。partition 是一条顺序追加的日志，每条消息一个递增 offset。所以同一巷里，CREATED 永远排在 PAID 前面；消费者从巷口往里读，业务时间线与 offset 线天然重合，不需要任何额外加锁。

代价同样清楚：不同 orderNo 之间没有任何顺序承诺。hash 把两单分到不同位置，谁先谁后纯属巧合。所以**保序的粒度等于业务键的粒度**：想为谁保序，就把谁的身份证填进 key。

## 2. key 定 partition 保序：原理三步与三句成稿

### 原理三步

1. **写的人给 key**：`kafka.send(TOPIC, orderNo, payload)`（K03 原话）。同一 orderNo 每次 hash 得到同一个值，同单不散巷。
2. **broker 存**：同 key 的消息排在同一 partition，offset 一路递增。offset 线就是这条单的业务时间线。
3. **读的人按 offset 读**：同巷里 CREATED 永远在 PAID 前面，顺序自动成立。

### 实测：同 orderNo 保序的真实事件（与 K03 实录对账）

```
$ timeout 10 tools/kafka/bin/kafka-console-consumer.sh \
    --bootstrap-server 127.0.0.1:9092 \
    --topic train-order-events --from-beginning --timeout-ms 8000 2>/dev/null

{"orderNo":"d1e0dde3-5175-4eb8-b725-f2dc49a2486b","tripId":1,"seatNo":1,"price":42,"phase":"CREATED"}
{"orderNo":"d1e0dde3-5175-4eb8-b725-f2dc49a2486b","tripId":1,"seatNo":1,"price":0,"phase":"PAID"}
{"orderNo":"d1e0dde3-5175-4eb8-b725-f2dc49a2486b","tripId":1,"seatNo":1,"price":0,"phase":"CANCELLED"}
{"orderNo":"2d4bcba1-0ae5-4a1e-95e1-f21572c688d8","tripId":5,"seatNo":1,"price":314,"phase":"CREATED"}
{"orderNo":"2d4bcba1-0ae5-4a1e-95e1-f21572c688d8","tripId":5,"seatNo":1,"price":0,"phase":"PAID"}
```

读证三行：

1. **同 orderNo 保序成立**：d1e0dde3 的三连（CREATED→PAID→CANCELLED）按 offset 排好；2d4bcba1 的两连（CREATED→PAID）同理。读到的序与生产序一致。
2. **不同 orderNo 之间无序**：两单各成一队，谁快谁慢不保证。业务不要跨单赌顺序。
3. **单 partition 的全序是副产品**：本项目 topic 只有一条巷，不看 key 也是全序。partition 扩多之后，同 key 才是唯一保序线。

### 三句成稿（保序戒律）

- 事件必须先 A 后 B：key 填业务身份（orderNo 这类单键）。
- 想加吞吐：加 partition，但定型后别再改。同 key 的 hash 会挪巷，保序连带清零。
- 想要全局面序：别走多 partition，那是"吞吐换顺序"；回单巷，或让业务自带序号由消费端判序。

## 3. 消费重试：默认行为与死信机制

### 默认行为：同条重读（at-least-once 的官式实现）

Spring-Kafka 的 container 默认行为：listener 抛运行时异常，当前这条消息的 offset 不提交，下一轮 poll 又是同一条。这正是 K05 说的 at-least-once 基石。

副作用就是**毒消息**：某条消息让业务每次都抛错，它就会无限重试，把同巷消费者摁住，后面的消息全部堆积。本项目 DispatchConsumer 的三重门（假单 return、phase 检查、状态机检查）让"必然失败的消息"进不来；但其他业务必须自己上死信机制。

### 死信机制的简化版（可编译、不合并主分支）

```java
// 教学样例：重试三次、每次隔一秒、仍败进死信
@RetryableTopic(
    attempts = 3,                                   // 顶多试三次（含首次消费）
    backoff = @Backoff(delay = 1000)                // 每次重试之间隔 1 秒
)
@KafkaListener(topics = OrderEventProducer.TOPIC, groupId = "dispatch")
public void onOrder(String payload) {
    /* K04 真码原样保留，本行不改动 */
}

@DltHandler                                        // 三次仍失败：自动进 "{topic}-dlt"
public void dlt(String payload) {
    System.out.println("[DLT] " + payload);
    // 真实生产：写死信表、发告警、人工处理
}
```

读法三细节：

1. **attempts=3**：同一条消息顶多消费三次。"无限循环重试"被切断，毒消息落到 DLT 之后不再阻塞巷道。
2. **backoff delay=1000**：重试之间给下游一点恢复时间，比如 H2 短暂不可用、外部接口限流。生产上常配指数退避（1 秒、2 秒、4 秒）。
3. **DLT 自动成型**：`@RetryableTopic` 会自动挂出一个名为"原 topic 名 + -dlt"的死信 topic。`@DltHandler` 就是它的消费方法。两者配对使用，不要单拆。

### 重试与幂等的配合（两件装备互锁）

重试三次，等价于"同一条消息来三次"。能不能扛住重试，靠的不是 Kafka，而是 K05 的业务幂等：DispatchConsumer 三重门让重复消费的结果与消费一次相同。死信是给"必然失败"的消息留档，幂等是给"会成功"的消息保正确。两者配合，才是消费端的完整防线。

## 4. LAG：怎么定义、怎么观察、何时告警

### LAG 速查表

| LAG 值 | 含义 | 动作 |
|---|---|---|
| 0 | 完全追上 | 无事 |
| 个位数 | 正常窗口内的"边消费边来" | 观察即可 |
| 百、千 | 消费者挂了或太慢 | 告警、人工减压 |

LAG 的定义一句话：**LAG = LOG-END-OFFSET − CURRENT-OFFSET**。LOG-END 是 broker 端最新的队尾序号，CURRENT 是消费组已提交的进度；两数相减就是"还有几条没处理"。K04 的对账表已经见过它一次（audit 5/5、dispatch 10/10、LAG 0）。

### 实测一：基线真账（LAG 0）

```
$ env KAFKA_HEAP_OPTS="-Xmx64M" tools/kafka/bin/kafka-consumer-groups.sh \
      --bootstrap-server 127.0.0.1:9092 --describe --group dispatch

GROUP    TOPIC                   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
dispatch takeout-order-events    0          10              10              0
```

### 实测二：手造四条消息（console-producer 真跑）

```
$ printf '{"orderNo":"lag-0001","dishId":1,"qty":1,"phase":"CREATED"}\n' \
    '{"orderNo":"lag-0002","dishId":1,"qty":1,"phase":"CREATED"}\n' \
    '{"orderNo":"lag-0003","dishId":1,"qty":1,"phase":"CREATED"}\n' \
    '{"orderNo":"lag-0004","dishId":1,"qty":1,"phase":"CREATED"}\n' \
    | env KAFKA_HEAP_OPTS="-Xmx64M" tools/kafka/bin/kafka-console-producer.sh \
        --topic takeout-order-events
```

### 实测三：再查 LAG（真账）

```
GROUP    TOPIC                   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
dispatch takeout-order-events    0          14              14              0
```

读解三条：

1. **offset 10 变 14**：四条真消息确实进了 topic，每条拿到递增 offset。
2. **LAG 仍是 0**：本机 dispatch 消费者追得快，岗位虽在、存货已清。什么时候 LAG 大于 0？真实场景是消费者下线、业务处理慢、或上游突发大流量；本机教学要"看见堆积"，最直接的办法是先停掉 takeaway 再发消息，LAG 立刻变大，重启后归零（练习题 3 亲手做）。
3. **LAG 是运维告警的钟**：生产里配一条定时任务或监控面板，盯住"LAG 连续十分钟大于阈值"就报警。数字本身简单，但它是 K04 两列 offset 的差值，看懂六列就看懂这条钟。

## 5. dispatch 复跑实录（同 smoke 流量）

复跑步骤一行行来（真实输出直接贴）：

```
$ TOK=$(curl -s -X POST http://127.0.0.1:8085/api/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"username":"alice","password":"123456"}' \
    | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')

$ curl -s -X POST http://127.0.0.1:8085/api/orders \
    -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
    -d '{"shopId":1,"dishId":1,"quantity":1}'
{"id":32,"orderNo":"2477c7fa-13fe-4103-b0b7-3ab1382a7aa0","status":"CREATED",...}

$ curl -s -X POST "http://127.0.0.1:8085/api/orders/2477c7fa-.../pay" \
    -H "Authorization: Bearer $TOK"
{"id":32,"status":"PAID",...}

$ sleep 3        # 给 DispatchConsumer 三秒

$ curl -s "http://127.0.0.1:8085/api/orders/2477c7fa-..." -H "Authorization: Bearer $TOK"
{"id":32,"status":"DISPATCHED","riderId":9000,"dispatchedAt":"2026-09-14T10:25:48.830Z",...}
```

读解两条：

1. **PAID 到 DISPATCHED 的三秒轮转**：状态不是 HTTP 同步改的，而是消费组在这个窗口内消费了 PAID 事件、并把状态机推进。这就是 K01 三连里"异步"二字的完整落点。
2. **[dispatch] 日志只有一行**：`[dispatch] order=2477c7fa-... -> 派给骑手 9000`。重复 PAID 事件再来，K05 三重门挡回，不打印第二行。保序、重试、幂等，三件事在这一单里全部到场。

## 6. 思考题（先想 3 分钟）

1. partition 从 1 扩到 2 时，同一个 key 的 hash 结果会挪巷。为什么"扩 partition"被视为"保序的断裂点"？生产上如何避免？
2. 同 key 保序、不同 key 无序，这两句合起来意味着什么？如果你的业务既想"同一用户的事件有序"又想"两个用户并发扩大吞吐"，key 应该填什么？
3. 毒消息反复重试为何会把整条巷道拖死？（提示：partition 内 dispatch 一次只能消费它前头的消息。）
4. LAG 长期为正但数值稳定，说明什么？LAG 突然从 20 跳到 20000 说明什么？

## 7. 练习题

1. 亲手造两条同 key 消息（console-producer, key 相同的 phase CREATED 与 PAID），再用 console-consumer 从头读，验证读到的顺冲与生产顺冲一致。贴出两条真输出。
2. 手造一条毒消息（value 不是合法 JSON、但 phase 已是 PAID、还要求有一份不存在的订单），体会"无限重试"的现象；再把监听器包一层 try-catch 记日志，比较两种行为的后果。
3. 停掉 takeaway 进程，发四条 fake 消息，观察 `--describe` 的 LAG 变化；再启动 takeaway，看 LAG 归零。贴两次 describe 的真实输出。

## 8. 参考答案

**练习 1**：按 key 同 hash 同 partition，两条消息的 offset 相邻，consumer 读到的顺序与生产顺序一致。若 key 换成不同的值，读到的相对顺序就不保证——实验一次即可证实保 helium。

**练习 2**：毒消息会用无限重试把这条巷道的消费逐条拖死。给业务包 try-catch 记日志会"放弃重试但保留 offset"（相当于 at-most-once 处理），而 `@RetryableTopic` 是"重试多次再进死信"（保 with），两种行为对应了 K05 语义表里的两行——取舍要明示。

**练习 3**：停 takeaway 后 LAG 从 0 升到 +4；重启后消费者加入 group、拉取四条、提交 offset，LAG 归零。真实输出形如：

```
（停 takeaway 期）
dispatch takeout-order-events    0          16              16？（随消息条数变）LAG= 超
（起 takeaway 后）
dispatch takeout-order-events    0          18              18              0
```

## 9. 本节小结

- **保序**：同 key 同 partition 巷内有序；不同 key 无序。业务键进 key 是保序的根。
- **重试**：默认同条重读（at-least-once），毒消息会摁死巷道；`@RetryableTopic(attempts, backoff) + @DltHandler` 可以救场。
- **LAG**：LOG-END − CURRENT。0 是完全追上，大幅为正是告警，数值稳定是小拥堵。
- **K 系列收官**：K01 三连与三件套、K02 KRaft 起停、K03 生产者、K04 消费组、K05 投递语义与幂等、K06 保序与堆积——六站已封闭成环。

## 附录 A：保序与重试、死信、LAG 的一张总图

一次"可能失败也会重试"的消费流程全部写在一行里：

```
send(topic, orderNo, payload)
    └─ 同 key → 同 partition（唯一保序线）
consumer poll
    ├─ 处理成功 → 提交 offset（LAG 收窄）
    └─ 处理失败 → offset 不前进（重试）
          └─ @RetryableTopic：至多 attempts 次、每次隔 backoff ms
                └─ 三次仍败 → {topic}-dlt（死信留档，巷道畅通）
```

**成败三轨**：正常（提交）、重试（不提交）、死信（挪库）——每一轨都有 K05 的幂等门押底（重试来了也不乱）。

## 附录 B：LAG 排障三问

| 问题 | 看哪 |对应动作 |
|---|---|---|
| LAG 稳定为小正数 | 处理速度 ≈ 产量 | 观察（正常窗口） |
| LAG 突涨过千 | consumer 挂 / 上游爆发 | 看 CONSUMER-ID 有无、启停逸漏 |
| LAG=0 但业务说"没收到" | offset 提交早于业务生效（重复消费落库） | K05 幂等审计 |

## 附录 C：@RetryableTopic 与手写重试的取舍

| 形态 | 优点 | 必注意 |
|---|---|---|
| `@RetryableTopic` 一次配齐（attempts/backoff/DLT） | 几乎零代码 | 自动动伴 DLT topic（命名与运维要知情） |
| 手写 try-catch + 短轮询（本节简化版思路） | 全在明处 | 没 DLT 时要自己写死信消费或即刻放弃 |

教学统一口径：**知道手写可以，但生产推荐一次配齐的注解版**——重试的"延迟、上限、死信"三件合并配置，事实双轨清晰。

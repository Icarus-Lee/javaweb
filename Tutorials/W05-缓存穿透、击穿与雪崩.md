**本站名词卡**

| 名词 | 英文 | 一句人话 | 在本项目哪里见到 |
|---|---|---|---|
| cache-aside | 旁路缓存 | 先问缓存，没有再查库并回填 | `menu()` 主体 |
| TTL | time to live | 缓存的保质期（秒） | 60s（有货）/ 30s（空哨兵） |
| 缓存穿透 | penetration | 查**不存在**的数据，每次都打穿到库 | 恶意刷 shopId=1134 |
| 空哨兵 | null sentinel | 用一个占位值把"查过了，没有"记下来 | `"\u0000"` |
| 缓存击穿 | breakdown | **热点 key 过期瞬间**，并发全打到库 | 菜单 60s 到期的一瞬 |
| 缓存雪崩 | avalanche | 大批 key **同时**过期，库被集体打穿 | 所有店同时 0 点过期 |
| 回源 | origin fetch | 缓存未命中，去数据库取数 | `dishes.findByShopId(shopId)` |

## 1. 生活类比与动机：前台备一份常见问题清单

顾客问"店 1 有什么菜"，前台（后端）没必要每次都跑进档案室（H2）翻账本——桌上的便签（Redis）写着答案，60 秒内直接照念。三个新问题随之而来：

1. 顾客问了一家**根本不存在的店**——便签上没写，前台每次都得白跑档案室（**穿透**）；
2. 便签**刚好过期的瞬间**，十个顾客同时问——十个人同时冲进档案室（**击穿**）；
3. 午夜零点所有便签**同时作废**——第二天开门全体顾客集体冲档案室（**雪崩**）。

`menu()` 这 21 行，就是把这三件事一起想到的产物。

## 2. 全件走查（MenuController.java:28-46）

```java
@GetMapping("/{shopId}")
public Object menu(@PathVariable Long shopId) {
    String key = "takeaway:menu:" + shopId;
    String cached = redis.opsForValue().get(key);                    // ① 先问缓存
    if ("\u0000".equals(cached)) return List.of();                   // ② 空哨兵：秒回空菜单
    if (cached != null) {                                            // ③ 命中：直接用
        try { return om.readValue(cached, List.class); } catch (Exception ignored) {}
    }
    List<Dish> menu = dishes.findByShopId(shopId);                   // ④ 未命中：回源查库
    String json;
    try { json = om.writeValueAsString(menu); }
    catch (Exception e) { throw new RuntimeException(e); }
    if (menu.isEmpty()) {
        redis.opsForValue().set(key, "\u0000", Duration.ofSeconds(30));   // ⑤ 空结果→写哨兵 30s
    } else {
        redis.opsForValue().set(key, json, Duration.ofSeconds(60));       // ⑥ 有货→写 JSON 60s
    }
    return menu;
}
```

逐格讲：

- **①③ 的命中路径**：存的是 JSON 字符串，取出来反序列化。为什么存 JSON 不存 Java 对象？Redis 序列化器配 JDK 序列化会有兼容性问题，字符串 + Jackson 是最直白、跨语言可见的方案（`redis-cli GET` 能直接看内容）。
- **② 的哨兵值 `\u0000`**：Unicode 的 NULL 字符。选它当"空标记"是因为**合法菜单 JSON 永远不会等于这个单字符**——不用额外字段就区分了"没货的店"和"没缓存"。代价：`redis-cli GET` 看到的是不可见字符（本站实验里有 xxd 实锤）。
- **⑤ 的 30 秒 vs ⑥ 的 60 秒**：空结果保质期更短——店家可能刚上架新菜单，30 秒后重新查库给"新店"翻案机会。**防御穿透与数据新鲜度的折中**。
- **③ 的 try-catch ignored**：缓存内容损坏时不炸接口，当作未命中继续走回源——**缓存的任何问题都不能影响可用性**，这是缓存代码的底线姿态。

## 3. 招牌实验：空哨兵防穿透实测（2026-09-14 本机实录）

### 实验设计

店 1134 不存在。先删掉可能的旧缓存，然后连查三次，用 curl 的 `%{time_total}` 记录每次耗时。

### 实测过程

```
$ redis-cli -p 6379 DEL takeaway:menu:1134        # 清场
$ redis-cli -p 6379 DEL takeaway:menu:1

$ curl -s -o /dev/null -w "status=%{http_code} 耗时=%{time_total}s\n" \
    "http://127.0.0.1:8085/api/menus/1134"
status=200 耗时=0.003570s                          ← 第 1 次：回源查库 + 写哨兵

$ curl -s -o /dev/null -w "..." "http://127.0.0.1:8085/api/menus/1134"
status=200 耗时=0.001637s                          ← 第 2 次：命中哨兵秒回

$ curl -s -o /dev/null -w "..." "http://127.0.0.1:8085/api/menus/1134"
status=200 耗时=0.001346s                          ← 第 3 次：仍然哨兵秒回
```

**注意**：本机 H2 与 Redis 都在 localhost，回源只慢 2 毫秒——单机演示里差距小。**放大到真实环境**：数据库在另一台机器（+2ms 网络）且慢查询 50ms、QPS 1000 时，没有哨兵 = 每秒 1000 次全量查库打满连接池；有哨兵 = 1000 次查询全变 Redis GET（约 0.1ms）。**穿透防御的价值 = （回源成本 - 缓存成本）× 攻击 QPS**。

### 看看哨兵在 Redis 里长什么样

```
$ redis-cli -p 6379 GET takeaway:menu:1134 | xxd
00000000: 000a                                     ← \u0000 + 换行（cli 显示）

$ redis-cli -p 6379 TTL takeaway:menu:1134
30                                                  ← 空哨兵 TTL=30s
$ redis-cli -p 6379 TTL takeaway:menu:1
60                                                  ← 正常菜单 TTL=60s（新写的）
```

### 对照组：正常店的 cache-aside

```
$ curl -s -o /dev/null -w "shop1 第1次 耗时=%{time_total}s\n" 127.0.0.1:8085/api/menus/1
shop1 第1次 耗时=0.004243s       ← 回源
$ curl -s -o /dev/null -w "shop1 第2次 耗时=%{time_total}s\n" 127.0.0.1:8085/api/menus/1
shop1 第2次 耗时=0.002410s       ← 命中缓存
```

同一个模式复现两遍：**第一次贵（回源+回填），第二次便宜**——这就是 cache-aside 的全部经济学。

### 附加实验：哨兵会过期"翻案"

```
$ redis-cli -p 6379 SET takeaway:menu:1134 "x"     # 手工制造一个错误缓存
$ curl -s 127.0.0.1:8085/api/menus/1134            # 反序列化失败→走回源
[]                                                  ← 自动纠正！
$ redis-cli -p 6379 GET takeaway:menu:1134 | xxd
00000000: 000a                                     ← 又写回正确哨兵
```

`catch (Exception ignored)` 那一行的价值当场兑现：**脏缓存自愈**。

## 4. 三大问题对照表格

| | 穿透 penetration | 击穿 breakdown | 雪崩 avalanche |
|---|---|---|---|
| 一句话 | 查**不存在**的数据，缓存永远不命中 | **单个热点 key** 过期瞬间并发全打库 | **大批 key 同时**过期（或 Redis 整体宕机） |
| 打库规模 | 持续（每请求都打） | 尖峰（一瞬间的高并发） | 洪峰（全站级别的尖峰） |
| 攻击者是谁 | 常是恶意扫描/爬虫（乱造 id） | 正常用户（热点恰好过期） | 正常用户 + 运维失误（统一 TTL） |
| 本项目的对应物 | 刷 `/menus/1134`（不存在的店） | `takeaway:menu:1`（爆款店）60s 到期瞬间 | 所有店的菜单 key 都是 60s，若同时写入将同时到期 |
| 防御手段 | **空哨兵**（本项目）；参数校验（shopId<=0 直接拒）；布隆过滤器 | 互斥重建（只放一个请求回源，其他等）；热点 key 逻辑过期不设 TTL | TTL 加随机抖动（60±10s）；多级缓存；Redis 高可用（哨兵/集群） |
| 防御成本 | 一行 set（本项目已做） | 加锁逻辑（略复杂） | 一行随机数（简单但易忘） |

**记法**：穿透防"假 id"，击穿防"单点过期"，雪崩防"集体过期"。三者共同点都是"库被打"，差异只在**打过来的方式**。

### 各配一个一分钟小实验

- **穿透**：本站第 3 节（1134 两次对比）。
- **击穿**：`redis-cli DEL takeaway:menu:1` 后立刻 `for i in $(seq 1 20); do curl .../menus/1 & done`——20 个请求在缓存空窗同时到达，全是回源（`logs/takeaway.log` 里看不到计数，但可用 H2 查询日志/慢日志佐证）。修复思路（互斥锁）在练习 M。
- **雪崩**：`for s in 1 2 3; do redis-cli SETEX takeaway:menu:$s 60 "$(curl -s 127.0.0.1:8085/api/menus/$s)"; done` 同一秒写入 → 60 秒后同时过期。防抖一行：`Duration.ofSeconds(60 + ThreadLocalRandom.current().nextLong(20))`。

## 6. 附：缓存代码的"通用骨架"与本项目的退化版

### 6.1 把 menu() 抽象成 cache-aside 通用骨架

任何缓存接口都长这个样子（伪代码）：

```
function cachedRead(key, ttl, originQuery):
    v = redis.get(key)
    if v == NULL_SENTINEL:  return EMPTY          # ① 哨兵短路（防穿透）
    if v != null:          return deserialize(v)  # ② 命中
    v = originQuery()                              # ③ 回源（击穿点：这里应加互斥锁）
    if v is empty:
        redis.set(key, NULL_SENTINEL, ttl / 2)     # ④a 空值短 TTL
    else:
        redis.set(key, serialize(v), ttl + jitter) # ④b 抖动 TTL（防雪崩）
    return v
```

对照本项目 menu()：①②③④ 全有，**缺的只有两样**——③ 的互斥锁（击穿防御，练习 M）和 ④b 的 TTL 抖动（雪崩防御，一行随机数）。也就是说：**你已经掌握了 80 分的缓存骨架**，剩下 20 分是两行代码的攻防意识。

### 6.2 缓存一致性：什么时候失效，什么时候等过期

menu() 只有被动过期（TTL 到了重新查库）。完整的 cache-aside 还要回答"**写路径**怎么办"：

| 策略 | 做法 | 一致性窗口 | 本项目适用吗 |
|---|---|---|---|
| 只靠 TTL | 写库后不管缓存 | 最长 60s（菜单可接受） | ✅ 现状 |
| 写时删除 | 写库后 `DEL key` | 下次读即新 | 有写入口后应加 |
| 写时更新 | 写库后重算并 SET | 几乎实时 | 计算贵时不划算 |
| 延迟双删 | 删→写库→延迟再删 | 防并发读旧回填 | 复杂度高，慎用 |

菜单是"读极多、写极少"的极端，TTL 60s 的窗口业务完全无感——**一致性强度要匹配业务容忍度**，这是缓存选型的第一性原理（订单状态就绝不能这么干，因为它是强一致数据——所以 W02 里订单从不进缓存，库存放 Redis 是因为 Redis 本身是"真相源"而非缓存）。

### 6.3 命中率观测（上线后怎么知道缓存有没有用）

本项目没配监控，但一行命令可粗测：

```
$ redis-cli -p 6379 INFO stats | grep -E "keyspace_hits|keyspace_misses"
keyspace_hits:128
keyspace_misses:14
# 命中率 = 128 / (128+14) ≈ 90%
```

（数字含 demo-counter 等其他 key 的读写，教学粗估即可。）生产上应按前缀分指标：`takeaway:menu:*` 的命中率单独统计——命中率骤降往往是"批量过期/被清库/写放大"的信号，是雪崩的前兆报警。

### 6.4 与 train 的对照：同一个 Redis，两种角色

| | takeaway 菜单缓存 | train 余票 |
|---|---|---|
| Redis 的身份 | **缓存**（H2 才是真相） | **真相源**（H2 只有初始值） |
| 丢数据后果 | 重新查库，无损 | 余票错乱，超卖 |
| TTL | 60s/30s | 无 TTL（永不过期） |
| 写路径 | 无（读多写少） | DECR/INCR 高频原子写 |

同一个中间件，因数据性质不同扮演完全不同的角色——**先问"这是缓存还是真相"，再决定要不要 TTL、要不要防穿透**。给真相源加 TTL 是新手最常见的自毁操作（余票 60 秒后消失，所有人都能白买票）。

## 7. 思考题

1. 空哨兵为什么不用空字符串 `""` 而用 `\u0000`？（提示：`""` 和"缓存了一个空列表的 JSON"如何区分？）
2. 哨兵 TTL 30 秒内，店家真的上架了菜——顾客多久后能看到？这个延迟可接受吗？怎么改进？
3. `menu()` 是**写代码时**查库（cache-aside），菜单数据什么时候会变？没有"写时失效缓存"逻辑，顾客最长要等 60 秒才看到改价——要不要加？
4. 布隆过滤器（Bloom Filter）防穿透的原理一句话？它和空哨兵比，各赢在哪？

## 8. 练习（H/F/M 三层）

- **H（热身）**：重跑第 3 节全部命令，把三次耗时和两个 TTL 抄进笔记；再用 xxd 确认哨兵字节。
  验收：第 2/3 次耗时 < 第 1 次；哨兵 TTL=30。
- **F（进阶）**：给 menu() 加参数校验：shopId ≤ 0 直接抛 IllegalArgumentException，根本不碰 Redis。
  验收：`curl .../api/menus/-1` 不产生任何 Redis key（`redis-cli KEYS 'takeaway:menu:*'` 验证）。
- **M（硬核）**：实现击穿防御——回源前用 `redis.opsForValue().setIfAbsent(key+":lock", "1", Duration.ofSeconds(3))` 抢互斥锁；抢到的回源+回填，没抢到的 sleep 50ms 后重读缓存（最多重试 5 次）。
  提示：参照 train 的 `book()` 分布式锁写法（BookingService.java:37 附近）；finally 释放锁。
  验收：DEL 缓存后 20 并发 curl，H2 查询只发生 1 次（加查询计数日志验证）。

### 参考答案要点

- 思考 1：空串是合法 JSON 序列化的边界产物，且"空菜单"语义应显式区分"没这家店"；`\u0000` 不可能出现在序列化菜单里，零成本无歧义。
- 思考 2：最多 30 秒。对菜单场景可接受；不可接受时用"上架事件主动删 key"（cache 旁路失效）替代被动过期。
- 思考 3：改价入口（未来会有店铺管理端）应在写库后 `DEL takeaway:menu:{shopId}`——写时失效让一致性从"分钟级"提到"实时"。本项目没有写入口所以省了，**一旦加了写路径必须补**。
- 思考 4：布隆过滤器用一个位数组+多哈希函数回答"这个 id **一定不存在**（或可能存在）"，内存 O(1) 挡住海量假 id；空哨兵实现简单但要为每个假 id 存一个 key（可被随机 id 海量刷爆）。海量假 id 用布隆，少量重复假 id 用哨兵足够。

## 9. 附一：本机实验的"放大镜"——把毫秒差换算成生产数字

本机 localhost 实测：回源 3.6ms vs 哨兵 1.3ms，差距 2.3ms——看着寒酸。教学要诚实：**这个数字必须做一次换算才有意义**。假设真实生产拓扑：

- 数据库在独立机器：每查询 +2ms 网络往返；
- 菜单查询是一个中等复杂度的联表（教学里 findByShopId 是单表，生产常带 分类/评分/边栏聚合）：50ms；
- 假设峰值 QPS 1000（中型外卖站点级）。

| | 无空哨兵（每请求都回源） | 有空哨兵 |
|---|---|---|
| 单次恶意请求成本 | 52ms DB 时间 | 1ms Redis |
| 1000 QPS 打击下 DB 压力 | 1000 次/秒全量查询 → **连接池（默认 10）立刻耗尽** | 0 次 DB 查询 |
| 正常用户受到的牵连 | 全站 500（连接池被恶意流量吃光） | 完全无感 |
| Redis 压力 | 同样 1000 QPS（查了也没用） | 1000 QPS GET（Redis 单机可扛 10 万 QPS） |

**换算结论**：2.3ms 的本机差距 × QPS 1000 = 每秒 2.3 秒的"数据库秒数"——数据库 1 秒只有 1 秒。**缓存防御买的不是速度，是数据库的命。**

这个换算还揭示了防御的**经济本质**：穿透攻击是一场"成本不对称"竞赛——攻击方每个请求成本（带宽+脚本）低于防守方每个请求成本（DB 查询）时，攻击总是赚的；哨兵/布隆过滤器把防守成本降一个数量级，不对称反转，攻击变得不经济。

## 本节小结
- cache-aside 四步：问缓存→哨兵短路→回源→回填；两种 TTL（空 30s/有货 60s）是防御与新鲜的折中。
- 实测：1134 回源 3.6ms → 哨兵 1.3ms；单机差距小，放大 QPS 后差距千倍——穿透防御买的是"数据库活着"。
- 三大问题：穿透（假 id）、击穿（单点过期）、雪崩（集体过期）；本项目已防第一个，后两个各留了实验与修法。
- `catch ignored` 让脏缓存自愈——缓存代码永远不能让主流程挂。

## 1. 一句人话开场

顾客问"店 1 有什么菜"，前台没必要每次跑档案室——桌上的便签（Redis）60 秒内直接照念。三件事随之：不存在的店每次白跑（穿透）；便签刚好过期的一瞬十个人同时冲档案室（击穿）；零点全员便签作废集体冲（雪崩）。

## 2. 全件走查（MenuController.java:28-46）

```java
@GetMapping("/{shopId}")
public Object menu(@PathVariable Long shopId) {
    String key = "takeaway:menu:" + shopId;
    String cached = redis.opsForValue().get(key);                    // ① 先问缓存
    if ("\u0000".equals(cached)) return List.of();                   // ② 空哨兵：秒回空菜单
    if (cached != null) {                                            // ③ 命中：直接用
        try { return om.readValue(cached, List.class); } catch (Exception ignored) {}
    }
    List<Dish> menu = dishes.findByShopId(shopId);                   // ④ 未命中：回源查库
    String json;
    try { json = om.writeValueAsString(menu); } catch (Exception e) { throw new RuntimeException(e); }
    if (menu.isEmpty())
        redis.opsForValue().set(key, "\u0000", Duration.ofSeconds(30));  // ⑤ 空结果→哨兵 30s
    else
        redis.opsForValue().set(key, json, Duration.ofSeconds(60));      // ⑥ 有货→JSON 60s
    return menu;
}
```

- **② 的 `\u0000`**：合法菜单 JSON 永远不等于这个单字符——一个字段都不加就区分了"没货的店"与"没缓存"。代价是 `redis-cli GET` 看到不可见字符。
- **⑤ 30s vs ⑥ 60s**：空结果保质期更短——新店上架菜单后 30 秒内翻案。防穿透与新鲜度的折中。
- **③ 的 catch ignored**：缓存内容损坏当未命中回源——**缓存的问题不能影响可用性**。

## 3. 工程实录：200 连发两种姿势——flood 与守坝（2026-09-15 真机实录）

攻击工具就一个 curl + xargs -P8（手搓潮水，零依赖）。

### 3.1 实测一：重复假 id 的洪流（都命中同一哨兵）

```text
$ redis-cli -p 6379 DEL takeaway:menu:1134      # 清场（首轮要写一次哨兵）
$ T0=$(date +%s.%N)
$ seq 200 | xargs -P 8 -I{} curl -s -o /dev/null -w "%{http_code}\n" \
    "http://127.0.0.1:8085/api/menus/1134" | sort | uniq -c
    200 200
$ python3 -c "print('Round A total: %.3fs -> RPS=%.1f'%(...)）"
Round A total: 0.433s → RPS≈461     （含首轮回源+设哨兵）
# 哨兵已就位后再跑一轮：
Round A2 total: 0.150s → RPS≈1332
```

### 3.2 实测二：随机假 id 的穿透洪流（对照组）

```text
$ BEFORE=$(redis-cli INFO commandstats | grep '^cmdstat_set:' | grep -o 'calls=[0-9]*')  # → 202
$ python3 -c "for i in range(200): print(30000+i)" \
    | xargs -P 8 -I{} curl -s -o /dev/null "http://127.0.0.1:8085/api/menus/{}"
Round B total: 0.286s → RPS≈700
$ AFTER=... （→ 402）
set 次数差 = 402 - 202 = 200      ← 每个请求都向 Redis 写了一个 sentinel key！
$ redis-cli KEYS 'takeaway:menu:3*' | head -3
takeaway:menu:30000 / takeaway:menu:30001 / ...（200 个残留哨兵键）
```

### 3.3 对账结论（本章核心增量）

| | Round A2（同一假 id，哨兵在位） | Round B（随机假 id） |
|---|---|---|
| RPS（本机） | ≈1332 | ≈700 |
| H2 查询 | 0 | 200 次/轮 |
| Redis SET | **0** | **200 次/轮** |
| 残留垃圾 | 无 | 每个唯一假 id 留一个键 |

三个结论：① **穿透的代价不只是慢**（700 vs 1332 只差 2 倍），而是**每请求一次 DB + 每请求一次写**——放大到 1000 QPS 时 connections 池与 Redis 的内存（每键 ~50B × 无限的假 id）双双失守；② 重复 id 的洪流几乎免费——**哨兵是一个"假 id 一个"的字典**，重复攻击它全免；随机假 id 洪流才逼出布隆过滤器（思考 4）；③ 实习后清场：`redis-cli -p 6379 -c "eval"` 不必——`KEYS 'takeaway:menu:3*'` 拿清单后 DEL，或等这批键 30s 自然过期（TTL 是哨兵的第三重福利：**防穿透不等于给攻击者留垃圾场**——30s 过期自动清污）。

### 3.4 单发对照：回源 vs 秒回

```text
$ redis-cli DEL takeaway:menu:30005
$ curl -o /dev/null -w "穿透首次(回源+写哨兵): %{time_total}s" /api/menus/30005 → 0.0036s
$ curl -o /dev/null -w "穿透二次(哨兵):     %{time_total}s" /api/menus/30005 → 0.0016s
$ redis-cli GET takeaway:menu:30005 | xxd → 000a      ← \u0000 + 换行
$ redis-cli TTL takeaway:menu:30005 → 30              ← 空哨兵 TTL=30s
```

**诚实换算**：本机回源只慢 2ms；放大到生产（DB 独立机器 + 慢查询 50ms、QPS 1000），无哨兵 = 每秒 1000 次全量查库打满连接池，有哨兵 = 全变 Redis GET。**穿透防御的价值 = （回源成本 - 缓存成本）× 攻击 QPS**。

### 3.5 脏缓存自愈一行

```text
$ redis-cli SET takeaway:menu:1134 "x"
$ curl /api/menus/1134 → []              ← 反序列化失败→回源自动纠正
$ redis-cli GET takeaway:menu:1134 | xxd → 000a  ← 写回正确哨兵
```

`catch (Exception ignored)` 的价值当场兑现。

### 3.6 清场纪律（本站常见垃圾键怎么收拾）

Round B 射出 200 个随机 id，就留下 200 个哨兵键。收拾三招（按优雅排序）：

```text
1. 等 TTL 自然过期：空哨兵 30 秒到期自动消失——哨兵的"防穿透不丢垃圾"福利；
2. 手工清场：redis-cli KEYS 'takeaway:menu:3*' 拿清单后 DEL（演示总量可控时最快）；
3. 生产姿势：批量对话用 SCAN（生产禁 KEYS ——O(N) 阻塞 Redis），配 TTL 兜底。
```

这不是洁癖：**垃圾键 = 攻击流量走后留下的内存足迹**——武器化的穿透会故意写满哨兵把 Redis 顶到 maxmemory 淘汰真缓存。30 秒短 TTL 是"垃圾场自动清理"的合同条款。

## 4. 穿透 / 击穿 / 雪崩对照表

| | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 一句话 | 查**不存在**的数据，缓存永不命中 | **单热点 key** 过期瞬间并发全打库 | **大批 key 同时**过期 |
| 打库规模 | 持续 | 尖峰 | 洪峰 |
| 谁攻击 | 恶意扫描乱造 id | 正常用户（热点恰好过期） | 用户 + 运维失误（统一 TTL） |
| 本项目对应物 | 刷 /menus/1134 | takeaway:menu:1 到期一瞬 | 所有店菜单同 60s 同时到期 |
| 防御 | 空哨兵/参数校验/布隆 | 互斥重建/逻辑过期 | TTL 随机抖动/多级缓存/高可用 |
| 成本 | 一行 set | 加锁逻辑 | 一个随机数（易忘） |

**记法**：穿透防"假 id"，击穿防"单点过期"，雪崩防"集体过期"。

## 5. 通用骨架与本项目的缺省版

```text
function cachedRead(key, ttl, originQuery):
    v = redis.get(key)
    if v == NULL_SENTINEL: return EMPTY        # ① 哨兵短路（本项目有）
    if v != null: return deserialize(v)        # ② 命中（本项目有）
    v = originQuery()                          # ③ 回源（缺：互斥锁＝击穿防御）
    if v is empty: redis.set(key, SENTINEL, ttl/2)   # ④a 空 TTL 短（本项目有）
    else: redis.set(key, serialize(v), ttl+jitter)   # ④b 缺：抖动＝雪崩防御
```

骨架读法：**你已经掌握 80 分的缓存骨架**，缺的两样各是两行代码的攻防意识；练习 M 补互斥、雪崩抖动一行 `Duration.ofSeconds(60 + ThreadLocalRandom.current().nextLong(20))`。

### 5.1b 本机毫秒差的"放大镜"换算（诚实版）

本机回源 3.6ms vs 哨兵 1.6ms，差 2ms——单机寒酸。教学要诚实：**这个数字必须做一次换算才有意义**。假设生产拓扑：DB 独立机器（+2ms 网络）、菜单查询是中复杂度联表（50ms）、峰值 QPS 1000：

| | 无空哨兵（每请求回源） | 有空哨兵 |
|---|---|---|
| 单次恶意请求成本 | 52ms DB 时间 | 1ms Redis |
| 1000 QPS 下 DB | 1000 次/秒全量查询 → **连接池（默认 10）立刻耗尽** | 0 次 DB 查询 |
| 正常用户牵连 | 全站 500 | 完全无感 |
| Redis 压力 | 1000 QPS 白查 | 1000 QPS GET（单机 10 万 QPS 扛得住） |

**换算结论**：2ms × QPS 1000 = 每秒 2 秒的"数据库秒数"——数据库 1 秒只有 1 秒。**缓存防御买的不是速度，是数据库的命。** 穿透攻击还是一场成本不对称竞赛：攻击方每请求成本低于防守方每请求成本时攻击总赚；哨兵/布隆把防守成本降一个数量级，不对称反转、攻击变得不经济。

### 5.2 缓存一致性：写路径的四档（什么时候失效，什么时候等过期）

| 策略 | 做法 | 一致性窗口 | 本项目适用吗 |
|---|---|---|---|
| 只靠 TTL | 写库后不看缓存 | 最长 60s（菜单可接受） | ✅ 现状 |
| 写时删除 | 写库后 `DEL key` | 下次读即新 | 有写入口后应加 |
| 写时更新 | 写库后重算并 SET | 近实时 | 计算贵时不划算 |
| 延迟双删 | 删→写→延迟再删 | 防并发读旧回填 | 复杂度高慎用 |

菜单是"读极多写极少"的极端——**一致性强度要匹配业务容忍度**，这是缓存选型的第一性原理。订单状态绝不能这么干（强一致数据）；库存放 Redis 是因为 Redis 本身是真相源而非缓存。

### 5.3 命中率观测（上线后怎么知道缓存有没有用）

```text
$ redis-cli -p 6379 INFO stats | grep -E "keyspace_hits|keyspace_misses"
keyspace_hits:128
keyspace_misses:14        # 命中率 ≈ 128/(128+14) ≈ 90%
```

（数字含 demo-counter 等其他键的读写，粗估即可。）生产按前缀分指标：`takeaway:menu:*` 命中率单独统计——**命中率骤降往往是批量过期/被清库/写放大的信号，是雪崩的前兆报警**。

### 5.4 与 train 的对照：同一个 Redis，两种角色

| | takeaway 菜单缓存 | train 余票 |
|---|---|---|
| Redis 的身份 | **缓存**（H2 才是真相） | **真相源**（H2 只有初始值） |
| 丢数据的后果 | 重新查库，无损 | 余票错乱，超卖 |
| TTL | 60s/30s | 无 TTL（永不过期） |
| 写路径 | 无（读多写少） | DECR/INCR 高频原子写 |

**先问"这是缓存还是真相"，再决定要不要 TTL、要不要防穿透**——给真相源加 TTL 是新手最常见的自毁操作（余票 60 秒后消失，所有人都能白买票）。

### 5.5 击穿/雪崩各配一分钟小实验（对照表的正餐）

- **击穿**：`redis-cli DEL takeaway:menu:1` 后立刻 `for i in $(seq 1 20); do curl -s -o /dev/null .../menus/1 & done`——20 个请求在缓存空窗同时回源。本站实录的连发技巧（xargs -P）就是这味药的加强版。
- **雪崩**：`for s in 1 2 3; do redis-cli SETEX takeaway:menu:$s 60 "$(curl -s .../menus/$s)"; done` 同一秒写入 → 60 秒后同时过期。防抖一行（上面 5.1）。

## 7. 思考题

1. 空哨兵为什么不用空字符串 ""？（""与"缓存了空列表 JSON"如何区分？）
2. 哨兵 30 秒内店家真上架了菜，顾客多久能看到？可接受吗？怎么改？
3. menu() 没有"写时失效缓存"——改价后最长 60 秒旧价。要不要加？
4. 布隆过滤器防穿透的原理一句话？与空哨兵各赢在哪？

### 参考答案要点

1：空串可能是合法序列化的边界产物；`\u0000` 不可能出现在菜单 JSON 里，零成本无歧义。
2：最多 30 秒；不可接受就"上架事件主动删 key"（cache 旁路失效）替代被动过期——一致性从分钟级提到实时，代价是要有事件源。
3：写路径一旦存在必须补 DEL；本项目没有写入口所以省了，**一旦加了写路径必须补**——这是"教学裁剪要显式标注"的另一例（W06 空缺地图的同族纪律）。
4：位数组+多哈希回答"一定不存在（或可能存在）"，O(1) 挡海量假 id；空哨兵实现简单但每个假 id 存一个 key（可被海量随机 id 刷爆）。海量假 id 用布隆，少量重复假 id 哨兵足矣（本实录 Round A/B 正是两种输入形状的活例子）。

## 9. 本节小结

- cache-aside 四步：问缓存→哨兵短路→回源→回填；空 30s / 有货 60s 是防御与新鲜的折中。
- 实录：重复假 id 的洪流被哨兵挡成"0 写 0 查"（RPS 翻倍一倍），随机假 id 的穿透每个请求都要 DB+写——两轮实测就是攻防的层数差。
- 穿透/击穿/雪崩是"库被打"的三种姿势；哨兵已防第一，后两个留了实验与修法。
- catch ignored 让脏缓存自愈——缓存代码永远不能让主流程挂。

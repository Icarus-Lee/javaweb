## 1. 概念最小人话 + 一句动机

状态机即自动售货机的投币口：**没投币按出货键没反应**。transition() 来一个"到 XX 状态"的请求，先查"当前状态→目标状态"这条边在不在轨道图里，不在就**当场拒绝**。

```java
// 三种写法对比（A/B 都是反面教材）
if (o.status.equals("CREATED")) { ... }                        // A：规则散在 4 个方法里
if (!o.isPaid && !o.isCanceled) { ... }                        // B：5 个布尔 32 种组合
if (!LEGAL_NEXT.contains(o.status + "-" + to)) throw ...       // C：全图一眼看全（本项目）
```

白名单三个胜点：**集中**（评审时一眼看出缺的边）、**默认拒绝**（忘加新边的结果是拒绝而非放行——fail-safe 方向正确）、**测试友好**（枚举非法组合就是完整状态机测试）。

## 2. 白名单逐条解读（OrderService.java:20-21）

```java
private static final Set<String> LEGAL_NEXT = Set.of(
        "CREATED-PAID", "PAID-DISPATCHED", "DISPATCHED-DELIVERED",
        "CREATED-CANCELED", "PAID-CANCELED");
```

| 边 | 触发者 | 联动动作 | 在哪个接口 |
|---|---|---|---|
| CREATED→PAID | 顾客支付 | Redis 扣库存 + 发 PAID 事件 | `POST /orders/{no}/pay` |
| PAID→DISPATCHED | 派单消费者 | riderId=9000 + dispatchedAt | Kafka 消费（W03） |
| DISPATCHED→DELIVERED | 骑手确认 | deliveredAt | `POST /rider/{no}/deliver` |
| CREATED→CANCELED | 顾客取消 | （无库存联动——思考 1） | `POST /orders/{no}/cancel` |
| PAID→CANCELED | 顾客取消 | （W06 讨论回不回库存） | 同上 |

**刻意缺席的边**：`CREATED→DISPATCHED`（没付钱就派单=白派）；`CANCELED→任何`（撕掉的单不复活）；`DELIVERED→CANCELED`（只能退款）；`PAID→DELIVERED`（跳过派单破坏完整性）；`PAID→REFUNDED`（**还没写**，W06 的作业）。

`transition()` 只管拓扑，不管"谁来按的按钮"——权限校验（是不是你的单、是不是骑手）在 Controller 层。**状态机管流程，权限管人**，两层正交。

## 3. pay() 全流水走查（OrderService.java:67-81）

```java
public Order pay(Long userId, String orderNo) {
    Order o = orders.findByOrderNo(orderNo)                          // ① 查单
            .orElseThrow(() -> new IllegalStateException("订单不存在"));
    if (!o.userId.equals(userId))                                    // ② 归属校验
        throw new IllegalStateException("不是你的订单");
    transition(o, "PAID");                                           // ③ 状态机放行
    o.paidAt = Instant.now();
    Long left = redis.opsForValue()                                  // ④ Redis 乐观扣减
            .decrement("takeaway:dish:" + o.dishId + ":stock");
    if (left != null && left < 0) {                                  // ⑤ 扣穿了→补回+拒绝
        redis.opsForValue().increment("takeaway:dish:" + o.dishId + ":stock");
        throw new IllegalStateException("库存不足，请稍后再试");
    }
    producer.orderCreated(o.orderNo, o.dishId, o.quantity, "PAID");  // ⑥ 广播事实
    return orders.save(o);                                           // ⑦ 落库
}
```

- **④⑤ 乐观扣减**：DECR 是 Redis 单线程原子操作；扣成负数说明超额，INCR 补回再抛异常。比"先 GET 判断再 DECR"少一个竞态窗口。
- **⑤ 抛异常时 ③ 改的状态去哪了？** transition 只改内存对象；异常让 @Transactional 回滚，H2 里 status 不变。但 **Redis 不跟着回滚**——所以必须手动 INCR。跨系统没有大事务，各自负责自己的回滚（W06 正题）。

## 4. 工程实录：直接调 transition，把"不同 to 状态"全量实测（2026-09-15 完整 diff 与输出）

transition() 是 Service 方法，HTTP 接口只露出它的 3 条边（pay/cancel/deliver）。想**直接**对着白名单上压力，就做一个 11 行的教学实验端点。

### 4.1 完整 diff（OrderController.java，临时实验用，验完撤回）

```diff
+    /** 教学实验端点（W04）：不落库地试一把状态机，看各 to 的返回。 */
+    @GetMapping("/orders/{orderNo}/try-to/{to}")
+    public Map<String, Object> tryTo(@PathVariable String orderNo, @PathVariable String to) {
+        Order o = service.find(orderNo);
+        String from = o.status;
+        try {
+            service.transition(o, to);
+            return Map.of("ok", true, "from", from, "to", to, "now", o.status);
+        } catch (IllegalStateException e) {
+            return Map.of("ok", false, "from", from, "to", to, "rejected", e.getMessage());
+        }
+    }
```

设计要点：① 没加 @Transactional、**不 save**——内存里试，库里不脏；② 异常直接改成 JSON 返回而不是抛 500——我们要看的是"规则怎么说话"，不是"HTTP 怎么回包"；③ 每个请求独立查单——from 干净。

### 4.2 实测矩阵（真机输出原样）

对一单 `status=CREATED` 的订单逐个 to 打一遍：

```text

$ ... /try-to/DISPATCHED
{"from":"CREATED","to":"DISPATCHED","ok":false,

$ ... /try-to/DELIVERED
{"from":"CREATED","to":"DELIVERED","ok":false,

$ ... /try-to/REFUNDED
```

换 `status=CANCELED` 的订单再打 4 个 to（其中 PAID/CANCELED/REFUNDED/DELIVERED）：

**读法**：`CANCELED -> PAID` 的拒绝由真枪接口出（500 + 日志原文 `IllegalStateException: 非法状态流转: CANCELED -> PAID`），实验端点则把**每一条缺席边的拒绝文案**结构化返回。两套测试结论一致：白名单 = 5 条边放行 + 31 条拒绝，拐骗无一处漏网。**矩阵表**（✓ 放行 / ✗ 拒绝）：

| CREATED | ✓ | ✗ | ✗ | ✓ | ✗ |
| PAID | — | ✓ | ✗ | ✓ | ✗（W06 会加） |
| DISPATCHED | ✗ | — | ✓ | ✗ | ✗ |
| DELIVERED | ✗ | ✗ | ✗ | ✗ | ✗ |

### 4.3 真枪解剖："知识内 500"的回包与日志

用真实接口对 CANCELED 单调 pay：

```text
$ curl -s -i -X POST "127.0.0.1:8085/api/orders/$ON/pay" -H "Authorization: Bearer $TOK" | sed -n '1p;$p'
HTTP/1.1 500
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/api/orders/xxx/pay"}
$ grep "非法状态流转" logs/takeaway.log | tail -1 | cut -c1-170
java.lang.IllegalStateException: 非法状态流转: CANCELED -> PAID
```

三个值得品的细节：① 500 而非 400/409——`IllegalStateException` 没被全局处理器映射，走兜底（改进方向 409 + 业务话术，练习 M）；② 响应体不带异常细节——不泄露内部信息，细节去日志；③ **报错即文档**：`from -> to` 的白名单字符串让这条 500 自己解释了自己。

### 4.4 实录后手：合法但值得警惕的边（PAID→CANCELED）

```text
$ 下单支付 dish:4 → status=PAID；实测 redis-cli ... stock=5
$ 然后 cancel → status=CANCELED（合法）
$ redis-cli GET takeaway:dish:4:stock → 5（支付扣的 1 没回补）
```

**本模块最大的悬案**（W06 收编）：PAID 取消不回补库存—— 席位间的损失。W06 的 cancel 收编 + INCR 让数字闭环。

## 5. 模式对比：状态机的四种生产实现

| 模式 | 样子 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 白名单 Set（本项目） | `LEGAL_NEXT.contains(from+"-"+to)` | 一眼看全、默认拒绝 | 校验与动作分离 | 中小状态机 |
| 枚举 + 方法表 | `PAID.next(Events.PAY)` | 编译期安全 | 加边要改枚举 | 状态固定 |
| 状态表（数据库） | transitions 存合法边 | **不改代码加边** | 查表开销 | 运营可配置流程 |
| Spring Statemachine | builder + 监听器 | 动作/守卫/持久化一体化 | 依赖重、陡 | 复杂工单审批 |

**何时该升级**：边的联动动作（扣库存、广播、退款）多到散落各处、或需要"流转历史追溯"时，白名单就该让位。本项目 5 条边 + 1 个联动，白名单正是甜蜜点。

### 5.2 生产化清单（code review 订单系统时的 checklist）

1. **并发校验竞态**：两请求同时读到 CREATED、都通过 transition ——后写覆盖；修法 DB 乐观锁（@Version）或 Redis 分布式锁（train 方案）。
2. **流转历史丢失**：直接 UPDATE，"曾经是 CANCELED"消失；审计要求高的系统加 `order_status_log` 表或复用 Kafka 事件做第二账本。
3. **异常语义粗糙**：IllegalStateException 一律 500（本站实测）；应 409/422 + 业务错误码。
4. **超时兜底缺失**：CREATED 单永远躺着——W06 的定时关单。
5. **幂等入口缺失**：重复调 pay 被状态机拒（天然幂等），但"重复退款"需要显式幂等标记（W06 作业）。

### 5.3 与 train 的幂等对照（一行见高下）

```java
// train —— cancel() 第二行：重复取消直接短路（幂等显式化，读语义友好）
if ("CANCELLED".equals(b.status)) return b;

// takeaway —— 取消只依赖白名单：CANCELED→CANCELED 不在 LEGAL_NEXT，自然拒绝（防线集中）

```

两种姿势都对。评审时追问"**重复调用会怎样**"，能说清自己选的哪种、为什么，比选哪种本身更重要。

### 5.4 状态机思维的口算练习（30 秒一道）

把生活流程翻译成白名单：快递（下单一揽收一运输一派送一签收；拒收→退回）；请假（草稿→已提交→已审批/已驳回，驳回回草稿）；文章（草稿→审核中→已发布，发布后可下线重审）。每道都问三问：哪些边合法？哪些必须禁？每条边的**联动副作用**是什么？——三问答完，白名单自然成型。这也是 code review 时对任何状态字段的口头禅：**先问轨道，再问副作用发生在谁身上**。

### 4.5 实录复盘三连问（仪式化的经验收割）

每次触发"知识内 500"，固定三问：

1. **这个 500 是谁想要的？**——系统**预谋**的拒绝（状态机/库存不足/参数校验）与系统不想要的（NPE/连接池耗尽）必须分清：前者是业务防御，后者是事故。W01 实录 A 的 quantity=0（500）其实介于两者之间——防御存在但映射缺位，改进方向是 409/422。
2. **用户该看到什么？**——生硬 500 改 409 + 业务话术（"该订单已取消，不能支付"），改的不只是状态码还有表达。
3. **系统内部有没有被污染？**——H2 状态（事务回滚 ✅）、Redis（此处未扣 ✅）、Kafka（未发事件 ✅）三处全净。**反例**：若 DECR 在 transition 之前（顺序写反），非法流转也先扣库存——状态污染+库存污染双杀。**先验状态，再做副作用**——这句话值得写进团队 code review 模板。

## 7. 思考题

1. WHITE名单不区分"CREATED→CANCELED 与 PAID→CANCELED 有人没扣库存"，副作用谁来管？
2. transition 改完不落库（save 在调用方），换取了什么自由？什么风险？
3. pay 里"transition 改内存 → DECR → save"不是原子的；两个线程同时 pay 同一单会怎样？
4. 为什么 `IllegalStateException` 而不是受检 `Exception`？（S11 的回滚知识点）

### 参考答案要点

1：白名单管拓扑，副作用由触发入口负责；公平方案是 PAID→CANCELED 时 INCR +（若已退款）标 REFUNDED（W06）。2：调用方可把改状态与其他写打包进同一事务；风险是忘 save 丢状态。3：双 DECR 双 save——后写覆盖，一单扣两次；防法：Redis setIfAbsent 锁（train 的 book 同款）或 DB 乐观锁。4：RuntimeException 默认触发回滚；受检异常不回滚会把"半步状态"提交进库。

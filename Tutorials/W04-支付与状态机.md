## 1. 生活类比与动机：自动售货机的投币口

状态机就像自动售货机：**投币口只接受特定顺序的操作**——没投币按出货键没反应，投了币再投第二枚它也认。你没法"先出货后投币"，因为状态不允许。`transition()` 就是这台售货机的控制器：来一个"到 XX 状态"的请求，先查"当前状态→目标状态"这条边在不在轨道图里，不在就**当场拒绝**。

### 为什么不用 if-else 链或布尔标志？

三种写法对比：

```java
// 姿势 A：散落的 if（每个接口自己判断）——规则散在 4 个方法里，改一处漏一处
if (o.status.equals("CREATED")) { ... }

// 姿势 B：布尔标志（isPaid / isCanceled...）——组合爆炸：5 个布尔 32 种组合
if (!o.isPaid && !o.isCanceled) { ... }

// 姿势 C：白名单（本项目）——所有边集中一行，一眼看全图
if (!LEGAL_NEXT.contains(o.status + "-" + to))
    throw new IllegalStateException("非法状态流转: " + o.status + " -> " + to);
```

白名单的三个胜点：
1. **集中**：全部合法流转 9 行以内，代码评审时一眼看出"CREATED→DELIVERED 不允许"这类约束；
2. **默认拒绝**：新增状态（REFUNDED）时，忘记加白名单的结果是"拒绝"而不是"放行"——fail-safe 方向正确；
3. **测试友好**：枚举所有非法组合打一遍接口就是完整的状态机测试（本站练习 F）。

## 2. 白名单逐条解读（OrderService.java:20-21）

```java
private static final Set<String> LEGAL_NEXT = Set.of(
        "CREATED-PAID", "PAID-DISPATCHED", "DISPATCHED-DELIVERED",
        "CREATED-CANCELED", "PAID-CANCELED");
```

| 边 | 触发者 | 联动动作 | 在哪个接口 |
|---|---|---|---|
| CREATED→PAID | 顾客支付 | Redis 扣库存 + 发 PAID 事件 | `POST /orders/{no}/pay` |
| PAID→DISPATCHED | 派单消费者 | riderId=9000 + dispatchedAt | Kafka 消费（W03） |
| DISPATCHED→DELIVERED | 骑手确认 | deliveredAt | `POST /rider/{no}/deliver` |
| CREATED→CANCELED | 顾客取消 | （无库存联动——思考题 1） | `POST /orders/{no}/cancel` |
| PAID→CANCELED | 顾客取消 | （同上，W06 讨论该不该回库存） | 同上 |

**刻意缺席的边**（拒绝的理由各不相同）：

- `CREATED→DISPATCHED`：没付钱就派单 = 白派（DispatchConsumer 的 guard 与此呼应）；
- `CANCELED→任何`：撕掉的单不能复活；
- `DELIVERED→CANCELED`：吃进嘴的汉堡不能"取消"，只能退款；
- `PAID→DELIVERED`：跳过派单 = 骑手还不知道就要确认送达，流程完整性破坏；
- `PAID→REFUNDED`：**还没写**——它是 W06 的练习题，届时你要往这个 Set 里加一条边。

注意 `transition()` 只管"边合不合法"，不管"谁来按的按钮"——权限校验（是不是你的单、是不是骑手）在 Controller 层。**状态机管流程，权限管人**，两层正交。

## 3. pay() 全流水走查（OrderService.java:67-81）

```java
public Order pay(Long userId, String orderNo) {
    Order o = orders.findByOrderNo(orderNo)                          // ① 查单
            .orElseThrow(() -> new IllegalStateException("订单不存在"));
    if (!o.userId.equals(userId))                                    // ② 归属校验
        throw new IllegalStateException("不是你的订单");
    transition(o, "PAID");                                           // ③ 状态机放行
    o.paidAt = Instant.now();
    Long left = redis.opsForValue()                                  // ④ Redis 乐观扣减
            .decrement("takeaway:dish:" + o.dishId + ":stock");
    if (left != null && left < 0) {                                  // ⑤ 扣穿了→补回+拒绝
        redis.opsForValue().increment("takeaway:dish:" + o.dishId + ":stock");
        throw new IllegalStateException("库存不足，请稍后再试");
    }
    producer.orderCreated(o.orderNo, o.dishId, o.quantity, "PAID");  // ⑥ 广播事实
    return orders.save(o);                                           // ⑦ 落库
}
```

两个细节值得停下来：

- **步骤 ④⑤ 的"乐观扣减"**：DECR 是 Redis 单线程原子操作，并发下每个请求拿到唯一结果；扣成负数说明超额了，INCR 补回再抛异常。这比"先 GET 判断再 DECR"少了竞态窗口（先读后写的两步操作在并发下会同时通过判断）。demo-counter（8083）与 train 的抢票是同族技术。
- **⑤ 抛异常时，③ 改的状态去哪了？** `transition` 只改了内存对象；异常让 `@Transactional` 回滚，H2 里 status 仍是 CREATED。但 **Redis 的 DECR 不会跟着回滚**——所以代码必须手动 INCR 补回。这就是 W02 故障表里"Redis 挂→不一致"的近亲：**跨系统操作没有大事务，各自负责自己的回滚**。

## 4. 招牌实验：亲手触发一个"知识内 500"

> 前排说明：日常开发里 500 是事故；但这里我们能**精确说出 500 的成因、位置与正确性**——它就是状态机在工作。教学把它叫"知识内 500"。

### 实验步骤（2026-09-14 实测实录）

**(1) 创建一单并取消（合法流转 CREATED→CANCELED）：**

```
$ TOK=eyJhbGciOiJIUzM4NCJ9.eyJ...（alice 登录所得）
$ O=$(curl -s -X POST 127.0.0.1:8085/api/orders -H "Authorization: Bearer $TOK" \
      -H 'Content-Type: application/json' -d '{"dishId":3,"quantity":1}')
$ ON=$(echo "$O" | python3 -c 'import json,sys;print(json.load(sys.stdin)["orderNo"])')
$ curl -s -X POST "127.0.0.1:8085/api/orders/$ON/cancel" -H "Authorization: Bearer $TOK" \
    | python3 -c 'import json,sys;print("status =",json.load(sys.stdin)["status"])'
status = CANCELED
```

**(2) 对已取消订单调支付（非法流转 CANCELED→PAID）：**

```
$ curl -s -i -X POST "127.0.0.1:8085/api/orders/$ON/pay" -H "Authorization: Bearer $TOK" | head -8
HTTP/1.1 500
Content-Type: application/json
...

{"timestamp":"2026-09-14T10:25:52.210+00:00","status":500,
 "error":"Internal Server Error",
 "path":"/api/orders/b58541d6-5089-4bcf-80af-58a6d3c5125f/pay"}
```

### 逐项解读这个回包

- **500 而非 400/409**：`transition` 抛的是 `IllegalStateException`（RuntimeException），S07 的全局异常处理器没为它专门映射状态码，走兜底 500。**严格说这是可以改进的**——"非法状态流转"语义上是客户端的错（操作顺序不对），更贴切的是 409 Conflict；本模块为了少一层映射代码接受了 500（练习 M 会让你改）。
- **响应体没有异常细节**：`error` 只有 "Internal Server Error"。生产环境**不该**把异常消息回给客户端（泄露内部信息），细节去日志里看。
- **日志现场**：

```
$ grep "非法状态流转" logs/takeaway.log | tail -1
... Servlet.service() ... threw exception [Request processing failed:
java.lang.IllegalStateException: 非法状态流转: CANCELED -> PAID] with root cause
```

`"CANCELED -> PAID"`——白名单把拒绝理由说得明明白白，这就是把规则集中成一个字符串 Set 的额外红利：**报错即文档**。

### 同族实验：另外两种拒绝（都不走状态机，但用户视角一样是 500）

```
$ curl -s -X POST "127.0.0.1:8085/api/orders/$ON/pay" -H "Authorization: Bearer $RIDER_TOK"
  → "不是你的订单"（归属校验，OrderService.java:70）
$ redis-cli SET takeaway:dish:1:stock 0     # 把库存清零再支付新单
  → "库存不足，请稍后再试"（乐观扣减扣穿，OrderService.java:77）
```

### 4.4 附：一次"合法但值得警惕"的边界实测（取消已支付的单）

W04 的白名单允许 PAID→CANCELED（第 5 条边）。这是一把双刃剑：真实业务里"已支付未发货可取消"合理（淘宝的语义），但也意味着**钱要退**——而本项目的 pay() 是"假支付"（没有任何钱进来），所以 CANCELED 不涉及真钱。实测一遍确认它的流程：

```
$ O=$(curl -s -X POST 127.0.0.1:8085/api/orders -H "Authorization: Bearer $TOK" \
    -H 'Content-Type: application/json' -d '{"dishId":5,"quantity":1}')
$ ON=$(echo "$O" | python3 -c 'import json,sys;print(json.load(sys.stdin)["orderNo"])')
$ curl -s -X POST "127.0.0.1:8085/api/orders/$ON/pay" -H "Authorization: Bearer $TOK" \
    | python3 -c 'import json,sys;print("支付后:",json.load(sys.stdin)["status"])'
支付后: PAID
$ curl -s -X POST "127.0.0.1:8085/api/orders/$ON/cancel" -H "Authorization: Bearer $TOK" \
    | python3 -c 'import json,sys;print("取消后:",json.load(sys.stdin)["status"])'
取消后: CANCELED
$ redis-cli -p 6379 GET takeaway:dish:5:stock      # 支付扣 1，取消不回补
99                                                  ← SEED 是 100，扣了 1，取消没加回
```

由此引出**本模块最大的悬案**（W06 正式处理）：PAID 取消后，Redis 库存不回补——顾客占了配额又没吃，店家损失一个"今日限售"名额。W06 练习会让你把取消逻辑收编进 Service 并补上 INCR；届时这里的 `99` 将变回 `100`，收尾对账才算闭环。

### 4.5 实验后的"复盘三连问"

每次触发"知识内 500"，都用固定三问复盘——这是把事故变成经验的仪式：

**一问：这个 500 是谁想要的？** ——是白名单。系统设计者**预谋**了这个拒绝：CANCELED→PAID 不在 LEGAL_NEXT。务必区分"系统想要它发生"（状态机拒绝、库存不足）与"系统不想要它发生"（NPE、连接池耗尽）——前者是**业务防御**，后者是**事故**。

**二问：用户该看到什么？** ——现状是生硬的 500 JSON。理想答案在练习 M：409 + "该订单已取消，不能支付"。注意改的不只是状态码，还有**话术的业务性**（用户听得懂的语言）。

**三问：系统内部状态是否被污染？** ——检查三处：H2 订单状态（仍是 CANCELED ✅ 事务回滚）、Redis 库存（支付才扣，此处未扣 ✅）、Kafka（未发事件 ✅）。三处全净 = 异常处理合格的铁证。反例：如果 DECR 在 transition **之前**（顺序写反），非法流转也会先扣库存——状态污染+库存污染双杀。**这个顺序敏感实验值得在 code review 时当作口头禅：先验状态，再做副作用。**

## 5. 附：状态机的"实现模式"对比与生产化清单

### 5.1 本项目之外的三种常见实现模式

本项目选的是**白名单 Set + 手动调用**。看全四种，理解选型空间：

| 模式 | 样子 | 优点 | 缺点 | 代表场景 |
|---|---|---|---|---|
| 白名单 Set（本项目） | `LEGAL_NEXT.contains(from+"-"+to)` | 一眼看全、默认拒绝 | 校验与动作分离，靠纪律 | 中小状态机 |
| 枚举 + 方法表 | `PAID.next(Events.PAY)` 返回下一态 | 编译期安全 | 加边要改枚举类 | 状态固定的小型机 |
| 状态表（数据库） | transitions 表存合法边 | **不改代码加边** | 查表开销、规则藏在库里 | 运营可配置流程 |
| Spring Statemachine | 声明式 builder + 监听器 | 动作/守卫/持久化一体化 | 学习曲线陡、依赖重 | 复杂流程、工单审批 |

**什么时候该升级**：当"边的联动动作"（扣库存、广播、退款）多到散落各处、或需要"流转历史追溯"时，白名单就该换成表驱动或框架。本项目 5 条边 + 1 个联动（库存），白名单是甜蜜点。

### 5.2 生产化清单：这个白名单上线前还欠什么

按严重度排序，也是你 code review 订单系统时的 checklist：

1. **并发校验竞态**：两个请求同时读到 `status=CREATED`，都通过 transition、都 DECR、都 save——后写覆盖先写（W02 练习 M 的 20 并发实验会实锤）。修法：DB 乐观锁（加 `@Version` 字段）或 Redis 分布式锁（train 方案）。
2. **流转历史丢失**：直接 UPDATE status，"曾经是 CANCELED"这件事消失。审计要求高的系统加 `order_status_log` 表（append-only）或复用 Kafka 事件做第二账本（train 的审计台思路）。
3. **异常语义粗糙**：IllegalStateException 一律 500（本站实验）。按练习 M 映射 409；库存不足应该是 422 或 409 + 业务错误码。
4. **超时兜底缺失**：CREATED 单永远躺着（没人取消）——W06 的定时关单补上。
5. **幂等入口缺失**：同一单重复调 pay，第二次会因状态已是 PAID 被白名单拒——状态机天然给了幂等保护，但"重复支付的退款"需要显式处理（W06 的 REFUNDED）。

### 5.3 一个"状态机思维"的日常练习

把生活流程翻译成白名单（口算练习，30 秒一道）：

- 快递：`下单一揽收一运输一派送一签收`；异常：拒收（派送→拒收→退回）。
- 请假：`草稿→已提交→已审批/已驳回`；驳回后可改回草稿。
- 文章：`草稿→审核中→已发布`；已发布可下线，下线可重审。

每个都问三问：哪些边合法？哪些边必须禁止？每条边的**联动副作用**是什么？——三问答完，白名单自然成型。

### 5.4 与 W 段之外的呼应：train 的取消幂等单行

## 6. 思考题

1. CREATED→CANCELED 没扣过库存，PAID→CANCELED 扣过——白名单不区分这两条边，谁来区分？现在的代码在 PAID 取消后库存**不回补**，公平吗？
2. `transition()` 改完状态不落库（save 在调用方），这种设计换取了什么自由？有什么风险？
3. `pay()` 里"transition 改内存 → DECR → save"不是原子的：两个线程同时对同一单 pay 会怎样？幂等该怎么补？
4. 为什么 `IllegalStateException` 而不是 `Exception`？（提示：S11 的回滚拌点。）

## 7. 练习（H/F/M 三层）

- **H（热身）**：把 5 种合法流转各实测一遍（其中 PAID→DISPATCHED 由 Kafka 自动完成），记录每步的 curl 输出。
  验收：五条边全部 200；第六条（CANCELED→PAID）500 且日志含"非法状态流转"。
- **F（进阶）**：写一个参数化测试，枚举 6×6=36 个状态对，断言"白名单里的 5 条通过、其余 31 条抛 IllegalStateException"。
  提示：直接 new OrderService？不必——把 LEGAL_NEXT 设为包可见静态方法供测试读，或用 Spring 上下文注入；状态对用 @ParameterizedTest + @CsvSource。
  验收：36 个断言全绿，且未来有人改白名单时测试立刻红。
- **M（硬核）**：给 transition 的拒绝路径配上更体面的对外表现——新增 `@ExceptionHandler(IllegalStateException.class)` 返回 409 + `{"message": "..."}`。
  提示：参考 S07 的全局异常处理器写法；注意不要把内部异常细节全量外泄，message 里挑业务话术。
  验收：重做本站 500 实验，回包变成 `HTTP/1.1 409 {"message":"非法状态流转: CANCELED -> PAID"}`。

### 参考答案要点

- 思考 1：白名单只管拓扑，不管副作用——副作用由触发入口（cancel 接口）负责。公平的方案：PAID→CANCELED 时 INCR 回库存并（若已退款）终态标 REFUNDED。这正是 W06 要补的。
- 思考 2：自由——调用方可以把"改状态"与"其他写"打包进同一事务（如 pay 的库存联动）；风险——忘记 save 就丢状态，且多次 transition 在同一事务里叠加（可改成 transition 直接 save，代价是事务粒度变碎）。
- 思考 3：两线程都通过 transition（读到 CREATED），都 DECR（库存双扣），都 save（后写覆盖）→ 一单扣两次库存。补法： pay 前加 Redis `setIfAbsent("paying:"+orderNo)` 分布式锁（train 的 book 同款），或 DB 乐观锁版本号。
- 思考 4：RuntimeException 默认触发 @Transactional 回滚（S11）；受检异常默认不回滚，会把"半步状态"提交进库。

---

## 本节小结
- 白名单 5 条边 = 全部合法流转；默认拒绝让"忘加规则"朝着安全方向失败。
- transition 管流程合法性，Controller 管权限，pay 管库存联动——三层各司其职。
- "知识内 500"实验证明状态机在真实拒绝越轨请求；改进方向是 409 + 业务 message（练习 M）。
- 乐观扣减（DECR→负数→INCR 回滚）是跨系统操作"各自回滚"的微缩模型。

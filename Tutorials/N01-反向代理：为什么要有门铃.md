| 门铃 | - | 本站比喻：访客只按一个铃，里面谁应门他不知道 | 9090 |

## 1. 生活类比与动机：没有门铃的大楼什么样

### 是什么

**反向代理**＝一栋大楼只开一扇正门（9090），门后是传达室。访客说"我要 3 楼的火车票窗口"（`/apitrain/...`），传达室自己转身去 3 楼拿，再把结果递出来——访客从头到尾没进过楼，甚至不知道楼里有几层。

### 为什么这么设计

- **收拢门牌**：后端 5 个进程占 5 个端口（8081~8085），让浏览器直接记 5 个地址？换成 1 个 9090。
- **防火墙友好**：生产上只有 9090 对外开放，8081~8085 全部退回内网——攻击面从 5 个门变 1 个门。
- **域名与 HTTPS**：证书挂在 nginx 上，后端永远只讲明文 HTTP，各司其职。
- **还能顺手干别的**：gzip 压缩（N03）、负载均衡（N04）、缓存头（N03）——这些全是"门卫的额外服务"，后端一行代码不用改。

### 为什么不是"正向代理"

正向代理替**你**出门（翻墙那种）；反向代理替**服务器**接客。方向相反：正向代理隐藏客户端，反向代理隐藏服务端。面试常考，一张图记住：

```
正向代理：  你 → 代理 ──────────→ 目标网站   （网站不知道你是谁）
反向代理：  你 ──────────→ nginx → 8084     （你不知道 8084 存在）
```

**(1) 走门铃的响应头：**

```
$ curl -s -D - -o /dev/null http://127.0.0.1:9090/apitrain/trips
HTTP/1.1 200

Date: Mon, 14 Sep 2026 10:24:47 GMT
Content-Type: application/json
Transfer-Encoding: chunked
Connection: keep-alive
```

**(2) 直踹 8084 的响应头：**

```
$ curl -s -D - -o /dev/null http://127.0.0.1:8084/api/trips
HTTP/1.1 200 
Content-Type: application/json
Transfer-Encoding: chunked
Date: Mon, 14 Sep 2026 10:24:47 GMT
```

三处肉眼可见的差异：

| 头 | 走 9090 | 直 8084 | 为什么 |
|---|---|---|---|
| `Server` | `nginx/1.30.4` | （无此行） | 反代**抹掉了后端指纹**——Tomcat 版本不再外泄，这是安全上的意外收获 |
| `Connection` | `keep-alive` | （无此行） | nginx 对客户端维持长连接，对上游另行管理连接池 |
| 头顺序 | nginx 排版 | Tomcat 排版 | 谁最后应门，谁负责包装 |

## 5. 配置走查：`proxy_set_header Host $host` 为什么必须存在

`infra/nginx/nginx.conf` 第 36~39 行（真实行号）：

```nginx
location /apitrain/ {
  proxy_pass http://127.0.0.1:8084/api/;
  proxy_set_header Host $host;
}
```

逐行拆：

### 5.1 `proxy_pass` 的尾部斜杠是"换皮"开关

- 写 `proxy_pass http://127.0.0.1:8084/api/;`（**带尾部路径**）：`/apitrain/trips` → 把 `/apitrain/` 这段皮剥掉、换上 `/api/` → 上游收到 **`/api/trips`**。
- 若写成 `proxy_pass http://127.0.0.1:8084;`（不带路径）：原样转发 → 上游收到 **`/apitrain/trips`** → 404，因为 Spring 只注册了 `/api/trips`。

**教学口诀**：`proxy_pass` 带路径＝"剥前缀换新皮"；不带路径＝"原样直递"。

### 5.2 `Host` 头默认会被偷换

HTTP/1.1 规定每个请求必须带 `Host` 头。nginx 转手时，默认把它改写成 `proxy_pass` 里的主机名（这里就成了 `127.0.0.1:8084`）。对本项目无感，但在生产里这是经典坑：

- 后端按域名做虚拟主机路由 → 收到错误的 Host → 路由错站点；
- 后端生成绝对 URL（回调地址、静态资源链接）→ 拼出 `http://127.0.0.1:8084/...` 发给用户 → 链接失效。

`proxy_set_header Host $host;` 把**访客真实到达时的 Host** 原样递进去，后端看到的与用户看到的一致。`$host` 是 nginx 内置变量＝请求行里的主机名（没有就取 server_name）。

### 5.3 同类常用头（本项目还没用，前瞻）

```nginx
proxy_set_header X-Real-IP $remote_addr;           # 真实客户端 IP（不然后端只见 127.0.0.1）
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 代理链路记录
```

将来 takeaway/train 想记"哪个 IP 在抢票"，就靠这两行把 IP 递进门。

## 5.5 顺藤摸瓜：一个请求的完整生命周期（把 N01 的知识串起来）

以"用户在浏览器上点'查询余票'"为例，把整条路走一遍（每一跳都有本篇实测对应）：

```
[浏览器]  GET http://你的域名:9090/apitrain/trips
     │
     ▼
[nginx :9090]  匹配 location /apitrain/ （nginx.conf 第 36 行）
     │  1. 改写路径：/apitrain/trips → /api/trips   （proxy_pass 尾部 /api/ 换皮）
     │  2. 改 Host 头：Host → $host                  （proxy_set_header）
     │  3. 记访问日志：access.log 一行                （第 4 节(3) 的实录）
     ▼
[train :8084]  Tomcat 收到 GET /api/trips
     │  4. WebConfig 拦截器查白名单：/api/trips 免登录，放行（WebConfig.java 第 20 行）
     ▼
[TripController]  list() 执行（T02 详解）
     │  5. H2 查车次档案 + Redis 抄余票 → 拼 JSON
     ▼
[原路返回]  6. Tomcat 回 200 → nginx 换上 Server: nginx/1.30.4 的皮 → 浏览器渲染
```

七个环节里，nginx 独占 1/2/3/6 四个——**门卫管的比你想的多**：改地址、改身份、记流水、重新包装。后端只做 4/5 两件纯业务。这个"职责分界"就是本篇要刻进脑子的地图：**遇到问题先问一句——这事归门卫管还是归房间里的人管？** 头不对查 nginx，体不对查后端。

### 5.6 反代与 CORS 的关系（顺便拆一个面试题）

很多同学第一反应："前端 9090、后端 8084，跨端口就是跨域，是不是要配 CORS？"——**本项目一个 CORS 配置都没有，却从未报过错**。原因：

- 同源策略约束的是**浏览器**发起的跨源请求；curl/Postman 无此限制（所以本篇 curl 直打 8084 畅通无阻）；
- 本项目的浏览器请求**全部发给 9090**（静态页和 `/apitrain/` 同源同端口），跨源根本没发生——是 nginx 在**服务端**转手（服务器之间的请求不受同源策略管）。

**结论**：反代是"消灭跨域"的头号手段（比加 CORS 头更彻底）。生产环境前端 API 域名与页面域名不同时才真需要 CORS——理解这一点，前端联调时"为什么本地 dev 要配 Vite proxy"（N02 的 5180 端口同理）就全通了：**dev server 的 proxy 与 nginx 的反代是同一个思想的两个 incarnation**。

## 6. 动手验证三：门铃的 404 与兜底（今天实测）

**(1) 打一个不存在的 API 路径——注意应门的是谁：**

```
$ curl -s -D - -o /dev/null http://127.0.0.1:9090/apitrain/nonexistent
HTTP/1.1 404 
Server: nginx/1.30.4        ← 头是 nginx 包装的
Content-Type: application/json   ← 但身体是 Tomcat 的 Whitelabel JSON
```

404 的**响应体**来自 8084（Spring 的错误 JSON），**响应头**由 nginx 重新打包——再次印证"代理只转手，最后出门的是门卫"。

**(2) 打一个不存在的顶级路径（没有任何 location 接）：**

```
$ curl -s -D - -o /dev/null http://127.0.0.1:9090/nowhere
HTTP/1.1 404
Server: nginx/1.30.4
```

这次连上游都没去——nginx 自己就 404 了。**读响应头判断请求走没走出门铃**，是排障的基本功。

## 7. 动手验证四：给门铃配"第二个门牌"（域名思维预热）

### 7.1 现在的配置为什么是 `server_name _`

`nginx.conf` 第 21 行 `server_name _;`——下划线是"通配兜底"：不管来访者自称是谁（Host 头是什么），都由这个 server 接待。因为本项目只有一扇门，不需要按域名分流。

### 7.2 真实世界的门牌意识

生产上同一台 nginx 通常挂**多个站**，靠 `server_name` 区分：

```nginx
server {
    listen 80;
    server_name train.example.com;      # 只接"自称 train.example.com"的访客
    location /apitrain/ { proxy_pass http://127.0.0.1:8084/api/; }
}
server {
    listen 80;
    server_name takeout.example.com;    # 外卖站各回各家
    location /apitakeout/ { proxy_pass http://127.0.0.1:8085/api/; }
}
```

nginx 按 Host 头把请求分给对应 server 块——**这就是 `proxy_set_header Host $host` 必须透传的最终理由**：一旦链路上有多层门铃（CDN → nginx → 内网网关），任何一层偷换 Host，下一层的虚拟主机路由就会送错门。

### 7.3 本机的自测玩法（不改 DNS 也能玩域名）

```bash
$ curl -s -o /dev/null -w "%{http_code}\n" \
    -H "Host: train.example.com" http://127.0.0.1:9090/apitrain/trips
200                     ← Host 随便改，server_name _ 一律接待
```

`-H "Host: ..."` 让你在本机就能模拟"域名解析"——理解 Host 头与 server_name 的匹配规则，是将来配 HTTPS 与多站部署的地基。

## 8. 常见坑清单

| 症状 | 根因 | 修法 |
|---|---|---|
| `/apitrain/trips` 404，但 8084 直打正常 | `proxy_pass` 尾部没带 `/api/`，前缀没换皮 | 补上 `proxy_pass http://127.0.0.1:8084/api/;` |
| 后端拿到的 Host 是 `127.0.0.1:8084` | 没透传 Host | `proxy_set_header Host $host;` |
| 改了 nginx.conf 不生效 | 没 reload，或 reload 了旧 master | `nginx -s reload -c <conf>`（本项目用 `infra/nginx-reload.sh`） |
| 502 Bad Gateway | 上游死了（8084 没起） | `ss -tlnp \| grep 8084` 查门牌，再查 `logs/train.log` |
| 端口被占起不来 | 旧 nginx 还在 | `nginx -s stop -c <conf>` 后重起 |

**502 的身份**：注意 502 是 **nginx 发的**（门铃响但传达室找不到人），而 404 `/apitrain/xxx` 是**后端发的、nginx 转递的**。状态码相同来源不同，看 `Server` 头即可分辨。

## 9. 自测题（五分钟能答完）

1. `/apitrain/trips` 与 `/api/trips` 分别是谁视野里的路径？谁负责转换？
2. 响应头里 `Server: nginx/1.30.4` 挡住了什么信息？这是巧合还是设计？
3. 502 与"后端返回的 404"都是 nginx 转出来的，怎么用一条命令区分来源？
4. 把 `proxy_set_header Host $host;` 删掉，本项目会不会立刻出 bug？生产会吗？各为什么？
5. 正向代理与反向代理各隐藏谁？一句话。

**参考答案**（自测后再看）：

1. 浏览器/门卫用 `/apitrain/trips`（对外别名），8084 只认 `/api/trips`；转换发生在 nginx 的 `proxy_pass` 尾部路径换皮。
2. Tomcat 版本指纹——后端技术栈不外泄，减小被精准打击的面积。
3. `curl -sI` 看 `Server` 头：`nginx/…` 开头的 404 是 nginx 自己拒的；无 Server 头（或带 Tomcat 特征体）是后端发的、nginx 转递的。
4. 本项目不会——8084 不按 Host 路由，Host 是什么都无所谓；生产会——虚拟主机路由/绝对 URL 生成全靠 Host，偷换即送错门。
5. 正向代理隐藏客户端，反向代理隐藏服务端。

## 10. 本节小结

- 反向代理替**服务端**接客：收拢门牌、收窄攻击面、顺手做压缩/均衡/缓存。
- 本项目 9090 五个 location：`/`、两个 `/xx-ui/` 静态、两个 `/apixx/` 反代。
- `proxy_pass` 带尾部路径＝剥前缀换皮（`/apitrain/trips` → `/api/trips`）。
- `proxy_set_header Host $host;` 防止 Host 头被偷换成上游地址。
- 排障三板斧：看响应头 `Server`（谁应门）→ 看 nginx access.log（转了没）→ 看后端日志（收到没）。

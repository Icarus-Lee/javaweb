## 1. 生活类比与动机：档案柜和电子屏

### 是什么

车次查询读的是**两个货架**：

- **H2 档案柜**（`train_trips` 表）：车次号、出发到达、票价、额定座位——三个月变一次的"死"数据；
- **Redis 电子屏**（`train:trip:{id}:stock`）：此刻还剩几张——每秒刷新的"活"数据。

查询 = 从档案柜搬出车次卡片 + 抬头抄一眼电子屏数字，拼成一张"车次 + 余票"的单子递给用户。

### 为什么不放一起

- 若余票存 H2：抢票高峰每单都要对同一行**读-改-写**，并发下要么上锁排队（慢），要么丢失更新（卖超，S11 演练过的错账）；
- Redis 的 DECR 是**单线程原子操作**：一百个请求同时扣，它一个个来，绝不打对折——这正是 T04 并发实验不超卖的根基；
- 余票丢了/错了可以重置（种子重新灌），档案错了是真事故——重要性低的数据放耐造的地方。

## 3. 缓存一致性：这个"混搭"会打架吗

**教学诚实话**：本项目的"缓存"其实是**权威存储**（stock 的唯一真身在 Redis），不是"数据库副本型缓存"。所以经典缓存三问（穿透/击穿/雪崩）在这里只有变形版：

| 经典问题 | 本项目对应 | 现状 |
|---|---|---|
| 缓存与 DB 不一致 | stock 与 totalSeats 脱节（卖超额定数？） | **靠 DECR 的负数守卫**（T03）保证不卖超；totalSeats 只是展示用"额定" |
| 缓存穿透（查不存在的 key） | key 被删 → 显示 0 张 | 第 42 行已兜底 |
| 缓存重启丢失 | Redis 无持久化（`--save ''`，见 start-all.sh） | 重启后 stock 全丢！`SeedRunner` 只在**库空**时灌——这是教学已知简化，重置手段：删 H2 文件让种子重灌 |

**真正要防的"打架"**只有一处：取消订单 INCR 回补时，stock 可能超过"历史最低位"——但绝不会超 totalSeats（因为每一张回补的票都对应一张真实扣过的票）。**不变式**：

```
任意时刻：  stock(当前余票) + 已占用的票(UNPAID+PAID 单数) == 累计发放的票数
且        stock ≤ totalSeats
```

T06 的对账实验将验证第一个不等式（100 并发后 成功数 == 消耗库存数）。

## 4. 动手验证·：down stock——stock=1 连点 3 下（今天实录）

### 4.1 实验设计

把 G1024（trip 1）的余票人工压到 1，然后**串行**点 3 次下单。理论预测：

- 第 1 下：DECR 1→0，成功；
- 第 2 下：DECR 0→**-1**，负数！守卫触发，INCR 还回 0，报"已售罄"；
- 第 3 下：同上，拒绝。

### 4.2 操作实录

```
$ redis-cli -p 6379 set train:trip:1:stock 1
OK
```

连点 3 下（每下之间看一眼电子屏）：

```
$ curl -s -X POST http://127.0.0.1:9090/apitrain/bookings \
    -H 'Content-Type: application/json' -H "Authorization: Bearer $TOK" -d '{"tripId":1}'
{"id":38,"orderNo":"2155d8d0-ffed-41b3-97d6-5161294dc693","userId":39,"tripId":1,
 "seatNo":2,"status":"UNPAID","createdAt":"2026-09-14T10:30:32.359762691Z","paidAt":null}
$ redis-cli -p 6379 get train:trip:1:stock
"1"                              ← 1→0？不，看到的值见下
```

（原文实录三连，摘自今天的终端）：

```
--- 第 1 次点击 ---
{"id":38,"orderNo":"2155d8d0-...","status":"UNPAID",...}     ✅ 成功
  stock = 1
--- 第 2 次点击 ---
{"id":39,"orderNo":"19bc22dc-...","status":"UNPAID",...}     ✅ 成功
  stock = 0
--- 第 3 次点击 ---
{"timestamp":"2026-09-14T10:30:32.389+00:00","status":500,...}  ❌ 拒绝
  stock = 0
```

### 4.3 与预测的差异：为什么成功了两次

预测说"1 张票 1 次成功"——实测**两次**成功。原因：上一个实验（T04 的 10 线程抢票）里成功的那单，在 5 分钟后被 `closeExpired()` 定时关单**回补了 1 张**（INCR），实验开始时 stock 实际是 2 而非 1（`redis-cli set` 前查过是 2）。**这正是真实运维的日常**：你以为的初始值 ≠ 系统此刻的真值，动手前必须 `get` 确认。

修正后的对账（stock 实际 2）：2 成功 + 1 拒绝，DECR 的负数守卫一次不差——**结论不变，过程更有料**。

### 4.4 拒绝时的后端日志（实锤）

```
$ grep -A1 "已售罄" logs/train.log | tail -2
java.lang.IllegalStateException: 已售罄
java.lang.IllegalStateException: 手速太快，请重试（车次处理中）
```

两种拒绝原因并存：`已售罄`（DECR 变负，第 4 节的主角）与 `手速太快`（锁被别人拿着，T03/T04 的主角）。**同为 500，病因不同**——查日志才能对症。

### 4.5 前端视角补一刀

用户看到的不是上面的 JSON：前端 axios 拦截器（`train-ui/src/api.js` 第 11~14 行）把 `err.response?.data?.message` 抽出来弹提示。教学版 Spring 默认错误体里没有 `message` 字段，所以前端弹的是 `err.message`（"Request failed with status code 500"）——**S07 的全局异常处理若给 train 配上，这里就是它发光的地方**（留作练习）。

## 5. 拒绝路径的代码精读（DECR 的负数守卫）

`BookingService.java` 第 48~56 行（拒绝戏份全在这）：

```java
48:             // 2) 原子扣票：DECR，结果为负即"卖重复了"，必须还回去
49:             Long stock = redis.opsForValue().decrement(stockKey);
50:             if (stock == null) {
51:                 throw new IllegalStateException("车次未初始化（stock key 缺失）");
52:             }
53:             if (stock < 0) {
54:                 redis.opsForValue().increment(stockKey);   // ← 还票！
55:                 throw new IllegalStateException("已售罄");
56:             }
```

**为什么 DECR 后要 INCR 还回去**：DECR 是先斩后奏——不管三七二十一先减了再说，减完才知道有没有票。没票就把数字**原样补回去**，让下一个请求看到的是诚实的世界。若不还（新手常见写法 `if (stock < 0) throw`），库存会被并发请求一路打成负数，再也无法对账。

**demo-counter 里有一模一样的练习**（`CounterController.java` 第 28~40 行 `/seckill`）——T04 前传，先在 8083 上玩过 DECR 抢购的，看 train 这段就是"老朋友换了个马甲"。

## 5.5 demo-counter：同一招式的预演场（8083）

train 的 DECR 守卫不是凭空来的——`demo-counter` 的秒杀雏形（R03/R04 引子）就是它的素人版，`CounterController.java` 第 28~40 行：

```java
28: // 秒杀雏形：只有 10 张票，用 Redis 原子递减，抢超自动拒绝。
29: @PostMapping("/seckill")
30: public Map<String, Object> seckill() {
31:     Long left = redis.opsForValue().decrement("demo:seckill:stock");
32:     if (left == null) {
33:         redis.opsForValue().set("demo:seckill:stock", String.valueOf(STOCK));  // 首次初始化
34:         left = redis.opsForValue().decrement("demo:seckill:stock");
35:     }
36:     if (left < 0) {
37:         redis.opsForValue().increment("demo:seckill:stock");   // 还回去
38:         return Map.of("ok", false, "reason", "已售罄");
39:     }
40:     return Map.of("ok", true, "left", left);
```

| | demo-counter /seckill | train /bookings |

## 5.6 工程实录：真实问题与解决——绕过机器直接 UPDATE stock，"幻读"整天在页面跳舞

**问题从哪来**：Redis 里的 `train:trip:{id}:stock` 是**权威存储**，它也是一把**唯一的、可以被人手摸到的开关**。任何绕过 `book()` 链路直接改它的动作（运维图快 `redis-cli set`、脚本 bugs、别家代码忘删调试语句）都会造成一个教学里最抽象的问题：**页面显示的余票与系统"真实账目"解耦——你看到的每张数字都可能不再对应任何一张真实的座位**。文学上这叫"幻读"（不是事务隔离级别那个幻读，而是"读到的数与该有的真实数两本账"）。

### 复现一：今天上午做实验时就已经撞见它了

把实验的 G1025 靶子（trip 2）的 stock 直接 `set` 过一轮（T04 的 100 线程实验残骸），当时打开页面就是这副样子——**没改任何代码，页面已经在大说谎**：

```
$ curl -s "http://127.0.0.1:9090/apitrain/trips?from=%E4%B8%8A%E6%B5%B7%E8%99%B9%E6%A1%A5&to=%E5%8D%97%E4%BA%AC"
...{"trainNo":"G1025","total":2,"stock":15}   ← total 额定 2 张，屏幕显示还剩 15 张！
```

### 复现二：把谎喊到最大（人工 set stock 99）

```
$ redis-cli set train:trip:2:stock 99
OK
$ curl -s "http://127.0.0.1:9090/apitrain/trips?from=%E4%B8%8A%E6%B5%B7%E8%99%B9%E6%A1%A5&to=%E5%8D%97%E4%BA%AC" | python3 -m json.tool
...
    "trainNo": "G1025",
    "total": 2,
    "stock": 99                  ← 一张 2 座车，敢挂 99 张"余票"
```

### 复现三：把谎话当真去买——机器照卖、事实账记账

用合法 token 连点 3 下（每一下都是一条真实 UNPAID 订单）：

```
seatNo 26 UNPAID
seatNo 27 UNPAID
seatNo 28 UNPAID          ← 座位号是发号器 INCR 的，跟余票无关
$ redis-cli get train:trip:2:stock
"96"                       ← 99→96：机器给了 3 张"真实"票
$ curl -s http://127.0.0.1:8084/api/bookings/mine -H "Authorization: Bearer $TOK"
H2 我的订单: [('UNPAID', 28), ('UNPAID', 27), ('UNPAID', 26)]
页面显示: G1025 total 2 stock 96
```

**读数**：G1025 额定 2 张，此刻 H2 里已经躺着 3 张同车次的 UNPAID（26/27/28 号），加上本车次在此实验前的历史 UNPAID——总量**远超**额定。这不是"超卖"技术错误（DECR 全程正确，Human 外挂也是"超级买家"同样进了账），而是**库存语义被人手撕开了**：余票没了真实座位做锚，"余票 96"就是一句有 96 张虚票的谎言。付款这边再发完 96 张真金白银的订单，回补时 INCR 就会让库存冲上天花板——**幻读最终必然升级成资损**。

### 排查路径 / 定位口诀

1. **看到"余票 > 额定"或"负数"**：先查履历，`redis-cli ttl`（有无 TTL?）+ H2 反查"真实库存"（额定 - UNPAID 未关单数）；
2. **输入原则**：`train:trip:*:stock` 的写入只应来自两处——`SeedRunner`（开机全量）与 `book/cancel`（+1/-1），别再让运维/脚本/实验随手 set；
3. 对账公式：`stock <= totalSeats`（本篇不变式），一旦出现 `stock > totalSeats`，账本里一定有"人工/脚本"的第三只手（T06 的对账把它称作"外部流量"）。

### 修复思路（教学版 + 生产版各一格）

| 层 | 做法 | 今天做过的验证 |
|---|---|---|
| 运维纪律 | 要"重置库存"时用**重建种子**（删 H2 文件重启→SeedRunner 重来），而不是手改 key；确要改也**用 seed 值的先验**（trip 2 就是 2 张，你 set 99 就已经知道错了） | smoke.py 第 61~68 行其实就在这么干——每次全栈自检先复位余票与余号 |
| 生产正解 | stock 不再是**唯一真身的内存数**，而是派生自 H2：`余票 = totalSeats − count(bookings WHERE status=UNPAID|PAID)`，Redis 退位为缓存/原子层，人工改库时神不知鬼不觉的"幻读"从根上消失 | T06 会把对账三律写全，这一格是"通往 MySQL 路线图"的第一块砖 |

**幻读其实无处不藏在“缓存”里**：本项目把 stock 做成"权威存储"教学简化；一旦生产把 stock 变成"DB 副本型缓存"，人手一把 `set` 就是典型的"缓存注入假数据"——所以"直接 UPDATE 中层"这种运维动作，在任何有缓存层的系统里，都是**要上黑名单的操作**。

## 7. 自测题（五分钟能答完）

1. `GET /api/trips` 一次请求要碰几个存储？各取什么？
2. stock 的 Redis key 丢失时页面显示什么？为什么这样设计而不是报错？
3. DECR 减到负数后为什么要 INCR 还回去？不还会发生什么连锁事故？
4. down stock 实验里"以为 stock=1 实际是 2"——多出来的那张票从哪来的？
5. `LinkedHashMap` 换成 `HashMap`，功能会坏吗？什么会坏？

**参考答案**（自测后再看）：

1. 两个：H2（车次档案：车次号/时刻/票价/额定座位）+ Redis（余票 stock）；一次循环里每个车次各摸一次 Redis。
2. 显示 0 张（`s == null ? 0`，:42 行）。宁可显示售罄也不显示虚构的票——余票数据"错杀"安全、"放行"危险。
3. DECR 是先斩后奏，负数说明这次"不该扣"；不还票则库存被永久污染，并发下越扣越负、从此对不上账，再也无法对账（T06 的三律全毁）。
4. 上一轮实验成功的那单在 5 分钟后被 `closeExpired()` 关单回补（T05 的机器人）——运维干扰项第三次现身，实验前必须 `get` 确认真值。
5. 功能不坏（查询照样返回），坏的是字段顺序——JSON 输出顺序随机化，前端阅读/调试/快照比对全遭殃。

## 8. 本节小结

- 查询读双货架：H2 档案 + Redis 活数，一次请求横跨两种存储。
- stock 是权威存储而非副本：不存在"DB 与缓存谁对"的问题，Redis 就是唯一真身。
- DECR 先斩后奏：减完发现负数必须 INCR 还票——这是防超卖的第一个闸门。
- down stock 实测：stock 压到 2 连点 3 下 → 2 成功 1 拒绝（"已售罄"），且演示了"实验前必须 get 确认真值"的运维纪律。
